# AxOS

AxOS — экспериментальная учебная операционная система, написанная на
Assembler и C, с двумя независимыми портами: **x86-64** (загрузчик проходит
весь путь real mode → protected mode → long mode) и **RISC-V (rv64)** под
OpenSBI/QEMU `virt`. Оба ядра — с прерываниями, многоуровневой страничной
памятью, пользовательским режимом, кучей, вытесняющим планировщиком с
приоритетами и файловой системой FAT12 — и дают интерактивный shell, в
котором всё это можно проверить вживую в QEMU.

## Возможности

**Общее для обеих архитектур:**
- Вытесняющий планировщик с приоритетами (`nice <pid> <1-10>`) — приоритет
  определяет, сколько последовательных тиков таймера задача удерживает CPU
  за один заход по кольцу (weighted round-robin, не строгие уровни)
- Куча с усилением в духе hardened_malloc/ARM MTE: 64-битный tag+redzone
  (детект underflow) + канарейка + карантин из последних `free()`
- FAT12 файловая система (чтение и запись, изменения переживают перезапуск)
- Интерактивный shell с внешними программами, конвейерами и фоновыми задачами

**x86-64:**
- Собственный загрузчик: реальный режим (16 бит) → защищённый режим
  (32 бита) → **long mode** (64 бита): `CR4.PAE` → `EFER.LME` → `CR0.PG`,
  far jump в 64-битный сегмент кода
- GDT с 64-битным TSS, кольцами 0 и 3 (ring3 — 32-битный compatibility mode)
- IDT (64-битные врата, 16 байт на запись): таймер PIT (IRQ0, 100 Гц),
  клавиатура (IRQ1), `#PF`, `int 0x80` (системные вызовы)
- Страничная память: полная 4-уровневая адресация (PML4→PDPT→PD→PT),
  identity-map первых 4 МБ, `NX`/`SMEP`/`SMAP`, постраничный W^X для
  пользовательских программ, `.text` ядра read-only, `CR0.WP`
- GCC `-fstack-protector-strong` для ядра (64-битная канарейка) поверх уже
  имевшегося userspace-стек-протектора
- Пользовательский режим (ring3, 32-битный compat mode): переход через
  `iretq`, обратно в ring0 — через `int 0x80` и TSS
- Куча ядра: 32 МБ (`0x400000`+, 2МБ huge pages), поверх — MTE-style
  усиление (см. выше)
- Preemptive планировщик (IRQ0): задачи ring0 и ring3, у каждой свой стек и
  свой стек ядра (per-task `TSS.RSP0`), с приоритетами (`nice`)
- MAC (Type Enforcement в духе SELinux) + MLS-уровни чувствительности

**RISC-V (rv64):**
- S-mode ядро под OpenSBI (QEMU `virt`), U-mode пользовательские процессы,
  Sv39 страничная адресация с W^X-хардненным ядром и приватными таблицами
  на процесс (изоляция)
- Драйверы virtio: блочное устройство, GPU (framebuffer), input (клавиатура
  и мышь)
- Собственный shell AxSH (`run`/`kill`/`nice`/`ps`/файловые команды) и
  набор пользовательских программ (текстовый редактор, рисовалка, тесты кучи
  и др.) — см. раздел "RISC-V порт" ниже

## Технологии

- Языки: Assembler (NASM для x86, GNU `as`/GAS для RISC-V), C
- Среда: Windows + `w64devkit` (MinGW: gcc/ld/objcopy, x86-64) и отдельный
  `riscv64-unknown-elf`-тулчейн (`riscv-gcc/`, RISC-V)
- Инструменты: NASM (`tools/nasm.exe`), Python (генерация образов FAT12 —
  `tools/make_fat12.py`/`make_fat12_rv64.py`), QEMU
  (`qemu-system-x86_64`/`qemu-system-riscv64`)
- Архитектуры: x86-64 (long mode, ring3 — 32-битный compat mode) и
  RISC-V rv64 (S-mode/U-mode, Sv39)

## Быстрый старт

### x86-64

Сборка (Windows, из корня репозитория):

```bat
build.bat
```

`build.bat` сам подставляет `w64devkit\bin` в `PATH`, собирает все
ассемблерные и C-файлы (ядро — `gcc -m64`, long mode; пользовательские
программы — `gcc -m32`, ring3 compatibility mode), линкует их в
`build\kernel.bin` и склеивает `build\boot.bin` + `build\kernel.bin` в
`build\os-image.bin` (дискета 1.44 МБ). Отдельно генерирует FAT12-образ из
содержимого `fs/` (`tools/make_fat12.py`) и записывает его в первые 256 КБ
`build\disk.img` (10 МБ, физический диск IDE).

Запуск в QEMU:

```bat
run.bat
```

или вручную:

```bat
qemu-system-x86_64 -drive format=raw,file=build\os-image.bin,if=floppy -boot a ^
  -drive format=raw,file=build\disk.img,if=ide,index=0,media=disk -cpu Broadwell
```

**Важно**: нужен именно `qemu-system-x86_64`, а не `qemu-system-i386` — с
переходом ядра на long mode образу требуется `EFER.LME`, которого нет у
`i386`-эмулятора. Флаг `-cpu Broadwell` обязателен: без него QEMU не
подставит SMAP (используется для харднинга страничной памяти, см.
"Архитектура" ниже) — на CPU без SMAP ядро тоже загрузится (детектирует
поддержку через CPUID и просто не включит соответствующий бит CR4), но
часть демонстраций харднинга не будет иметь эффекта.

После загрузки автоматически запускается AxSH (`SH.BIN`, полноценный
Unix-подобный shell с конвейерами и фоновыми задачами — см. "Команды
shell") и появится приглашение `$ ` — наберите `help`, чтобы увидеть
список встроенных команд.

### RISC-V (rv64)

Независимый порт под QEMU `virt`/OpenSBI, живёт в `src/arch/riscv64/` +
`src/user/rv64/`, собирается отдельным скриптом:

```bat
build_riscv.bat
```

Требует отдельный тулчейн `riscv64-unknown-elf`-типа (в этом репозитории —
`riscv-gcc/`, xPack RISC-V GCC). Собирает ядро (`gcc -march=rv64imac_zicsr
-mabi=lp64 -mcmodel=medany`) и ~20 пользовательских ELF-программ, кладёт их
в `rv64build\fs\rv64\` и генерирует `rv64build\disk.img` через
`tools\make_fat12_rv64.py`.

Запуск в QEMU (нужны virtio-блок/GPU/клавиатура/планшет-мышь; сеть
опциональна — без неё `virtio_net_init()` просто не находит устройство и
`SYS_NET_*` безобидно отдают -1/0):

```bat
qemu-system-riscv64 -M virt -bios default -kernel rv64build\out\kernel.elf ^
  -drive file=rv64build\disk.img,if=none,id=hd0,format=raw ^
  -device virtio-blk-device,drive=hd0 -device virtio-gpu-device ^
  -device virtio-keyboard-device -device virtio-tablet-device ^
  -netdev user,id=net0 -device virtio-net-device,netdev=net0
```

После загрузки — приглашение AxSH/RV64 (`src/user/rv64/axsh.c`), команда
`help` печатает список.

## Архитектура (x86-64)

### Загрузка: real mode → protected mode → **long mode**

1. **`src/boot/boot.asm`** (грузится BIOS по адресу `0x7C00`, реальный
   режим):
   - первым делом копирует себя целиком (все 512 байт сектора) на
     `0x0600` и продолжает выполнение оттуда (`jmp relocated_start +
     RELOC_DELTA`) - буфер чтения ядра (см. ниже) доходит до `0xC200`,
     то есть проезжает через `0x7c00`-`0x7e00`, где BIOS изначально
     положил сам загрузчик; без переезда входящие с диска данные
     переписывали бы код, который ещё не доисполнился, и BIOS молча
     зависал в середине `int 0x13` (не `jc`, без кода ошибки). `jc`/`jne`/
     `jmp`-на-метку в 16-битном режиме кодируются относительно
     (position-independent, работают и после переезда без изменений);
     вручную поправлены только абсолютные места - указатель на GDT
     (`gdt_descriptor`) и far jump в защищённый режим (`gdt.asm`,
     `switch_to_pm.asm`, обе через `RELOC_DELTA`);
   - переключает видеорежим в 80×25 текст;
   - читает ядро (89 секторов = 45568 байт) с диска в память по адресу
     `0x1000`;
   - подключает `src/kernel/gdt.asm` (таблица GDT, включая дескрипторы
     ring3-кода/данных, 64-битного кода ядра и TSS) и
     `src/boot/switch_to_pm.asm`;
   - переключается в защищённый режим (`switch_to_pm`, `CODE_SEG=0x08`) и
     передаёт управление на метку `BEGIN_PM` (та же секция, `[bits 32]`).
   - **`BEGIN_PM`** (`boot.asm`, ещё в 32-битном защищённом режиме) готовит
     переход в long mode:
     1. обнуляет 3 страницы (`0x9C000`/`0x9D000`/`0x9E000`) под временные
        `PML4`/`PDPT`/`PD`;
     2. `PML4[0] → PDPT`, `PDPT[0] → PD` (P|RW|US);
     3. `PD[0]` = 2 МБ huge page `0x000000-0x1FFFFF` (P|RW|US|PS,
        доступна ring3), `PD[1]` = 2 МБ huge page `0x200000-0x3FFFFF`
        (P|RW|PS, без US — ядро-only; сюда позже лягут слоты
        пользовательских программ, см. ниже);
     4. `CR4.PAE = 1`, `CR3 = 0x9C000` (адрес PML4);
     5. `EFER.LME = 1` через MSR `0xC0000080` (`rdmsr`/`or`/`wrmsr`);
     6. `CR0.PG = 1` — активирует long mode (CR0.PE уже 1);
     7. far jump `jmp dword 0x18:(long_mode_64 + RELOC_DELTA)` в
        `CODE64_SEG` (64-битный сегмент кода) — адрес обязан быть
        релоцированным (`+RELOC_DELTA`), как и в исходном переходе в
        protected mode.
   - **`long_mode_64`** (`[bits 64]`, тот же файл): обнуляет сегменты
     данных (`ds/es/ss/fs/gs = 0`) и абсолютным переходом через регистр
     (`mov rax, 0x1000` / `jmp rax`) передаёт управление ядру.
2. **`src/kernel/kernel_entry.asm`** (полностью `[bits 64]`) — точка входа
   `_start` (указана как `ENTRY` в `kernel.ld`): выставляет `rsp = 0x90000`,
   обнуляет `.bss` (`rep stosb` от `__bss_start` до `__bss_end` — реальное
   железо не гарантирует нулевую RAM при старте) и вызывает `kernel_main()`
   (Windows x64 ABI: `RSP` перед `call` должен быть выровнен на 16 байт —
   `0x90000` кратно 16, GCC-пролог сам компенсирует вычитаемые `call`'ом
   8 байт через `push rbp`). Комментарий в файле уточняет: в PE-x86-64
   (`pe-x86-64`) GCC/ld не добавляет подчёркивание к именам символов,
   поэтому `extern kernel_main`, а не `_kernel_main`.
3. **`kernel_main()`** (`src/kernel/kernel.c`) первым делом — ДО вообще
   любого другого вызова — вызывает `kernel_init_stack_guard()` (сидит
   `__stack_chk_guard` через `rdtsc64()`, см. "Stack-protector" ниже; если
   вызвать позже, первые же защищённые функции получили бы нулевой
   BSS-canary). Дальше — `init_ttys()` → `init_idt()` → `init_mouse()` →
   `init_paging()` (переход на полноценную 4-уровневую адресацию + NX/
   SMEP/SMAP, см. "Память" ниже) → `kcfi_init()` → `init_tss()` →
   `init_heap()` → `init_tasking()` (плюс встроенные демо-задачи
   `heartbeat`/`ring3demo`) → `vfs_init()` (загружает FAT12-том с
   `build/disk.img` через IDE) → автозапуск `run SH.BIN` (полноценный
   ring3-shell AxSH — см. "Команды shell") и уходит в цикл
   `while(1) { hlt; }`, ожидая прерываний.

### GDT / IDT / прерывания

- **GDT** (`src/kernel/gdt.asm`), актуальные селекторы:

  | Селектор | Назначение |
  |---------:|-------------|
  | `0x08` (`CODE_SEG`) | 32-битный код — используется только во время перехода boot → long mode |
  | `0x10` (`DATA_SEG`) | данные, общий для 32/64-бит |
  | `0x18` (`CODE64_SEG`) | **основной 64-битный сегмент кода ядра** (`L=1`) |
  | `0x20` (`USER_CODE_SEG`) | ring3, **32-битный compatibility mode** (`L=0, D=1`, DPL=3) |
  | `0x28` (`USER_DATA_SEG`) | ring3 данные |
  | `0x30` (`TSS_SEG`) | TSS64 — 16-байтный дескриптор (2 слота GDT, в 64-бит режиме TSS больше не помещается в 8 байт) |

- **IDT** (`src/kernel/idt.asm`), 64-битные врата (16 байт на запись, было
  8 в 32-битном режиме): обработчики
  - IRQ0 (таймер PIT, настроен на 100 Гц) — увеличивает `timer_ticks`,
    используется командами `uptime`/`sleep`, а также приводит в действие
    планировщик (см. "Многозадачность");
  - IRQ1 (клавиатура) — читает скан-код через порт `0x60`, переводит в
    символ по таблице из `src/drivers/keyboard.h` и кормит командную строку;
  - `#PF` (исключение 14, page fault) — `page_fault_handler_main`
    (`paging.c`) печатает адрес из `CR2` и код ошибки; если фолт произошёл
    в ring0 ядра или встроенных неизолированных демо-задач — останавливает
    систему, если в ring3 у изолированной `run`-задачи — убивает только её
    (см. "Жизненный цикл задач"); отдельно распознаёт и подписывает
    SMEP/NX-fault (попытка исполнить пользовательскую страницу из ядра) и
    SMAP-fault (обращение ядра к данным на пользовательской странице без
    `stac`) — см. "Память" ниже;
  - `int 0x80` — системные вызовы (см. ниже), шлюз с `DPL=3`, чтобы ring3
    мог его вызывать.

### Память: страничная организация и защита

`init_paging()` (`src/kernel/paging.c`) настраивает полную **4-уровневую**
x86-64 адресацию — `PML4 → PDPT → PD → PT` (не PAE-only, честная long-mode
адресация с 64-битными PTE и битом `NX`/XD). Boot-временные 2 МБ huge pages
(см. "Загрузка" выше) заменяются 4 КБ-страницами через `GLOBAL_PT0`
(идентичный маппинг первых 2 МБ). Постоянные физические адреса структур
(не статические массивы в `.bss`, чтобы не раздувать `kernel.bin`):

```
0x9C000 — GLOBAL_PML4   0x9D000 — GLOBAL_PDPT
0x9E000 — GLOBAL_PD     0x9F000 — GLOBAL_PT0 (4КБ-страницы, VA 0x0-0x1FFFFF)
```

Страницы, целиком лежащие внутри `.text` ядра, помечаются read-only;
включаются `CR0.PG`/`CR0.WP` — даже ring0 не может случайно записать в
собственный код.

**Аппаратный харднинг (CPUID-детект, safe fallback на CPU без поддержки):**

- **NX** (CPUID `0x80000001`, EDX[20]) — страницы данных помечаются
  неисполняемыми.
- **SMEP** (CR4[20], CPUID.07H:EBX[7]) — запрещает ядру (ring0)
  **исполнять** код со страниц с флагом `US=1` (пользовательских); защита
  от классической атаки "jump to user-mode shellcode" (ret2usr). Для этого
  у ядровых страниц в `GLOBAL_PT0` снят флаг `US`.
- **SMAP** (CR4[21], CPUID.07H:EBX[20]) — запрещает ядру **читать/писать**
  данные на пользовательских страницах без явного `stac`/`clac`
  (`smap_allow()`/`smap_deny()`, `paging.c`, кодируются вручную через
  `.byte 0x0F,0x01,0xCB`/`0xCA` — тулчейн не знает мнемоники stac/clac);
  оборачивает каждую запись ядра в пользовательское окно (копирование ELF-
  сегментов, ASLR-патчинг, argv-блок, диспетчер syscall'ов).
- `page_fault_handler_main()` отдельно распознаёт и подписывает нарушения
  SMEP (`[SMEP/NX] kernel exec fault`) и SMAP (`[SMAP] kernel data access
  to user page ... (missing stac?)`) — вместо непонятного общего `#PF`.
- Лог `[paging] NX=... SMEP=... SMAP=...` печатается при каждой загрузке.
- Требует `-cpu Broadwell` в QEMU (Haswell поддерживает SMEP, но не SMAP).

**W^X постранично для пользовательских программ**: `USER_PROGRAM_BASE`
(куда ядро копирует ELF-сегменты перед запуском) перенесён на `0x200000` —
это supervisor-huge-page `PD[1]` (ядро-only), запись туда не требует
`stac`/SMAP вообще. Граница код/данные ELF-сегмента (`wx_data_off`)
выбирается так, что ASLR-дельта всегда попадает точно на границу 4 КБ-
страницы — иначе одна и та же страница не может быть одновременно
"только код" (R+X) и "только данные" (RW+NX), что раньше давало ложный
NX-execute-fault (проявлялось в `ls.bin`). Итог: каждая 4 КБ-страница
пользовательской программы — либо R+X, либо RW+XD, никогда оба сразу
(`paging_create_user_directory()`, `paging.c`). Демо: `src/user/wxdemo.c`
(`run WXDEMO.BIN`) проверяет W^X живьём.

**Изоляция**: пул приватных PML4/PDPT/PD/PT для до 4 изолированных
`run`-задач — `PML4_POOL_BASE`/`PDPT_POOL_BASE`/`PD_POOL_BASE`/
`PT_POOL_BASE` = `0x140000`/`0x144000`/`0x148000`/`0x14C000` (см. "Изоляция
памяти" ниже — детали устройства не изменились, изменились только адреса
пула из-за добавления двух уровней таблиц).

### Stack-protector (ядро)

`build.bat`: `KFLAGS` включает `-fstack-protector-strong` (раньше защита
была только у userspace-библиотеки `libaxiom`, у самого ядра — не было
вообще). `src/kernel/stack_chk.c`:

- `__stack_chk_guard` — **64-битный** (`unsigned long long`), не
  `unsigned long`: на этом тулчейне (MinGW/w64devkit) `unsigned long` — это
  32 бита (LLP64), а сгенерированный GCC-пролог реально грузит honest
  64-битное значение (`movq .refptr.__stack_chk_guard(%rip), %rbx; movq
  (%rbx), %rax`) — 32-битный guard читал бы мусор в старших 4 байтах и либо
  ловил бы постоянные ложные срабатывания, либо (хуже) утекал соседнюю
  память как часть значения.
- Нет TLS: тулчейн не использует `%fs:0x28` (как типичный Linux gcc), а
  обычный глобальный символ через refptr-таблицу — удобно, поскольку TLS в
  этом freestanding-окружении не настроен вообще.
- `kernel_init_stack_guard()` сидит guard через `rdtsc64()` XOR
  `0x9E3779B97F4A7C15` (golden-ratio константа, защита от нулевого guard) —
  **обязана** быть первым вызовом в `kernel_main()` (см. "Загрузка" выше).
- `__stack_chk_fail()` печатает `*** STACK SMASHING DETECTED ***` и уходит
  в `hlt`-цикл, как и `heap_corrupted()`.
- Гочка при тестировании: переполнение буфера через `for`-цикл с
  константной верхней границей — GCC считает выход за границы локального
  массива недостижимым UB и может **оптимизировать прочь саму проверку
  границы**, получая настоящий бесконечный цикл записи (triple fault)
  вместо срабатывания canary; тестовый код должен писать по фиксированным
  индексам, а не в цикле.

### Пользовательский режим (ring3) и системные вызовы

`src/kernel/usermode.asm` (`enter_usermode`, вызывается из 64-битного ядра
по Windows x64 ABI) готовит на стеке кадр для **`iretq`** с селекторами
ring3 32-битного compatibility mode (`USER_CODE_SEG=0x20 | 3`,
`USER_DATA_SEG=0x28 | 3`) и переключает CPU в CPL=3 с отдельным стеком
`0x9B000`. Ring3-код по-прежнему честный 32-битный (все ~30 пользовательских
программ — обычные ELF32, `gcc -m32`, ни строчки не менялось при переходе
ядра на long mode — см. коммит "Transition kernel to x86-64 long mode").
Команда shell `usermode` демонстрирует переход в ring3 и обратный вызов в
ring0 через `int 0x80`.

`src/kernel/tss.c` настраивает **TSS64** (104 байта) по адресу `0x9B000`
(`TSS_BASE`, `RSP0` по смещению 4 — 8 байт, не 4, как у 32-битного TSS):
при прерывании/исключении/`int 0x80`, случившемся в ring3, CPU переключает
стек на стек ядра по этому значению; `tss_set_rsp0()` вызывается
планировщиком при каждом переключении задачи.

`src/kernel/syscalls.asm` — тонкий мост `int 0x80` → `syscall_dispatch()`
(`kernel.c`): сохраняет регистры, передаёт код функции (`AH`) и аргумент
(`ESI`) в диспетчер (код чтения `AH` из `[rsp+1]`, а не через `mov ah, ...`
напрямую — избегает конфликта REX-префикса с адресацией "high byte"
регистра в 64-битном режиме кодирования).

Коды функций и структуры аргументов определены в `src/user/syscall.h` —
общем заголовке для ядра и ring3-программ (`SYS_*`-константы). **Важная
особенность сборки**: это ОДИН ИЗ ДВУХ независимых, вручную
синхронизируемых копий ABI — `src/user/syscall.h` (для ring3-программ,
32-бит) и `src/libaxiom/include/syscalls.h` (общий заголовок библиотеки
`libaxiom`, тоже 32-бит, включается через `axiom.h`); при добавлении
нового syscall нужно поправить оба файла плюс саму обёртку в
`src/libaxiom/src/syscalls.asm`, иначе сборка `libaxiom`-программ падает с
"undeclared" (тот же паттерн независимо повторён и в RISC-V-порте — см.
ниже).

### Куча (`src/kernel/heap.c`/`heap.h`)

Классический связный список блоков (`block_header_t { size, free, next,
magic, tag }`) над регионом `KHEAP_BASE`–`KHEAP_BASE+KHEAP_SIZE`
(`0x400000`, **32 МБ** — 16 huge pages по 2 МБ сразу после первых 4 МБ
identity-map, см. "Память" выше). Регион расширен с исходных 192 КБ
(`0x60000`-`0x90000`, тесно зажатых между FAT12-образом и стеком ядра) при
переходе на long mode, когда честная 4-уровневая адресация сделала это
дёшево — см. `paging.h`:

- `init_heap()` — один свободный блок на весь регион, вызывается один раз при
  старте ядра;
- `malloc(size)` — выравнивание до 4 байт, поиск первого подходящего
  свободного блока (first-fit), при избытке места — разбиение;
- `free(ptr)` — отправляет блок в карантин (см. ниже), а не сразу обратно в
  free-list.

Команда shell `memtest` прогоняет `malloc`/`free` через несколько сценариев
(выделение, переиспользование адреса после `free`, слияние блоков при
выделении большого блока) и печатает `PASS`/`FAIL` (с момента добавления
карантина немедленное переиспользование адреса больше не гарантировано —
тест печатает информационный `WARNING`, не считает это сбоем).

#### Усиление кучи: теги + карантин (software-аналог ARM MTE)

Настоящий ARM Memory Tagging Extension (4-битный тег на каждые 16 байт RAM,
аппаратная проверка через TBI — игнорирование верхних битов адреса при
трансляции) на x86 не портируется буквально: закодировать тег в старших
битах указателя, как делает ARM, сломало бы каждый вызов `malloc()` в
`kernel.c`/`tasking.c` — все они используют результат как обычный 32-битный
адрес, без аппаратного "снятия" тега. Вместо этого — software-only аналог,
проверяемый самим аллокатором (а не на каждом обращении к памяти):

- **magic** в заголовке отличает "выделенный блок" от "свободного"/"в
  карантине"/чужого мусора — `free()` отказывает на double-free и на
  указателе, чей заголовок не похож на блок, который выдавал этот же
  `malloc()`.
- **tag** — изначально 4 бита, позже расширен до полных **64 бит**
  (`unsigned long long tag`, больше пространство состояний генераций — то
  же самое расширение сделано во всех четырёх аллокаторах проекта: x86-ядро,
  x86-userspace, RV64-ядро, RV64-userspace) — вшит в канарейку
  (`tagged_canary`) сразу после пользовательских данных — переполнение,
  которое раньше тихо переписывало заголовок СЛЕДУЮЩЕГО блока, теперь
  детектируется в `free()` до того, как испорченный заголовок успеет что-то
  сломать. Дополнительно добавлен **левый redzone** перед пользовательскими
  данными — детектирует underflow (запись ДО начала своего блока), которую
  одна только канарейка-после-данных не поймала бы.
- **Карантин** (кольцо на `QUARANTINE_CAPACITY` = 8 последних `free()`):
  блок не виден `malloc()`, пока не вытеснен из карантина (FIFO) — типичный
  use-after-free сразу после `free()` с большей вероятностью попадёт в блок,
  который ещё никто не успел переиспользовать. Отравление данных
  (фиксированным паттерном `0xDD`) и слияние с соседями происходят только
  при вытеснении из карантина, не в момент самого `free()` — это
  принципиально важно: `schedule()` (`tasking.c`) освобождает кадровый стек
  задачи, выполняющейся прямо сейчас НА ЭТОМ ЖЕ стеке (`RSP0`/CR3
  переключаются позже) — запись в блок непосредственно в `free()` означала
  бы запись под собственным текущим кадром вызовов (на этом и попался первый
  вариант реализации — раньше срабатывал triple fault на каждом выходе
  изолированной `run`-задачи).

При обнаружении double-free, чужого указателя или испорченной канарейки
ядро печатает `*** HEAP CORRUPTION: <причина> *** System halted.` и
останавливается (`hlt`-цикл) — детерминированный громкий отказ вместо тихой
порчи кучи.

### Многозадачность (tasking.c)

Preemptive планировщик: задачи — обычные C-функции с бесконечным циклом,
каждая на своём стеке (`malloc`, 4 КБ). Переключение происходит в
обработчике таймера (IRQ0, `idt.asm`): вместо `pusha`/`popa` (не существуют
в 64-битном режиме) — явные `push r15`..`push rax` (15 GPR) на стеке задачи,
оставляющие кадр `[15×push][RIP][CS][RFLAGS]` (и `[RSP][SS]`, если задача
была в ring3) — `schedule()` (сигнатура теперь принимает/возвращает
`unsigned long long rsp`) сохраняет текущий `rsp`, выбирает следующую задачу
и возвращает её `rsp`; обратные `pop`'ы + `iretq` резюмируют уже её.

- `task_create(name, entry)` — создаёт задачу ring0 (`CS=0x18`, 64-битный
  сегмент кода ядра, кадр без привилегированного перехода).
- `task_create_user(name, entry)` — создаёт задачу ring3 (32-битный compat
  mode, `CS=0x20|3`, `SS=0x28|3`): на стеке ядра задачи собирается кадр
  `ring3 → ring0`, так что первый возврат сразу запускает её в CPL=3.
- У каждой задачи свой стек ядра (`KSTACK_SIZE`, 4 КБ) — `schedule()`
  обновляет `TSS.RSP0` (`tss_set_rsp0()`, `tss.c`) под текущую задачу при
  каждом переключении, чтобы переходы `ring3 → ring0` (IRQ/`int 0x80`) одной
  задачи не портили стек другой.
- У каждой задачи свой `page_directory` (теперь CR3 = физический адрес
  PML4, не PD) — для `task_create`/`task_create_user` это общий
  `PAGE_DIRECTORY` (`paging.h`, без изоляции), а для
  `task_create_user_isolated` — приватный PML4/PDPT/PD/PT (см. "Изоляция
  памяти" ниже). При переключении на задачу с другим `page_directory`, чем
  у предыдущей, `schedule()` перезагружает CR3.

Две демо-задачи показывают работу планировщика прямо на экране: `heartbeat`
(ring0, символ `|/-\` в правом верхнем углу) и `ring3demo` (ring3, символ
`+x*.` рядом) — крутятся параллельно с основным shell. Команда `ps` печатает
список задач (`id`, имя, число тиков планировщика, приоритет).

#### Приоритеты планировщика (`nice`)

Weighted round-robin, не строгие уровни приоритета: поле `task_t.priority`
(1-10, по умолчанию 3) определяет, сколько ПОСЛЕДОВАТЕЛЬНЫХ тиков таймера
задача удерживает CPU за один заход по кольцу, прежде чем `schedule()`
перейдёт к следующей — `task_t.slice_left` считает оставшиеся тики текущего
захода, сбрасываясь на `priority` при каждом новом заходе. Задача с
приоритетом 1 всё равно получает своё время, просто реже, чем задача с
приоритетом 10 — никакого голодания. `task_set_priority(pid, priority)`
(`tasking.c`) вызывается через `SYS_SET_PRIORITY` (`0x24`) и доступна из
AxSH командой `nice <pid> <1-10>` (см. "Команды shell"). Идентичный
механизм реализован и на RISC-V-порте (см. ниже) — проверено вживую на
обеих архитектурах: два процесса с приоритетами 1 и 10 показывают в `ps`
прирост тиков за одинаковое время примерно в 4-8 раз в пользу
высокоприоритетного (не ровно 10:1, т.к. конкурируют и другие задачи с
приоритетом по умолчанию).

### Жизненный цикл задач (task exit/cleanup)

У каждой задачи (`task_t`, `tasking.c`) есть поля `user_slot_index` (-1 для
`task0`/`heartbeat`/`ring3demo`, 0..3 для `run`-задач) и `exiting` (0 —
работает, 1 — помечена на удаление). Оба пути завершения ниже просто
выставляют `exiting=1` через `task_mark_current_exiting()` — реальное
удаление происходит в `schedule()` на следующем тике таймера:

1. находит предшественника умирающей задачи в кольце и убирает её оттуда
   (`pred->next = next`);
2. если `user_slot_index >= 0` — зовёт `on_task_exit(idx)` (`kernel.c`),
   освобождая слот `run` (`slot_free[idx] = 1`);
3. освобождает (`free`) кадровый стек задачи и сам `task_t`.

Инвариант, который делает unlink безопасным без проверки "пустого
кольца": `exiting` выставляется только у `run`-задач —
`task0`/`heartbeat`/`ring3demo` никогда не завершаются, поэтому кольцо
планировщика никогда не опустеет.

**Добровольный выход — `SYS_EXIT` (`0x06`)**: `src/libaxiom/src/crt0.asm`
(реальная точка входа для всех программ, слинкованных с libaxiom —
`src/user/start.asm` оставлен как более старый, ныне не используемый
сборкой вариант) после `call _main` переносит `EAX` (возврат `main()`,
cdecl) в `ESI` и выполняет `mov ah, 0x06; int 0x80`. Если `main()`
вернулась (как `exitdemo.c`, `return 7;`), `sys_exit()` (`kernel.c`)
записывает `ESI` как код выхода (`task_set_current_exit_code`) и
помечает текущую задачу на завершение. Для `hello.c` (бесконечный цикл в
`main`) этот код недостижим — поведение не меняется.

**Код выхода и `kill <pid>`**: `task_t` (`tasking.c`) получил поле
`exit_code`, записываемое либо самой задачей (`sys_exit`/`ax_exit(code)`),
либо ядром при аварийном завершении (`-1` — Ctrl+C, `kill <pid>`, page
fault в ring3). `on_task_exit(slot, exit_code)` (`kernel.c`) сохраняет его
в `slot_exit_code[slot]` РОВНО в момент реапа задачи в `schedule()` — тот
же момент, когда `slot_free[slot]` становится `1` и `SYS_TASK_ALIVE`
впервые сообщает "завершена". Родитель (обычно `sh.c`, поллящий
`ax_task_alive` в цикле после `ax_set_foreground`) вызывает
`ax_exit_code(slot)` (`SYS_LAST_EXIT_CODE`, `0x28`) сразу после этого и
печатает `[exit code: N]`. Новая команда `kill <pid>` (`SYS_KILL`, `0x29`,
`task_kill_by_pid` в `tasking.c`) убивает ЛЮБУЮ изолированную задачу по
pid — не только foreground-задачу активной консоли, как Ctrl+C — и
работает симметрично RISC-V-порту (`axsh.c`'s `kill`), хотя ABI между
платформами не совпадает 1:1: x86 остался slot-центричным
(`SYS_TASK_ALIVE`/`SYS_SET_FOREGROUND` по-прежнему принимают slot, не
pid — как и раньше), только `kill`/`nice` адресуются по pid, как в
`ps`. Ring0/builtin-задачи (`shell`/`heartbeat`/`ring3demo`,
`user_slot_index == -1`) убить так нельзя — то же ограничение, что и у
Ctrl+C.

**Принудительный выход — kill при page fault в ring3**: `idt.asm`
передаёт в `page_fault_handler_main` указатель на кадр с явно сохранёнными
64-битными GPR (см. "Многозадачность" выше — `pusha` не существует в
64-битном режиме), откуда видны сохранённые `RIP`/`CS`. Если фолт произошёл
в ring3 у изолированной (`task_create_user_isolated`) задачи,
`page_fault_handler_main`:

- печатает `*** PAGE FAULT in '<name>' at 0x<addr> - task killed ***`;
- помечает задачу на завершение (`task_mark_current_exiting()`);
- перезаписывает `RIP` в кадре на `USER_SPIN_ADDR` — последние 2 байта
  окна задачи (`USER_WINDOW_BASE + USER_WINDOW_SIZE - 2` = `0x10FFFE`),
  куда `task_create_user_isolated` записывает `jmp $` (`EB FE`) при
  создании задачи;
- возвращается (не виснет) — `iretq` резюмирует ring3 на этом безопасном
  адресе (`PRESENT|RW|USER`, внутри своего окна), задача крутится в
  `jmp $`, "добивая" квант, до реапа в `schedule()` на следующем тике.

Начальный `RSP` изолированной задачи — `USER_STACK_TOP =
USER_WINDOW_TOP - 16` (`tasking.c`), а не сам верх окна: стек растёт вниз, и
первый push (`call _user_main` в `start.asm`) не должен затирать
`USER_SPIN_ADDR` до того, как он понадобится.

**"ASLR-подобный" разброс стека.** Полноценный ASLR (рандомизация базы
кода/данных) здесь недостижим без position-independent бинарников:
`user.ld` линкует все программы на фиксированный `0x100000`, абсолютные
ссылки в их коде это предполагают (см. "Изоляция памяти" выше). Зато
`task_create_user_isolated` сдвигает САМ СТАРТ стека на случайные 0–1024
байта (кратно 16, `STACK_ASLR_MAX_SHIFT`) вниз от `USER_STACK_TOP` — через
xorshift32, перемешанный с `timer_ticks` на каждый запуск (`tasking.c`).
Эксплойт, рассчитанный на точный фиксированный адрес стека, промахивается;
сдвиг заведомо безопасен — между `USER_STACK_TOP` (`0x10FFF0`) и блоком
`argv` (`USER_ARGS_VADDR`, `0x10F800`) около 2000 байт зазора.

Page fault в ring0 (баг ядра) или у встроенных демо-задач без изоляции
(`ring3demo`/`usermode`) — как и раньше, останавливает всю систему
(`*** PAGE FAULT at 0x... ***` / `System halted.`).

**Слоты `run`**: `slot_free[USER_PROGRAM_SLOTS]` (`kernel.c`) заменяет
прежний слепой round-robin — `run` ищет первый свободный слот; если все
4 заняты живыми задачами, печатает `No free program slots, try again
later.`.

**Демо**: `EXIT.BIN` (`src/user/exitdemo.c`) печатает строку и
возвращается из `user_main()` — проверяет `SYS_EXIT`/реап/освобождение
слота (`ps` после `run EXIT.BIN` вскоре больше не показывает задачу).
`CRASH.BIN` (`src/user/crashdemo.c`) печатает строку и пишет по адресу
вне своего виртуального окна `0x100000`-`0x110000` — проверяет kill-путь:
из `ps` исчезает только эта задача, `shell`/`heartbeat`/`ring3demo`
продолжают тикать. `WXDEMO.BIN` (`src/user/wxdemo.c`) аналогично проверяет
W^X — пытается исполнить код с writable-страницы своих данных.

### Потоковые pipes (`cmd1 | cmd2`) — x86 (RISC-V пока не реализовано)

Раньше `cmd1 | cmd2` (`sh.c`) был "пакетным": cmd1 выполнялся ПОЛНОСТЬЮ,
весь его stdout оседал во временном файле `PIPE.TMP` на диске, и только
после этого запускался cmd2 с именем `PIPE.TMP`, дописанным последним
аргументом. Никакой конкурентности, никакого потока — работало только
потому, что все программы-потребители (`cat.c`, `grep.c`) и так уже
принимают имя файла аргументом.

Теперь это настоящий потоковый конвейер, без единого нового syscall'а и
без единой правки в `cat.c`/`grep.c` — переиспользованы два уже
существующих механизма под зарезервированную строку `"PIPE:N"` вместо
настоящего имени файла:

- **Запись** — тот же путь, что и у обычного `> file` редиректа
  (`ax_exec_redir`/`SYS_EXEC_REDIR`, `slot_redir_buf`): `sys_exec_redir()`
  распознаёт `"PIPE:N"` и вместо приватного буфера, сбрасываемого на
  диск при выходе, направляет `sys_print_string()` в общий
  `pipe_bufs[N]` (`kernel.c`) — единственный на данный момент буфер в
  ядре, видимый ДВУМ разным задачам одновременно (писателю и читателю).
  При выходе писателя (`on_task_exit`) выставляется `writer_done` вместо
  сброса на диск.
- **Чтение** — тот же путь, что и у обычного `ax_open(filename)`/
  `ax_fread`: `sys_open()` распознаёт `"PIPE:N"` и создаёт fd с новым
  `struct fd_entry.type = FD_TYPE_PIPE` вместо загрузки файла с диска.
  `sys_fread()` на таком fd, если данных ещё нет и писатель жив,
  блокирует ТЕКУЩУЮ задачу (`task_wait_pipe_current`, tasking.c — то же
  поле-флаг `waiting_pipe`, что и `sleeping` у sleep-очереди, тот же
  wake-скан в `schedule()`, та же уже готовая машинерия немедленного
  переключения из `syscalls.asm`/`task_current_wants_resched`) и
  возвращает специальное значение `-2` ("пусто, повтори"). `_ax_fread()`
  (`syscalls.asm`) оборачивает свой `int 0x80` в цикл повтора при `-2` —
  цикл НЕ горячий, повтор происходит только после того, как задачу
  реально разбудили (данные пришли или писатель закрылся), а не в busy-wait.

`sh.c` запускает cmd1 и cmd2 сразу оба (было: дождаться cmd1 полностью,
потом запускать cmd2), foreground-ожидание — только на cmd2; EOF читателю
даёт `writer_done`, выставляемый автоматически при выходе cmd1.
`PIPE_MAX=2` слота по `PIPE_BUF_SIZE=2048` байт каждый; как и у старого
батч-редиректа, у писателя нет backpressure — переполнение молча
обрезает (не хуже прежнего поведения, просто теперь потоково, а не
пакетно).

Проверено вживую: `ls | grep BIN` даёт корректно отфильтрованный вывод
(без `MOTD.TXT`/`STARTUP.CFG`/прочего мусора), повторный запуск сразу
после первого корректно переиспользует слот pipe'а без утечки старых
данных, `ls | grep <несуществующее>` корректно возвращает пустой
результат и не виснет (EOF отрабатывает), обычный (не pipe'овый)
`run`/`kill`/exit-код не задеты.

### `fork()` — обе платформы

Последний пункт из списка улучшений многозадачности, теперь закрыт на
обеих платформах (в два раунда). Ни на одной платформе раньше не было
ВООБЩЕ никакого дублирования процесса - `exec()`/`elf_load()` всегда
грузят СВЕЖИЙ бинарник в СВЕЖЕЕ адресное пространство.

**x86** оказался на удивление несложным благодаря модели памяти
изолированных задач: каждая `run`-задача живёт в одном из
`USER_PROGRAM_SLOTS=4` **фиксированных, физически непрерывных** блоков
по 64КБ (`USER_PROGRAM_BASE=0x200000 + slot*USER_PROGRAM_SLOT_SIZE`,
`kernel.c`) - дублирование памяти процесса это ОДИН `memcpy` целого
слота в свободный, без обхода таблиц страниц.

**Клонирование регистрового состояния — в обход обычного диспетчера
syscall'ов**: обычные обработчики видят только `arg` (значение/указатель
из ESI) - `fork()` же нужен ВЕСЬ прерванный кадр GPR+iretq вызывающей
задачи целиком, чтобы потомок продолжил выполнение ровно с той же точки
(сразу после возврата из `int 0x80`), но с другим значением возврата.
`syscalls.asm`'s `syscall_handler` и так уже кладёт на стек 20-слотовый
(160 байт) кадр — 15 GPR (порядок `SAVE_REGS`: R15..RAX) + 5,
которые кладёт сам CPU (SS/RSP/RFLAGS/CS/RIP) — ДО вызова
`syscall_dispatch`. Новый `SYS_FORK` (`0x2A`) обрабатывается ОСОБО прямо
в `syscall_handler`: вместо обычного `syscall_dispatch(func, arg)` (C-
таблица) он напрямую зовёт `sys_fork_impl(unsigned long long
parent_rsp)` (тот же приём, что уже использован для вызовов
`schedule()`/`task_current_wants_resched()` в раунде sleep-очереди).
`sys_fork_impl` пишет результат ПРЯМО в RAX-слот кадра РОДИТЕЛЯ
(`frame[0]`, т.к. RAX кладётся последним = самый нижний адрес) - потомок
получает свой `RAX=0`, запечённый в СВОЮ отдельную копию кадра (см.
ниже) - это и есть механизм, которым `fork()` "возвращается дважды" с
разными значениями. Раз это в обход `syscall_dispatch`, теряется и его
автоматический `smap_allow()`/`smap_deny()` (см. `syscall_dispatch`) -
`sys_fork_impl` оборачивает копирование памяти сама, тем же приёмом, что
уже применён к записи argv в kernel-shell'овой команде `"run "` (тоже не
идёт через общий диспетчер).

**Дублирование памяти** (`kernel.c::sys_fork_impl`): найти свободный
слот потомку (нет — `-1`); потребовать, чтобы вызывающий сам был
изолированной задачей; `ax_mac_check(AX_CLASS_EXEC)` (тот же класс, что
и у `exec()`); `smap_allow()` + `memcpy` всего 64КБ слота родителя в
слот потомка + `smap_deny()`; построить `task_t` потомка через новую
`task_fork_current()` (`tasking.c`) — структурно параллельна
`task_create_user_isolated()`, но КЛОНИРУЕТ живой кадр родителя вместо
фабрикации свежего, и **копирует** (не сбрасывает) `mls_level`/
`syscall_mask`/`priority` — потомок стартует как точный снимок состояния
родителя, не со свежими значениями по умолчанию. Нужны те же
`wx_delta`/`wx_data_off`, которыми была построена директория страниц
родителя (скопированная память имеет тот же W^X-макет) — они нигде не
хранились после разового вызова `task_create_user_isolated()`, добавлены
`slot_wx_delta[]`/`slot_wx_data_off[]`, заполняемые в ОБОИХ независимых
местах, откуда вызывается `task_create_user_isolated` (`do_exec()` и
отдельная kernel-shell'овая команда `"run "`).

Однажды созданный, потомок **неотличим от `exec()`'нутой задачи** для
любой другой подсистемы — `kill <pid>`, чтение exit-кода, `nice`,
Ctrl+C, sleep и pipes все работают через `user_slot_index`/общие поля
`task_t`, а не через то, КАК задача была создана, так что ни одна из них
не потребовала fork-специфичных правок вообще.

**Сознательно НЕ наследуется в этой версии** (задокументированное
упрощение, не тихо забытое): открытые файловые дескрипторы (`fd_table`
остаётся привязан к слоту родителя, потомок стартует без единого) и
активный редирект вывода (`slot_redir_pipe`/`slot_redir_buf` у потомка
сбрасываются, не копируются). Настоящий POSIX `fork()` дублирует таблицу
fd — пропуск этого сохраняет первую версию компактной и корректной,
той же дисциплины, что уже принята для отсутствия backpressure у
писателя pipe'а и отсутствия COW.

Новый `SYS_FORK` (`0x2A`) без arg-структуры — ESI не используется,
результат приходит напрямую в EAX. `_ax_fork()` (`libaxiom/src/
syscalls.asm`) — просто `mov ah, 0x2A; int 0x80; ret`, никакой
структуры строить/разбирать не нужно, в отличие от всех остальных
обёрток в этом файле. `AX_SC_FORK` сознательно не входит ни в один
готовый seccomp-профиль (как и `AX_SC_KILL`/`AX_SC_REBOOT`) — клонирование
себя не относится к обычному жизненному циклу "запустить и дождаться".

Демо `FORKDEMO.BIN` (`src/user/forkdemo.c`) — классика: вызывает
`ax_fork()`, печатает "I am the CHILD" или "I am the PARENT, child
pid=N" в зависимости от возврата. Проверено вживую: оба сообщения
(родителя и потомка) появляются с корректным pid потомка; при
исчерпанных слотах (4/4 заняты) `ax_fork()` внутри уже запущенного
`forkdemo` корректно возвращает -1 ("fork failed") без краша; обычный
(не fork'нутый) `run`/`ls` не задеты.

**RISC-V** нужна была новая инфраструктура: страницы там выделяются
динамически по мере загрузки сегментов (bump-аллокатор), без какой-либо
существующей возможности "перечислить всё, что этот процесс успел
замапить". Новая `paging_fork_user_pages(src_root, dst_root)`
(`paging.c`) обходит таблицы страниц: единственная "живая" ветка
пользовательского адресного пространства - `root[1]` (см.
`paging_create_user_pt()`), и КАЖДОЕ маплено `elf_loader.c` туда - это
4KB-лист на уровне L0 (ни мега-, ни гигастраниц в пользовательском
пространстве не бывает) - так что обход это два вложенных цикла по 512
записям (L1 → L0), для каждого валидного листа: выделить новую
физстраницу, скопировать байты, замапить в `dst_root` по ТОМУ ЖЕ VA с
ТЕМИ ЖЕ флагами.

В отличие от x86, клонирование РЕГИСТРОВ здесь оказалось даже проще:
`syscall_dispatch(unsigned long *frame, unsigned long sepc)` и так уже
получает живой кадр параметром - `SYS_FORK` (`31`) обычный `case` в
существующем `switch`, никакого обхода диспетчера не требуется (в
отличие от x86, где `syscall_dispatch` пришлось обходить целиком - см.
выше). Автоматический хвост функции (`frame[REG_A0]=ret;
sepc+4`) сам отдаёт родителю pid потомка, как и любому другому
syscall'у - вручную нужно выставить `regs[]`/`sepc` только у ОТДЕЛЬНОЙ
`proc_t` потомка (он не "возвращается" из этого вызова вообще - строится
так, будто уже вернулся, с `a0=0`).

Как и на x86: потомок неотличим от обычного процесса для `kill`/`wait`/
`nice`/pipes (ничего не потребовало правок), открытые fd и активный
pipe-редирект не наследуются явно.

Демо `FORKTEST.ELF` (`src/user/rv64/forktest.c`) - то же самое, теперь
переносимо благодаря появившемуся в этой сессии argv (см. "Минимальный
argv" выше). Проверено вживую: оба сообщения появляются с верным pid
потомка. Отдельно найден и задокументирован (не баг, ожидаемое
поведение) нюанс при проверке исчерпания слотов: потомок, порождённый
`fork()`, которого никто не `wait()`'ит явно (как в этом демо - только
СВОЕГО родителя ждёт `axsh.c`, а не его потомка), становится **вечным
zombie** на RISC-V (уже задокументированный трейд-офф отсутствия
строгого parent/child-трекинга) - его слот навсегда потерян до
перезагрузки. Из `MAX_PROCS=4` эффективно доступно на один меньше сразу
после первого непойманного fork-потомка.

### Терминалы (TTY) — Ctrl+Alt+F1/F2

Две независимые виртуальные консоли (`TTY_COUNT=2`, `src/kernel/screen.c`),
каждая со своим буфером экрана 80×25×2 байта (символ+атрибут), курсором и
состоянием ANSI-парсера — вывод на неактивной консоли (например, фоновая
задача) никогда не задевает то, что видно на экране. `Ctrl+Alt+F1`/
`Ctrl+Alt+F2` переключают активную консоль (`tty_switch()`, копирует буфер
целевой консоли в реальную видеопамять `0xB8000`); если на этой консоли
ещё никогда не запускали shell — на ней автоматически стартует `SH.BIN`,
как при обычном autoboot.

Хранятся консоли по фиксированному физическому адресу `TTYS_BASE`
(`0x160000`), а не как статический массив в `.bss` — см. "Карта памяти"
ниже и найденный/исправленный там же баг с пересечением адресов.

### Файловая система (FAT12 на build/disk.img)

`src/fs/fat12.c`/`fat12.h` — драйвер FAT12-тома (2 МБ, 4096 секторов,
4079 кластеров данных по 512 Б), который физически живёт в первых 2 МБ
(LBA 0-4095) `build/disk.img`. При старте ядра `fat12_init()` читает эти
4096 секторов через `ide_read_sector` в RAM по адресу `0x300000`
(supervisor-only, сразу после слотов пользовательских программ
`0x200000`-`0x23FFFF` — см. "Карта памяти") — дальше всё работает с этой
RAM-копией, как с обычным FAT12-томом. Сам том собирается из файлов
каталога `fs/` скриптом `tools/make_fat12.py` и записывается в
`build/disk.img` при сборке (`build.bat`).

Чтение: `fat12_list()` (команда `ls`), `fat12_cat(filename)` (команда `cat`)
и `fat12_load(filename, buffer, max_size)` (команда `run`, см. ниже).

Запись: `fat12_write(filename, data, size)` (команда `write`, см. ниже) —
создаёт файл (первая свободная/удалённая запись корневой директории) или
перезаписывает существующий (старая цепочка кластеров освобождается).
Кластеры под новые данные ищутся однопроходным сканированием FAT
(`fat12_alloc_chain`, без промежуточных массивов — важно при вызове из
syscall на 4 КБ стеке ring3-задачи) и линкуются на ходу; 12-битная запись
FAT-записей (`fat12_set_entry`) — та же арифметика read-modify-write, что
и `set_fat_entry` в `tools/make_fat12.py`. После успешной записи
`fat12_flush()` пишет всю RAM-копию обратно на `build/disk.img` через
`ide_write_sector` — изменения переживают перезапуск QEMU.

Если `build/disk.img` отсутствует или не содержит валидный FAT12-том,
`fat12_init()` возвращает 0, ядро печатает предупреждение и все команды
файловой системы (`ls`/`cat`/`write`/`run`) становятся no-op (флаг
`fat12_ready`).

**Защита от записи (`lock`/`unlock`)**: `fat12_set_locked()`/
`fat12_is_locked()` хранят флаг `fat12_locked` (по умолчанию 1 —
заблокировано). `fat12_write()` сразу возвращает 0, пока диск
заблокирован, — это касается и команды `write`, и `SYS_WRITE_FILE` из
ring3 (`sys_write_file`). Команда `unlock` снимает защиту, `lock`
восстанавливает её; текущее состояние видно в `about`. Чтение (`ls`,
`cat`, `run`) защитой не ограничено.

**Расширение FAT12 (128 КБ → 256 КБ → 1 МБ → 2 МБ).** Том изначально был
128 КБ (256 секторов); статические файлы из `fs/` (демо-программы,
`clip.bin` и т.п.) выросли настолько, что заняли 250 из 252 кластеров
данных — для runtime-файла `selftest.c` (`test_fat12`, ~1100 байт = 3
кластера) не осталось места, и регрессионный тест стал детерминированно
проваливаться. Объём подняли вдвое (512 секторов = 256 КБ), заодно
увеличив `SECTORS_PER_FAT` с 1 до 2. Позже объём подняли ещё в 4 раза —
до 1 МБ (2048 секторов, `SECTORS_PER_FAT=6`, `ROOT_ENTRIES` 32→64).

Последний раз объём удвоили ещё раз — до текущих 2 МБ (4096 секторов,
`SECTORS_PER_FAT=12`, 4079 кластеров данных) — когда сетевой стек на x86
(virtio-net/ARP/ICMP/UDP-тесты, см. выше) добавил несколько новых
программ по ~30КБ каждая: тома уже не хватало даже для СУЩЕСТВОВАВШИХ
файлов (`WXDEMO.BIN не помещается на FAT12-диск`), а не только для
новых. Этот конкретный шаг роста был не чисто механическим: `FAT12_BASE`
(`0x300000`) при удвоении до 2 МБ стал заканчиваться на `0x500000` —
дальше старой границы фиксированных первых 4 МБ (`PD[1]` в `paging.c`
покрывает только 2-4 МБ), внутрь диапазона, который раньше был НИЗШИМ
кандидатом случайной базы кучи (KASLR, см. "KASLR/ASLR" ниже).
Понадобилось: (1) зафиксировать ещё `PD[2]` (4-6 МБ) той же huge page,
что и `PD[1]` — и в `init_paging()`, и в `paging_create_user_directory()`
(иначе у ЛЮБОЙ изолированной задачи FAT12 читался бы только частично,
#PF на второй половине), (2) сдвинуть нижнюю границу кандидатов кучи в
`kheap_pick_pd_index()` с `PD[2]` на `PD[3]` (32 варианта → 31 — то, что
"lite"-рандомизация никогда не претендовала на точное число). Актуальные
константы должны двигаться синхронно при следующем расширении:
`TOTAL_SECTORS`/`SECTORS_PER_FAT`/`ROOT_ENTRIES` в `tools/make_fat12.py`,
`FAT12_TOTAL_SECTORS` в `src/fs/fat12.c` — и, если новый размер снова
пересечёт очередную границу фиксированной `PD[N]`, та же самая правка в
`paging.c` (закрепить `PD[N]`, сдвинуть floor кучи дальше).

**Известный класс багов в этой кодовой базе**: при одном из расширений
`FAT12_BASE` временно совпал с только что появившимся `USER_PROGRAM_BASE`
(оба были `0x200000`) - "тихое" пересечение физических адресов без единого
предупреждения при компиляции. Исправлено переносом `FAT12_BASE` на
`0x300000` (внутри той же supervisor-only части `PD[1]`, но после слотов
пользовательских программ `0x200000`-`0x23FFFF`). Тот же класс бага нашёлся
и был исправлен позже ещё раз, у `TTYS_BASE`/`ELF_STAGING_BASE` (см.
"Терминалы (TTY)" и "Карта памяти" ниже) - в кодовой базе нет ни
compile-time, ни runtime проверки на такие коллизии, только ручная сверка
при добавлении нового фиксированного физического адреса.

### Запуск пользовательских программ (run)

Команда `run <file>` грузит файл с FAT12-диска в один из `USER_PROGRAM_SLOTS`
(4) слотов по `USER_PROGRAM_SLOT_SIZE` (32 КБ) каждый, начиная с
`USER_PROGRAM_BASE` (`0x100000`, 1 МБ) — `vfs_read()` — и запускает его как
изолированную ring3-задачу `task_create_user_isolated(filename, addr,
slot_index)` (`tasking.c`).

Сами программы линкуются так же, как `kernel.bin`: исходники в `src/user/`
(`crt0.asm` — точка входа `_start`, `hello.c` — `main()`, `user.ld` —
линковка на `0x100000`, `syscall.h` — общий ABI syscall'ов), собираются и
стрипуются в `build/hello.bin` (`objcopy -O binary`) — но дальше, в отличие
от ядра, `tools/make_elf.py` оборачивает этот плоский бинарник в
минимальный настоящий ELF32 (`Ehdr` + один `Phdr` PT_LOAD) перед тем, как
он попадёт в `fs/HELLO.BIN`. Имя файла в FAT12 не меняется (`.BIN`), меняется
только содержимое.

#### ELF32-загрузчик (`src/kernel/elf.c`/`elf.h`)

Toolchain этого проекта (`w64devkit/bin/ld.exe`) умеет линковать только в
PE — emulation `elf_i386` в нём нет. Конвертация уже слинкованного PE
через `objcopy -O elf32-i386` тоже не подходит: формально результат
проходит (верный `e_entry`/magic/class/machine), но **`p_vaddr` в Program
Header выходит мусорным** (`0xffd00000` вместо `~0x100000`) — проверено
вручную побайтовым разбором заголовка, известный класс багов binutils BFD
при PE→ELF с нестандартным image base. Поэтому `tools/make_elf.py` пишет
ELF32-контейнер сам — `Elf32_Ehdr` (52 байта) + один `Elf32_Phdr` (32
байта, `PT_LOAD`, `p_vaddr=p_paddr=0x100000`, `p_filesz=p_memsz=`размер
бинарника) + сами байты бинарника, по аналогии с тем, как `make_fat12.py`
вручную собирает FAT12.

На стороне ядра `elf_load()` (`do_exec()` и ветка `"run "` в
`execute_command()`, `kernel.c`) читает файл целиком во временный буфер
(`vfs_read`/`fat12_load` не умеют читать "со смещения"), разбирает
`Ehdr`/`Phdr`, копирует каждый `PT_LOAD`-сегмент по его `p_vaddr` в
физическую память слота программы и зануляет `[p_filesz, p_memsz)`.
Проверяются magic/class/data/machine/type, разумный потолок `e_phnum`, и
что ни один сегмент (и точка входа) не выходит за пределы окна задачи и
не залезает в зону `argv` (`USER_ARGS_OFFSET`) — отдельный код ошибки на
каждую причину отказа, как и у `mkdir`/`write`/`rm` (см. "Безопасность
файловых операций" выше). Результат — slot, или `-1` (файл не найден),
`-2` (нет свободных слотов), `-3` (не валидный ELF); `sh.c` показывает
для каждого отдельное сообщение.

**ВАЖНО про размер временного буфера**: буфер для разбора ELF (`ELF_STAGING_SIZE
= USER_ARGS_OFFSET + 0x200`, ровно потолок легального размера программы) живёт
по фиксированному физическому адресу (`ELF_STAGING_BASE = 0x150000`, сразу
после пула приватных таблиц изолированных задач), а НЕ как статический массив
в `.bss` ядра. На практике
это поймали живьём: `.bss` ядра начинается сразу после `.data`
(`kernel.bin` грузится с `0x1000`), а GDT загрузочного сектора в тот
момент физически жила по `0x7c00`-`0x7e00`; 32 КБ статического буфера в
`.bss` утащили `__bss_end` далеко за `0x7c00`, и `rep stosb`,
обнуляющий `.bss` при старте, стирал GDT — `#GP` → `#DF` → Triple fault
прямо во время загрузки. Тот же класс бага, что когда-то уже ловили на
самом `.bss` ядра. При добавлении новых крупных статических буферов в
`kernel.c` — фиксированный физический адрес в свободной зоне (как
`PAGE_DIRECTORY`/`GLOBAL_PT0`/`PML4_POOL_BASE`..`PT_POOL_BASE`), не `.bss`.
(С тех пор `boot.asm` сам себя копирует на `0x0600` перед чтением ядра —
GDT там больше не живёт на `0x7c00`, см. "Загрузка" выше, но привычка
проверять `__bss_end` после новых буферов остаётся правильной.)

#### Изоляция памяти (приватные PML4/PDPT/PD/PT на процесс)

`task_create_user_isolated` строит для задачи приватные PML4/PDPT/PD/PT
(`paging_create_user_directory`, `paging.c`) — копию глобальных таблиц, но с
**`PAGE_USER` сброшенным везде** (ring3 этой задачи по умолчанию не видит ни
код/данные ядра, ни кучу, ни видеопамять, ни слоты других программ - любое
такое обращение вызовет page fault), кроме виртуального окна
`USER_WINDOW_BASE`-`USER_WINDOW_BASE+USER_WINDOW_SIZE` = `0x100000`-`0x110000`
(16 страниц), которое переотображается на физический слот
`USER_PROGRAM_BASE + slot_index * USER_PROGRAM_SLOT_SIZE` (`0x200000 +
slot*0x10000`) программы с флагами `PRESENT|RW|USER`. `RIP` и `RSP`
изолированной задачи — всегда виртуальные `0x100000`/`0x110000`: код,
данные и стек программы живут только в этом окне (64 КБ суммарно),
независимо от того, в каком физическом слоте она на самом деле загружена.
`schedule()` переключает CR3 на этот PML4 при возврате к задаче (см.
"Многозадачность" выше).

Приватные PML4/PDPT/PD/PT берутся из пула `PML4_POOL_BASE`/
`PDPT_POOL_BASE`/`PD_POOL_BASE`/`PT_POOL_BASE` (`paging.h`,
`0x140000`-`0x14FFFF` — по 4 КБ×4 на каждый из `USER_PROGRAM_SLOTS`); эти
приватные таблицы дополнительно копируют записи кучи ядра
(`GLOBAL_PD[2..2+KHEAP_PAGES-1]`) из общей `GLOBAL_PD` — без этого код ядра
(обработчики прерываний/syscalls), выполняющийся под чужим CR3, падал бы с
`#PF` при любом обращении к куче.

Побочный эффект: раньше все 4 слота были видны программе по их настоящим
физическим адресам, а `user.ld` линкует программы на фиксированный
`0x100000` — поэтому абсолютные ссылки на данные (строки и т.п.) в
программе, загруженной в слот 1-3, указывали на `0x100000+offset`
(т.е. в слот 0), и "работали" только потому, что во всех слотах лежала
идентичная копия `hello.bin`. Переотображение окна исправляет это: теперь
такие ссылки всегда корректно резолвятся в "свой" слот.

`task0` (shell), `heartbeat` и `ring3demo` (встроенные ring0/ring3
демо-задачи, код которых — часть `kernel.bin`, пишут прямо в видеопамять)
продолжают использовать общий `PAGE_DIRECTORY` без изоляции — изоляция
применяется только к `run`-задачам.

**Завершение при ошибке**: page fault в ring3 у изолированной `run`-задачи
больше не останавливает всю систему — убивается только эта задача (см.
"Жизненный цикл задач" выше). Page fault в ring0 (баг ядра) или у
встроенных демо-задач без изоляции (`ring3demo`/`usermode`) — по-прежнему
останавливает ОС: такой fault обычно сигнализирует баг ядра и должен быть
заметен.

`HELLO.BIN` демонстрирует все ring3-syscall'ы: печатает приветствие,
записывает файл `RING3.TXT` через `SYS_WRITE_FILE`, читает его обратно
через `SYS_READ_FILE` и печатает прочитанное (доказывая, что запись и
чтение через FAT12 из ring3 работают), затем в цикле опрашивает
клавиатуру через `SYS_READ_KEY` (неблокирующе) и эхо-печатает нажатые
символы — независимо от обычного ввода shell. Диск по умолчанию
заблокирован от записи (см. ниже) — выполните `unlock` перед `run
HELLO.BIN`, иначе `SYS_WRITE_FILE` ничего не запишет и `SYS_READ_FILE`
вернёт пустую строку.

Каждый `run` занимает следующий слот по кругу — несколько программ могут
работать одновременно (видно в `ps`). После полного круга слот
переиспользуется: `run` перезапишет программу, которая занимала этот слот
раньше, если она ещё работает. Для учебной ОС без отдельных адресных
пространств на задачу это ожидаемо.

### Драйвер IDE/ATA (PIO)

`src/drivers/ide.c`/`ide.h` — PIO-драйвер ATA для primary bus, master-диска,
LBA28-адресация. Без DMA и прерываний: чтение и запись секторов через порты
`0x1F0`-`0x1F7` с поллингом регистра статуса (`ide_wait_ready`/`ide_wait_data`,
ограничены `IDE_WAIT_LIMIT` итерациями, чтобы не зависнуть, если IDE-устройство
не подключено — `status == 0xFF`).

- `ide_read_sector(lba, buffer)` / `ide_write_sector(lba, buffer)` — команды
  `READ SECTORS` (`0x20`) / `WRITE SECTORS` (`0x30`), 256 слов (512 байт) за
  раз; после записи — `CACHE FLUSH` (`0xE7`).
- `ide_identify(model)` — команда `IDENTIFY DEVICE` (`0xEC`), возвращает строку
  модели диска (слова 27-46 ответа).

Это настоящий физический диск — `build/disk.img` (10 МБ, создаётся при
сборке и подключается к QEMU как `if=ide`). Диск разделён на две области:

- **LBA 0-511** (первые 256 КБ) — FAT12-том, который `fat12_init()`/
  `fat12_flush()` грузят и сохраняют целиком (см. раздел про FAT12 выше).
  Не трогайте эту область через `diskread`/`diskwrite` — `write`/`run`
  работают с ней через FAT12-драйвер.
- **LBA ≥512** — свободное место для демонстрации `diskread <lba>`/
  `diskwrite <lba> <text>` напрямую через IDE, без FAT12.

Команды shell: `diskinfo`, `diskread <lba>`, `diskwrite <lba> <text>` (см.
таблицу команд ниже; для демо используйте `lba >= 512`). Записи через
`diskwrite` сохраняются между запусками QEMU. VFS-слой над несколькими
файловыми системами — следующий шаг (см. Roadmap).

## Карта памяти (x86-64)

Все адреса — физические:

| `0x8C000`          | 4 КБ       | Guard page стека ядра (не отображена — переполнение стека триггерит `#PF`, а не тихую порчу памяти) |

| `0x9D000`          | 4 КБ       | `GLOBAL_PDPT`                                   |
| `0x9E000`          | 4 КБ       | `GLOBAL_PD` — `[0]`→PT0, `[1]`/`[2]`=2МБ huge pages (2-6МБ), `[g_kheap_pd_index..+15]`=куча, `[g_pool_pd_index]`=пул (оба KASLR, см. "KASLR/ASLR" ниже) |
| `0x9F000`          | 4 КБ       | `GLOBAL_PT0` (4КБ-страницы, VA `0x0`-`0x1FFFFF`) |

| `0x100000`–`0x110000`| 16×4КБ = 64КБ | `USER_WINDOW` — виртуальное окно ring3 изолированной задачи (одинаково для всех, переотображается на реальный слот) |
| `0x140000`–`0x17FFFF`| — (свободно) | Раньше здесь был пул PML4/PDPT/PD/PT изолированных задач (`PML4_POOL_BASE`..`PT_POOL_BASE`) — с переходом на KASLR переехал на случайный PD-слот (см. ниже), это место сейчас не используется |
| `0x180000`–`0x19FFFF`| 128 КБ (`DMA_POOL_SIZE`) | `dma_pool.c` — фиксированный identity-mapped bump-аллокатор физической памяти для драйверов (virtqueue и т.п.). Появился, когда куча перестала годиться для этого без риска (см. "KASLR/ASLR" ниже) — `virtio_net.c` теперь берёт память отсюда, а не из `malloc()` |
| `0x150000`–`0x15FA00`| ~62,5 КБ (`ELF_STAGING_SIZE`) | Буфер разбора ELF-файла программы перед загрузкой (`ELF_STAGING_BASE`, `kernel.c`) — фиксированный адрес, не `.bss` (см. "ELF32-загрузчик") |
| `0x160000`+        | ~7,9 КБ (`sizeof(tty_state)*2`) | `TTYS_BASE` (`screen.c`) — буферы двух виртуальных консолей (см. "Терминалы (TTY)"). **Раньше был на `0x158000`, внутри `ELF_STAGING` — реальный баг, найденный и исправленный** (см. врезку там же) |
| `0x200000`–`0x240000`| 4×64КБ (`USER_PROGRAM_SLOT_SIZE`) | `USER_PROGRAM_BASE` — физические слоты копий ELF-сегментов ring3-программ (supervisor huge page `PD[1]`, запись без SMAP/`stac`) |
| `0x300000`–`0x500000`| 2 МБ (`FAT12_TOTAL_SECTORS=4096`×512Б) | `FAT12_BASE` — RAM-копия FAT12-тома (`fat12_init`/`fat12_flush` через IDE с `build/disk.img`). **Раньше был на `0x200000` — совпадал с `USER_PROGRAM_BASE`, тоже реальный баг** (см. | `0x6000000`–`0x8000000` (диапазон) | 2 МБ (используется 64 КБ) | `g_pool_base` — пул PML4/PDPT/PD/PT изолированных `run`-задач. **KASLR**: случайный PD-слот `[48,64)`, специально не пересекается с диапазоном кучи |

**Компиляторских/рантайм проверок на пересечение этих регионов НЕТ** — только
ручная сверка при добавлении нового. За время разработки это уже дважды
приводило к реальным багам с тихой порчей памяти (`FAT12_BASE`/
`USER_PROGRAM_BASE`, затем `TTYS_BASE`/`ELF_STAGING_BASE`) — при добавлении
следующего фиксированного физического адреса стоит явно сверяться с этой
таблицей.

## KASLR/ASLR

Рандомизация адресов есть на обеих платформах, но устроена по-разному —
и историю о том, ПОЧЕМУ она устроена именно так (а не шире, чем могла
бы), стоит прочитать перед тем, как трогать этот код: одна попытка
расширить её на x86 закончилась реальным, живым double fault, найденным
и откаченным в этой же сессии.

### x86: куча/пул ядра

`src/kernel/paging.c` рандомизирует, на каком PD-слоте начинается куча
ядра (`g_kheap_base`, 32МБ, 16 huge pages подряд, диапазон стартов
`[3,48)` — 45 вариантов) и пул PML4/PDPT/PD/PT изолированных задач
(`g_pool_base`, диапазон `[48,64)`, специально не пересекается с кучей).
Сид - `early_random64()`: RDRAND (`CPUID.1:ECX[30]`), если процессор
поддерживает, иначе RDTSC (тот же фоллбэк, что и раньше, - `init_paging()`
исполняется до `init_idt()`, тикового счётчика ещё нет).

**Попытка №1 (откачена): полная развязка VA/PA.** Изначально куча/пул
переезжали за ОТДЕЛЬНЫЕ, независимые от первого фиксированного гигабайта
цепочки `PML4→PDPT→PD` со случайным индексом на каждом уровне -
виртуальный адрес мог оказаться где угодно в первых ~64ТБ, физическая
память при этом оставалась фиксированной (`KHEAP_PHYS_BASE`/
`POOL_PHYS_BASE`) - тот же принцип, что и у настоящих ядер (секрет - в
том, ЧЕРЕЗ КАКОЙ виртуальный адрес можно достучаться до памяти, а не в
том, где она физически лежит). Это требовало сперва перевести
`virtio_net.c` с `malloc()`-указателя как физического адреса на
отдельный identity-mapped `dma_pool.c` (см. "Драйвер virtio-net" выше) -
куча identity-mapped быть перестала бы, драйвер сломался бы иначе.

При первой же живой проверке — реальный double fault в `schedule()`
при переключении задач: `mov (%rax),%rax`, где `%rax` = `current_task`
(структура процесса, сама живущая на куче) - точная причина не
локализована за разумное время, несмотря на нормальную живую отладку
(bisection через screendump, QEMU `-d int` трассировку прерываний,
дизассемблирование конкретного адреса падения). Отдельно выяснилось,
что даже если бы причину нашли: при обязательной identity-mapping
(`VA==PA`) и физическом потолке в 128МБ RAM (умолчание QEMU) реальная
энтропия ВСЁ РАВНО была бы зажата на ~6 битах, сколько бы уровней таблиц
ни заводить - для куда большей энтропии нужна была именно развязка
VA/PA (риск которой и не окупился), либо увеличение реальной RAM
(отдельное решение, не сделано).

**Что реально осталось (безопасная версия):** identity-mapping
сохранён как есть (`VA==PA`, риска double fault такого рода нет), но
диапазон кандидатов расширен почти на весь доступный объём (было
`[3,34)`/`[50,64)`, стало `[3,48)`/`[48,64)` - на 14 больше стартов у
кучи), плюс RDRAND вместо чистого RDTSC для сида. `dma_pool.c` при этом
остался - лучшая архитектура сама по себе (драйвер больше не привязан к
тому, identity-mapped куча или нет), не требует отдельного отката.

### x86: код/стек/куча пользовательских программ

Отдельная, более старая система - `src/kernel/elf.c`/`tasking.c`:
- **Code ASLR** (только если ELF несёт `PT_AXOS_RELOC`, см. "ELF32-
  загрузчик" ниже): случайный постраничный (4096Б, НЕ 16Б - гранулярность
  обязана быть страничной, иначе сдвинется невыровненно граница W^X)
  сдвиг кода внутри слота. Комментарий в коде раньше завышал энтропию
  (~11 бит) - реальная оценка (~2-4 бита для типичной программы) найдена
  и исправлена при аудите этой темы, поведение кода не менялось.
- **Stack ASLR** (`tasking.c`): случайный сдвиг начала стека, до 1024Б
  шагом 16Б (~6 бит).
- **Heap-slide** (`kernel.c`): случайный сдвиг точки старта кучи
  программы, до 4032Б шагом 64Б (~6 бит).

Сид всех трёх - `aslr_next_random()` (xorshift32, реseed'ится из
`timer_ticks` при каждом вызове) - осознанно некриптографический, той
же природы, что и `early_random64()` выше, просто других источник (тут
уже есть тиковый счётчик, `init_idt()` к этому моменту давно отработал).

### RISC-V: куча ядра

`src/arch/riscv64/kernel_main.c` - до этой сессии randomization не было
вообще никакой (в отличие от x86, где "KASLR-lite" существовала уже
давно). Учитывая, к чему привела попытка развязать VA/PA на x86-стороне
(см. выше), тут сразу выбран заведомо безопасный путь: `pmem_init()`
(бамп-аллокатор физических страниц, `pmem.c`) получает не голый
`_kernel_end`, а `_kernel_end` плюс случайный сдвиг на 0-2047 страниц
(0-8МБ, шаг 4КБ, ~11 бит энтропии) - куча (первый и самый частый
потребитель `alloc_page()`, см. `heap.c`) стартует с ПЕРВОЙ страницы,
которую вернёт `pmem`, так что этот сдвиг и определяет её адрес на
конкретной загрузке. Ни одна таблица страниц не трогается - всё та же
единственная, всегда identity-mapped 1ГБ-gigapage (`map_gigapage` в
`paging.c`), просто другой стартовый оффсет внутри неё. Сид - тот же
CSR `time`, что `heap.c` уже использует для MTE-тегов.

### RISC-V: стек и куча пользовательских программ

Тоже не было вообще никакой ASLR до этой сессии (в отличие от x86, где
хотя бы код/стек/куча пользовательских программ уже имели свою, пусть и
скромную, рандомизацию) - при этом RISC-V userspace честно 64-битный
(в отличие от 32-битного x86 userspace), так что это оказалось
единственным местом во всей этой работе, где реально можно было
получить широкую (не зажатую 128МБ RAM) энтропию без всякого риска -
в отличие от куч ядра (x86 и RISC-V), стек и точка старта кучи
пользовательской программы - это адреса, которые ЯДРУ никогда не нужно
разыменовывать как свои собственные указатели при переключении
контекста (в отличие от `current_task`, который и стал источником
double fault на x86-стороне) - никакого риска той же природы тут нет.

`src/arch/riscv64/elf_loader.c`, `pick_stack_va()`: случайная 4КБ-
выровненная страница стека внутри `[USER_HEAP_CEILING, USER_VA_TOP)` =
`[0x7E000000, 0x80000000)` - весь этот зазор раньше был зарезервирован,
но не использовался (стек всегда сидел на фиксированном
`0x7F000000`). ~13 бит энтропии - на порядок больше, чем что-либо на
x86-стороне. Реальный адрес хранится в новом поле `proc_t.stack_va`, не
в константе - константа `USER_STACK_VA` убрана целиком, ничего на неё
больше не ссылается. `heap_brk` тоже получил небольшой случайный сдвиг
(до 64 страниц = 256КБ), та же идея, что у x86 heap-slide.

`SYS_SBRK` (`syscall.c`) сверяется с фиксированным потолком
(`USER_HEAP_CEILING`), не с фактическим `stack_va` конкретного процесса
- весь диапазон `[USER_HEAP_CEILING, USER_VA_TOP)` зарезервирован под
возможные позиции стека независимо от того, куда он реально уехал в
этот раз, так что сверяться с константой одновременно проще и
безопаснее.

**Явно не сделано**: рандомизация адреса ЗАГРУЗКИ САМОГО КОДА
пользовательской программы (аналог x86-шного `PT_AXOS_RELOC`) -
потребовала бы механизма релокаций в ELF64/RISC-V тулчейне (новый шаг
сборки, аналог `make_elf.py`), отдельная задача, не сделана.

## Команды shell

На x86 фактически два shell'а:

- **AxSH** (`src/user/sh.c`, `SH.BIN`) — обычный ring3-процесс, автоматически
  запускается на автобут (`execute_command("run SH.BIN")` в
  `kernel_main()`) и есть то, с чем реально работает пользователь. Более
  Unix-подобный: большинство "команд" (`ls`, `cat`, `grep`, ...) — не
  встроенные, а ОБЫЧНЫЕ внешние программы, запускаемые через `exec()`;
  поддерживает конвейеры (`cmd1 | cmd2`, один уровень), редирект
  (`cmd > file`) и фоновые задачи (`cmd &`). Встроено прямо в шелл только
  то, что должно менять состояние самого шелла или быть предельно быстрым:

  | Команда | Описание |
  |---|---|
  | `<program> [args]` | запустить программу (`ls`, `cat`, `grep`, ...) |
  | `cmd1 \| cmd2` | конвейер (вывод `cmd1` → вход `cmd2`, один уровень) |
  | `cmd > file` | перенаправить вывод в файл |
  | `cmd &` | запустить в фоне |
  | `cd <dir>` / `cd /` / `cd ..` | сменить каталог |
  | `pwd` | текущий каталог |
  | `clear` | очистить экран |
  | `lock` / `unlock` | за-/разблокировать диск для записи |
  | `paste` | напечатать буфер обмена (алиас `clip get`) |
  | `nice <pid> <1-10>` | задать приоритет планировщика задаче (см. "Многозадачность") |
  | `help` | список встроенных команд |
  | `exit` | выйти из AxSH |

- **Встроенный shell ядра** (`execute_command()`, `src/kernel/kernel.c`,
  приглашение `AxOS> `) — более старый, самодостаточный набор команд прямо
  в ring0; используется только как fallback, если `SH.BIN` не найден на
  диске (нормальный автобут его никогда не показывает). Набор команд шире
  диагностическими и низкоуровневыми файловыми операциями:

  | Команда         | Описание                                                  |
  |-----------------|------------------------------------------------------------|
  | `help`          | список команд                                              |
  | `clear`         | очистить экран                                             |
  | `about`         | информация об ОС (версия, статус блокировки FAT12-диска)   |
  | `date` / `time` | текущая дата и время (CMOS RTC)                            |
  | `uptime`        | время с момента загрузки (тики PIT, 100 Гц)                |
  | `sleep <0-9>`   | пауза на N секунд                                          |
  | `reboot`        | программная перезагрузка                                   |
  | `echo <text>`   | вывод текста                                               |
  | `ls`            | список файлов на FAT12 RAM-диске                           |
  | `cat <file>`    | содержимое файла                                           |
  | `write <file> <text>` | создать/перезаписать файл на FAT12 RAM-диске (нужен `unlock`) |
  | `lock`          | защитить FAT12 RAM-диск от записи (по умолчанию)           |
  | `unlock`        | разрешить запись на FAT12 RAM-диск                          |
  | `run <file>`    | загрузить и запустить программу с FAT12 (ring3); `No free program slots, try again later.`, если все 4 слота заняты живыми задачами |
  | `usermode`      | демо: переход в ring3 и вызов `int 0x80` из user mode      |
  | `memtest`       | тест кучи (`malloc`/`free`): выделение, переиспользование, слияние блоков |
  | `selftest`      | регрессионные тесты heap/paging/FAT12, печатает `SELFTEST: ALL PASS`/`FAILED` |
  | `ps`            | список задач планировщика (id, имя, тики, приоритет)       |
  | `diskinfo`      | модель диска IDE (`build/disk.img`), команда `IDENTIFY DEVICE` |
  | `diskread <lba>`| hexdump сектора с диска IDE (первые 128 из 512 байт)       |
  | `diskwrite <lba> <text>` | записать текст в сектор диска IDE                  |

Команды RISC-V-порта (AxSH/RV64, свой независимый шелл) — см. раздел
"RISC-V порт" ниже.

## Буфер обмена (`clip`/`paste`)

`SYS_CLIPBOARD_SET`/`SYS_CLIPBOARD_GET` (`0x1F`/`0x20`, `kernel.c`) — один
общий буфер обмена в ядре (до `CLIPBOARD_MAX_SIZE` = 1 КБ - исторически
ограничен из-за близости `.bss` ядра к загрузочному сектору 0x7c00, где
раньше жила GDT, см. `kernel_entry.asm`; после самоперемещения `boot.asm`
на `0x0600` это конкретное ограничение уже не актуально само по себе, но
лимит не пересматривался), переживающий завершение задач. Доступен из AxSH
(`sh.bin`, см. "Запуск пользовательских программ"):

| Команда                | Описание                                              |
|------------------------|--------------------------------------------------------|
| `clip set <text>`      | записать текст в буфер обмена (`fs/CLIP.BIN`)          |
| `clip get`             | вывести содержимое буфера обмена (`fs/CLIP.BIN`)       |
| `clip clear`           | очистить буфер обмена (`fs/CLIP.BIN`)                  |
| `clip level <N> set <text>` | поднять себе MLS-уровень до `sN` (0-15) и сразу записать на нём — см. "MLS" ниже |
| `clip level <N> get`   | поднять себе MLS-уровень до `sN` и сразу попытаться прочитать |
| `clip level <N> idle <ms>` | поднять себе MLS-уровень до `sN` и поспать `ms` мс — демо для `ps`/`task_info` (см. "MLS" ниже) |
| `paste`                | алиас `clip get`, встроен прямо в `sh.c` — отдельный `.bin` для однострочного алиаса не оправдывает свои ~4.6 КБ накладных расходов на crt0/libaxiom (см. "Расширение FAT12" ниже) |

## MAC: Type Enforcement в духе SELinux (`kernel.c`)

Настоящий SELinux — Linux Security Module: хуки на inode/dentry/socket/
capability внутри Linux-ядра, security-контексты, политику грузит userspace.
Ничего из этого в AxOS нет и не может быть буквально — это не Linux и не
AOSP. Реализован тот же ПРИНЦИП (Type Enforcement: субъект в домене, объект
в классе, политика "домен × класс → разрешено/запрещено", default-deny),
нативно для собственных ресурсов ядра — без претензии на совместимость с
настоящим SELinux.

- **Домены** (`ax_domain_t`) — как security context процесса: изолированные
  `run`-задачи (`task_current_is_isolated()`, т.е. вообще все программы,
  загруженные через `run`/AxSH) — confined `user_t`; ядро и неизолированные
  демо-задачи (`heartbeat`/`ring3demo`) — unconfined `kernel_t`.
- **Классы** (`ax_class_t`) — по одному на syscall, который решили confine, в
  `kernel.c`:

  | Класс           | Syscall(ы)                                              | Политика для `user_t` |
  |-----------------|----------------------------------------------------------|------------------------|
  | `disk_raw`      | `SYS_DISK_READ_SECTOR`/`WRITE_SECTOR`/`SYS_DISK_IDENTIFY` (минуя FAT12) | deny |
  | `system_reboot` | `SYS_REBOOT`                                              | deny |
  | `file_write`    | `SYS_WRITE_FILE`, `SYS_OPEN` (флаг ≠ `O_RDONLY`), `SYS_MKDIR` | allow |
  | `file_unlink`   | `SYS_UNLINK`                                              | allow |
  | `fs_lock`       | `SYS_FS_LOCK` (`lock`/`unlock`)                           | allow |
  | `exec`          | `SYS_EXEC`/`SYS_EXEC_REDIR`                               | allow |
  | `clipboard`     | `SYS_CLIPBOARD_SET`                                       | allow (но см. MLS ниже) |
  | `task_info`     | `SYS_PS` (имена/`heap_brk` ДРУГИХ задач — info-disclosure поверхность) | allow |
  | `pci_raw`       | `SYS_PCI_GET_DEVICE` (порты `0xCF8`/`0xCFC`, минуя любую абстракцию ядра) | deny |

  Запрещены только `disk_raw`/`system_reboot`/`pci_raw` (прямой доступ к
  железу мимо абстракций ядра — одна и та же категория риска во всех
  трёх) — остальные пять allow-правил (как и большинство правил в
  настоящей политике SELinux): запрещать
  повседневные операции AxSH и демо-программ (`write.bin`/`rm.bin`/`mkdir.bin`/
  `lock`/`unlock`) без причины означало бы ломать рекламируемую
  функциональность. Ценность — единообразная, проверяемая граница для
  каждой операции, которую можно сузить позже без правок в самих `sys_*`.
- При отказе `ax_mac_check()` печатает audit-подобную строку (формат — привет
  от настоящего `avc: denied` в `dmesg`/`auditd`) и возвращает 0; syscall
  отказывает вызывающему как при любой другой ошибке (`result=0`) — с точки
  зрения вызывающего denied неотличим от обычного отказа, как и в реальном
  SELinux.

```
avc:  denied  { disk_raw }  for comm="disktool.bin"  scontext=axos:user_t  tclass=disk_raw
```

Добавление новой confined-операции — это новый класс в `ax_class_t` + строка
в `ax_policy` + вызов `ax_mac_check(...)` в начале нужного `sys_*`.

### MLS: уровни чувствительности (`SYS_SET_LEVEL`, буфер обмена)

Полный security context в SELinux — `user:role:type:level`, где `level`
(MLS/MCS) — отдельная "шкала" чувствительности (`s0`..`s15`, опционально с
категориями `c0`..`c1023`), проверяемая ПОВЕРХ Type Enforcement через
доминирование (Bell-LaPadula: субъект должен доминировать над объектом,
чтобы его прочитать — "no read up"). Добавлена аналогичная шкала для одного
конкретного ресурса — буфера обмена:

- `SYS_SET_LEVEL` (`0x21`) — задача поднимает СЕБЕ MLS-уровень (`s0`..`s15`,
  `task_set_current_mls_level()`, `tasking.c`). Самодекларация без проверки
  полномочий: в AxOS нет ни аутентификации, ни ролей, которые могли бы её
  ограничить (в отличие от настоящего SELinux MLS, где переход уровня сам
  подчинён политике) — честно задокументированное упрощение, как и 4-битный
  tag кучи (см. "Куча" выше).
- Каждый успешный `SYS_CLIPBOARD_SET` "окрашивает" буфер уровнем ПИСАТЕЛЯ
  (`clipboard_level`, `kernel.c`). `SYS_CLIPBOARD_GET` отказывает
  (`out_size=0` + `avc: denied { read } ... (MLS: no read up)`), если уровень
  читателя ниже уровня, на котором буфер был заполнен последний раз.
- Поднятый уровень живёт только до конца ЭТОГО процесса (как и контекст
  процесса в SELinux — не переживает следующий `exec`). Поэтому `clip.bin`
  совмещает подъём уровня и операцию в одном запуске:

  ```
  $ run CLIP.BIN level 5 set top secret    # пишет на s5
  $ run CLIP.BIN get                       # читатель на s0 (по умолчанию) - denied
  $ run CLIP.BIN level 5 get                # читатель s5 >= s5 - "top secret"
  ```

**Вторая защищённая поверхность: `ps` (класс `task_info`).** Каждая задача
несёт собственный MLS-уровень (`task_t.mls_level`, по умолчанию `s0`).
`SYS_PS` отдаёт ту же dominance-проверку (`ax_mls_dominates(level, "task")`)
по каждой записи: задачу с уровнем выше уровня наблюдателя видно (запись не
пропадает из списка — иначе цикл `ps.bin` прервался бы раньше времени), но
её `NAME`/`TICKS`/`heap_brk` заменены на `<hidden>`/`0`/`0x0` — наблюдатель
не узнаёт о ней ничего, кроме самого факта существования (тот же принцип,
что у `hidepid` в Linux/Android).

Поскольку свежий `ps` всегда стартует на `s0`, продемонстрировать редакцию
нужно ДВУМЯ процессами: один поднимает себе уровень и остаётся живым
(`clip.bin level N idle <ms>`, в фоне через `&`), второй (`ps`) смотрит на
него со стороны:

```
$ CLIP.BIN level 5 idle 9000 &
[1] bg
$ ps
   5  <hidden>             0  user:1  heap=0x0
avc:  denied  { read }  for comm="ps.bin"  scontext=axos:user_t:s0  tcontext=axos:object_r:task:s5  (MLS: no read up)
```

## Цвет в AxSH (`screen.c`, ANSI SGR)

`screen.c` уже умел разбирать ANSI escape-последовательности (`\033[...m`
для цвета, `\033[2J`/`\033[r;cH` для очистки/позиционирования курсора) —
просто никто их не использовал. Подсветка добавлена туда, где она помогает
сразу видеть результат, без декоративных красивостей:

- зелёный (`\033[32m`) — приглашение AxSH (`$`/`[dir]$`), успешные
  операции (`disk: unlocked`, `clip: set N bytes`, `-> file` после
  редиректа);
- циан (`\033[36m`) — баннер `AxSH v0.1`, `Goodbye.`;
- жёлтый (`\033[33m`) — фон-задачи (`[N] bg`), kill изолированной задачи
  при page fault (предупреждение, не фатально — система продолжает работать);
- красный (`\033[31m`) — `sh: not found`/`no free slots`/`cd: not found`,
  `avc: denied` (MAC/MLS, `kernel.c`), `*** HEAP CORRUPTION ***`/
  `*** PAGE FAULT ... System halted.` (фатальные остановки системы).

## AI-демо: нейросеть учит булеву функцию (`ai.bin`, `src/user/ai.c`)

![ai 01101001: прогресс-бар обучения и таблица предсказаний для parity/XOR3](docs/screenshots/ai-3input-parity.png)

*`ai 01101001` (parity/XOR трёх входов, дефолт без аргументов): прогресс-бар
обучения (красный → жёлтый → зелёный по мере убывания ошибки) и финальная
таблица предсказаний с колонками A/B/C.*

![ai 00010111: majority сходится почти сразу - линейно разделима](docs/screenshots/ai-3input-majority.png)

*`ai 00010111` (majority — выход 1, если хотя бы 2 из 3 входов единицы) —
сходится заметно быстрее parity, т.к. линейно разделима.*

`ai` (запускается прямо из AxSH или `run AI.BIN` из kernel-shell) — живое
обучение крошечного многослойного перцептрона (3 входа → 6 скрытых
нейронов → 1 выход, обучение обратным распространением ошибки) предсказывать
любую из 256 булевых функций трёх аргументов. Таблица истинности (8 бит —
выходы для входов 000,001,010,011,100,101,110,111) задаётся либо аргументом
командной строки (`ai 01101001` — parity/XOR3, `ai 00000001` — AND,
`ai 00010111` — majority, и т.д.; невалидный аргумент — 8 символов `0`/`1`
обязательны — печатает предупреждение и откатывается на parity), либо
интерактивно: без аргументов `ai` запрашивает 8-битную строку через
`ax_readline` (Enter без ввода — тоже parity). Перед обучением печатает
распознанное имя функции — но, в отличие от версии на 2 входа (16 функций,
исчерпывающая таблица `KNOWN_FNS`), у 3 входов 256 функций, и именами
покрыты только несколько "известных" (AND/OR/NAND/NOR/XOR-parity/XNOR/
MAJORITY/FALSE/TRUE) — остальные lookup помечает как `custom (no common
name)`. Parity и XNOR — самые сложные из известных: не линейно разделимы
(обобщение контрпримера Минского/Паперта 1969 года на 3 входа), отсюда и
скрытый слой.

**Веса переживают выход из программы**: после успешного обучения сеть
сохраняет веса на FAT12 в `AI.WTS` — следующий запуск `ai` с тем же
8-битным паттерном находит совпадение, грузит готовые веса и сразу
показывает таблицу предсказаний, без повторного обучения и без
прогресс-бара (баннер показывает `Loaded:` вместо `Training:`). Файл —
не одни веса под одну функцию, а "банк" из `BANK_SIZE`=8 слотов
(`weights_bank_t`/`save_weights()`/`load_weights()`): можно обучить
parity, потом majority, потом AND — каждая своя, без переобучения при
переключении между уже выученными паттернами (`ai list` показывает,
что сейчас в банке — паттерн и распознанное имя для каждого занятого
слота). Когда банк полон и совпадения нет, новый паттерн вытесняет
слот по кругу (`next_slot`, простой FIFO, без учёта реального времени
последнего использования). Запись требует разблокированного диска
(команда `unlock` в AxSH — FAT12 заблокирован на запись по умолчанию,
`fat12_locked=1`, см. "Файловая система" выше); если диск заблокирован,
`ai` просто предупреждает и работает как раньше — чтение `AI.WTS` не
требует `unlock`. Несошедшуюся модель (`all_ok=0`) не сохраняет.

**Никакого `float`/`double`**: в этом freestanding-окружении FPU не
инициализирован (нет `fninit`, `CR0.EM` не сброшен) и вектор `#NM` (7) не
обработан в `init_idt()` (`kernel.c`) — любая x87-инструкция тут же
положила бы систему тройным сбоем (проверено явно: float не используется
вообще ни в одном файле проекта). Вся арифметика — fixed-point Q16.16
(`fx_mul()` — `((long long)a*b) >> 16`, без `libgcc`-хелперов: 32×32→64 —
один аппаратный `imul`, проверено линковкой). Сигмоида — через таблицу из
512 точек на домене `[-8, 8)`, посчитанную заранее в Python и
вкомпилированную как `static const int[]` — без `exp()` в рантайме.

Веса инициализируются своим xorshift32 (как ASLR-генератор в `tasking.c`,
но отдельная userspace-копия), сидится `ax_get_ticks()` — на каждом запуске
свои случайные веса. На 2 входа было достаточно 4 скрытых нейронов и 5000
эпох (проверено на 200 случайных сидах в Python-прототипе: 200/200
сходится); на 3 входа сложность задачи выше (256 функций вместо 16,
parity/XNOR требуют различать более тонкие комбинации входов) — подняли до
6 нейронов и 8000 эпох. Системной статистики по сходимости на множестве
сидов для 3-входовой версии нет (в отличие от 2-входовой) — проверено
вручную в QEMU на parity и majority, оба раза сошлось с первой попытки.

**UI**: баннеры (`print_boxed()`) рисуются рамкой из CP437 box-drawing
символов (`\xDA`/`\xC4`/`\xBF`/...) — аппаратный VGA-текстовый шрифт
всегда содержит CP437 независимо от настроек ОС, так что это не мусор,
а реальные линии. Каждые 800 эпох (8000 всего) печатается живой
прогресс-бар (`print_progress_bar()`, блоки `\xDB`/`\xB0`), цвет полосы
меняется по величине ошибки — красный (`err > 1.0`), жёлтый
(`0.2-1.0`), зелёный (`< 0.2`). Финальные предсказания — таблица с
рамкой (те же box-drawing символы, `PRED_TABLE_WIDTHS`, 7 колонок —
`PRED_TABLE_COLS`) с колонками A/B/C/predicted/target/status/conf,
`OK`/`FAIL` подсвечены зелёным/красным; выравнивание ячеек — через свой
`print_padded()` (ширина берётся из переменной, а не из литерала
формата, как требует `%-Ns` у `ax_printf`). Цвет в ячейках `status`/
`conf` не портит выравнивание: ANSI-escape'ы печатаются отдельными
вызовами вокруг `print_padded()`, а не внутри её аргумента, так что в
видимую ширину поля не попадают. Таблица обучения (8 строк, ~34 строки
вывода вместе с прогресс-баром) длиннее 25-строчного VGA-экрана —
баннер с именем функции успевает уехать за экран до конца обучения,
это нормально, не баг.

**`conf` (confidence)** — не то же самое, что `status`: `OK`/`FAIL`
сравнивает предсказание с target (правильность), а `conf` смотрит
только на то, насколько уверенно сеть выдала именно ЭТОТ выход,
независимо от того, угадала она или нет (`confidence_pct()` —
`|output - 0.5| * 2`, в процентах: 0% на самой границе принятия
решения — output ровно 0.5, сеть не определилась, в какую сторону —
100% на выходах, прижатых сигмоидой к самим 0 или 1). Подсветка:
зелёный (`≥80%`), жёлтый (`50-79%`), красный (`<50%`).

### `ai ask` — Q&A-режим про сам AxOS

![ai ask: баннер и ответ на "what is axos"](docs/screenshots/ai-ask.png)

Отдельный режим, не имеющий отношения к MLP выше: `ai ask` запускает REPL
(жёлтый `? ` — приглашение, `exit`/`quit` — выход), где пользователь
печатает вопрос на английском (клавиатурный драйвер — только ASCII/US-layout,
см. `scancode_to_char[]` в `kernel.c`), а `ai.bin` ищет ответ сначала в
жёстко заданной базе `QA_DB` (вопрос → до 3 ключевых фраз → ответ), затем
в выученных на лету записях (см. ниже) — всё простым поиском подстроки
(`contains()`, регистронезависимо через `lower_copy()`) — никакого
обучения нейросети тут нет, это обычный lookup. Первое совпадение по
порядку записей в `QA_DB` побеждает. Ответ выводится с зелёным префиксом
`AI:`, баннер — в той же рамке `print_boxed()`, что и у тренировочного
режима.

**Учится новым ответам**: если совпадение не нашлось ни в `QA_DB`, ни в
уже выученных записях, `ai ask` печатает дефолтный ответ со списком тем
(axos, xor, fpu, syscalls, fat12, mac, mls, elf, neurons) и предлагает
научить — ввести ответ прямо там же. Сам заданный вопрос (целиком, как
ключевая фраза) и ответ сохраняются на FAT12 в `AI.QA` тем же банковым
механизмом, что и веса в `AI.WTS` (`learned_bank_t`, `BANK_SIZE`=16,
round-robin вытеснение) — повторный такой же вопрос в этой же сессии
сразу получает ответ (банк держится в памяти на весь `run_ask_mode()`),
а после перезапуска снова находит его через `AI.QA`. Запись требует
`unlock` (как и `AI.WTS`); если диск заблокирован, ответ запоминается
только на текущую сессию (in-memory, без записи на диск), о чём явно
предупреждается. На самом prompt'е "научи меня" `exit`/`quit` — это
попытка выйти, а не буквальный текст ответа (та же ловушка, что и в
основном `? `-промпте) — иначе привычно набранное "exit" обучило бы
программу отвечать на этот вопрос словом "exit" навсегда.

**Список выученного**: команда `list` прямо в REPL (`list_learned()`)
печатает все непустые записи текущего `AI.QA`-банка как `[N] "вопрос" ->
ответ`, без поиска по ключевому слову — иначе единственный способ
увидеть, чему программа уже научена, был бы перебор вопросов наугад.
Если банк пуст, печатает отдельное сообщение об этом вместо пустого
списка.

## Сетевой стек (x86)

Первый шаг x86-версии того же сетевого стека, что уже полностью собран
на RISC-V (см. ниже) — начат с нуля с самого драйвера, пошагово, тем же
методом. В отличие от RISC-V, на x86 не было вообще никакой virtio-
инфраструктуры (там IDE/VBE/PS2, ни одного virtio-устройства) - драйвер
`src/drivers/virtio_net.c`/`.h` пишет её впервые для этого ядра, поверх
**legacy PCI-транспорта** (I/O-порты через BAR0, а не MMIO, как на
RISC-V) - осознанный выбор ради единообразия названия устройства
(`virtio-net-pci`, тот же протокол очередей), при том что сам транспорт
принципиально другой.

Требует `-netdev user,id=net0 -device virtio-net-pci,netdev=net0` (QEMU
по умолчанию делает `virtio-net-pci` "transitional" - legacy-интерфейс
доступен без дополнительных флагов вроде `disable-legacy`).

**Особенность legacy PCI, которой нет на MMIO-варианте**: размер очереди
(`Queue Size`, PCI-offset 0x0C) - только для чтения, драйвер не может
попросить очередь поменьше (в отличие от RISC-V MMIO-транспорта, где это
писалось напрямую). QEMU у `virtio-net-pci` сообщает 256 - код это
явно проверяет при инициализации и отказывается работать, если когда-
нибудь станет иначе, вместо того чтобы тихо всё сломать неверной
раскладкой памяти очереди. При этом реально используются только первые
8 слотов дескрипторной таблицы (`NUM_ACTIVE`) - как и на RISC-V,
остальные 248 просто не задействуются, экономя память на RX-буферах.
Позиция в avail/used-кольце крутится по модулю ПОЛНОГО 256 (как её
понимает устройство) - это отдельное от `NUM_ACTIVE` понятие, спутать
которое - готовый источник бага (что и произошло при первой попытке,
см. ниже).

PCI-инфраструктура (`pci.c`/`pci.h`) уже существовала (`lspci.bin`), но
только для перечисления устройств (vendor/device/class) - для virtio
понадобилось дополнительно прочитать BAR0 и включить bus mastering,
поэтому `pci_config_read32`/`pci_config_write32` вынесены из `pci.c` в
публичный `pci.h`.

Куча ядра (`heap.c`) - identity-mapped (виртуальный адрес совпадает с
физическим для всей области кучи, см. "KASLR/ASLR" ниже), поэтому
указатель `malloc()` МОЖНО было бы использовать как физический адрес
для virtqueue напрямую - но с некоторого момента `virtio_net.c` берёт
эту память из отдельного `dma_pool.c`, а не из `malloc()`. Причина не
в том, что куча перестала быть identity-mapped (она ей и осталась - см.
"KASLR/ASLR" за тем, почему), а в том, что ПЕРВАЯ попытка расширить
KASLR кучи требовала именно этого разрыва (куча временно переставала
быть identity-mapped) - `dma_pool.c` был написан для этого перехода и
оставлен даже после того, как сам переход откатили: не заводить лишнюю
связку "драйверу нужен malloc()-указатель как физический адрес" - более
правильная архитектура сама по себе, вне зависимости от того, как
устроена куча сегодня, и снимает этот риск на будущее. В отличие от
RISC-V, где отдельный постраничный аллокатор (`pmem.c`) был с самого
начала, на x86 его не было вообще - `dma_pool.c` (фиксированный
identity-mapped bump-аллокатор, страничное выравнивание уже встроено)
восполнил этот пробел.

**Реальный баг, пойманный при первой проверке**: `virtio_net_send()`
ждала завершения передачи тугим busy-spin'ом (миллионы итераций опроса
used-ring в памяти без единого выхода из режима исполнения гостя). Кадр
при этом РЕАЛЬНО уходил на провод - подтверждено пакетным захватом на
уровне QEMU (`-object filter-dump`): ARP-запрос долетал, SLIRP реально
отвечал - но `used->idx` в нашей копии памяти НИКОГДА не менялся за все
отведённые 50 млн итераций. Похоже, гостевой vCPU, ни разу не выходя из
режима исполнения (ни одного VM-exit), не давал циклу событий самого
QEMU (который и обслуживает virtio-backend/SLIRP) ни единого шанса
дописать used ring. Исправлено тем же приёмом, что уже описан у
`ide_wait_irq()` в `ide.c`: `sti()` (обязателен - `int 0x80` это
interrupt gate, IF гасится процессором на входе) плюс `hlt()` в цикле
ожидания вместо busy-spin - `hlt` гарантированно вызывает VM-exit на
каждой итерации, чего тугой спин не даёт никогда.

Три новых syscall'а (`SYS_NET_MAC`/`SEND`/`RECV`, 0x25-0x27) добавлены в
оба ABI-заголовка (`src/user/syscall.h` для ядра+userspace,
`src/libaxiom/include/syscalls.h` для asm-обёрток - у этого проекта нет
единого источника истины для номеров syscall'ов, оба правятся руками) и
обёрнуты вручную написанными NASM-стабами в `syscalls.asm`
(`ax_net_mac`/`ax_net_send`/`ax_net_recv`), как и все остальные
syscall'ы в libaxiom - готового шаблона "обёртка на N произвольных
аргументов" тут нет, каждая - отдельная маленькая asm-функция. Новый
класс MAC-политики `AX_CLASS_NET` разрешён confined `user_t` (как
`file_write`/`exec`, а не как `disk_raw`/`pci_raw`) - демо-программы
вроде `nettest.bin` рассчитаны запускаться из-под обычных изолированных
задач, как и всё остальное в AxSH.

Проверено вживую `fs/NETTEST.BIN` (собирается тем же способом, что и
`lspci.bin`) - тот же протокол проверки, что и у самого первого теста
RISC-V стороны этого стека: берёт MAC, шлёт широковещательный ARP-запрос
("кто держит 10.0.2.2?", гейтвей QEMU SLIRP), получает настоящий ответ:
```
net: MAC = 52:54:00:12:34:56
net: ARP request sent, listening for a reply (5s)...
net: got 64 byte frame
net: ARP reply! Sender MAC = 52:55:0a:00:02:02 -- TX and RX both confirmed working.
```

### ARP

Второй слой, `src/user/arp.h` — header-only (в стиле `axiom.h`-программ,
подключается в один .c-файл), портирован практически один в один с
RISC-V стороны (`src/user/rv64/arp.h`) - тот же протокол, тот же кэш на
8 записей, та же логика `arp_resolve`/`arp_maybe_respond`/
`arp_resolve_next_hop` (маршрутизация - см. подробное объяснение бага на
RISC-V стороне, здесь добавлена сразу, не пришлось находить отдельно).
Отличается только на уровне вызовов синтаксиса: `ax_net_mac`/
`ax_net_send`/`ax_net_recv`/`ax_sleep_ms` (`axiom.h`) вместо RISC-V-шных
`net_mac`/`net_send`/`net_recv`/`sleep_ms`.

Проверено вживую `fs/ARPTEST.BIN` (та же программа, что и на RISC-V -
резолвит гейтвей SLIRP и DNS, затем резолвит гейтвей повторно):
```
arp: resolve 10.0.2.2 (gateway) -> 52:55:0a:00:02:02 (10ms)
arp: resolve 10.0.2.3 (dns)     -> 52:55:0a:00:02:03 (10ms)
arp: resolve 10.0.2.2 (cached)  -> 52:55:0a:00:02:02 (0ms)
arp: ALL OK
```
Разница во времени видна даже на грубом 100 Гц таймере x86 (`ax_get_ticks`,
10мс на тик) - свежий резолв укладывается в один тик, повторный из кэша
- в ноль.

### IPv4 + ICMP (ping)

Третий слой, `src/user/icmp.h` — тоже header-only, поверх `arp.h`,
портирован построчно с RISC-V стороны (`src/user/rv64/icmp.h`): та же
RFC 1071 `ip_checksum()`, тот же `icmp_ping()` (исходящий echo request/
reply) и `icmp_maybe_respond()` (входящий - отвечает, если пингуют
саму AxOS). Единственная содержательная разница - измерение round-trip
времени: RISC-V использует `gettime()` (10МГц CLINT, микросекундная
точность), x86 - `ax_get_ticks()` (100Гц PIT, округление до 10мс) - на
локальной виртуальной сети разница не заметна (оба показывают ~0-10мс),
но на медленном таймере это менее показательно, чем на RISC-V.

Проверено вживую `fs/PINGTEST.BIN` (тот же тест, что и на RISC-V) -
классический `ping -c 4` на гейтвей SLIRP:
```
PING 10.0.2.2 (gateway):
  reply seq=1 time=10ms
  reply seq=2 time=10ms
  reply seq=3 time=10ms
  reply seq=4 time=10ms
--- statistics: 4 sent, 4 received
```
4 из 4, без единого бага при первой же попытке - как и с ARP, вся логика
уже проверена на RISC-V, портирование чисто механическое.

### UDP

Четвёртый слой, `src/user/udp.h` — портирован построчно с RISC-V стороны
(`src/user/rv64/udp.h`): `udp_send()`/`udp_recv()` поверх `arp_resolve_
next_hop()`/`ip_checksum()` из `icmp.h` (сам ICMP не нужен, но выносить
его в третий header ради переиспользования пары функций не стоило и на
RISC-V). UDP-чексумма сознательно не считается (поле = 0) - по RFC 768
это легальный режим "чексумма не проверялась", а не битый пакет.

Проверено вживую `fs/DNSTEST.BIN` (тот же тест, что и на RISC-V) - шлёт
настоящий DNS A-запрос на `example.com` через встроенный DNS-прокси QEMU
SLIRP (`10.0.2.3:53`) и разбирает достаточно ответа, чтобы убедиться, что
это осмысленный ответ именно на наш запрос:
```
dns: sending A query for example.com to 10.0.2.3:53...
dns: got 61 byte reply, id=0x1234, QR=1, answers=2
dns: ALL OK (valid response to our query, UDP TX+RX both work)
```

Добавление этого слоя (плюс `ARPTEST.BIN`/`PINGTEST.BIN`/`NETTEST.BIN` из
предыдущих слоёв) переполнило x86 FAT12-том - см. врезку "Расширение
FAT12 (128 КБ → 256 КБ → 1 МБ → 2 МБ)" выше за тем, что пришлось
поправить в `paging.c`, когда том вырос до 2 МБ и пересёк старую границу
фиксированных первых 4 МБ.

### DHCP

Пятый слой, `src/user/dhcp.h` — портирован построчно с RISC-V стороны
(`src/user/rv64/dhcp.h`): классический DORA-обмен (Discover→Offer→
Request→Ack, RFC 2131) с одним сервером, без renewal/rebinding/DECLINE/
RELEASE. При успехе перезаписывает `g_my_ip`/`g_subnet_mask`/
`g_router_ip` (`arp.h`) реально выданными значениями - до этого они были
статикой по умолчанию.

Проверено вживую `fs/DHCPTEST.BIN` (тот же тест, что и на RISC-V) -
полный DORA с QEMU SLIRP, затем **пинг полученного router** через уже
проверенный `icmp_ping()` - доказательство, что выданный адрес реально
рабочий, а не просто "сервер прислал ответ":
```
dhcp: static IP before lease: 10.0.2.15
dhcp: starting DORA (Discover/Offer/Request/Ack)...
dhcp: lease OK - IP=10.0.2.15 mask=255.255.255.0 router=10.0.2.2 dns=10.0.2.3
dhcp: pinging DHCP-assigned router to prove the lease actually works...
dhcp: ALL OK - ping reply using DHCP-assigned identity, rtt=10ms
```
Снова чисто с первой попытки.

### TCP

Шестой слой, `src/user/tcp.h` — портирован построчно с RISC-V стороны
(`src/user/rv64/tcp.h`): и клиент (`tcp_connect` - активное открытие), и
сервер (`tcp_accept` - пассивное открытие), three-way handshake, приём/
отправка данных, four-way close. Изначально - только "счастливый путь"
одного соединения за раз (без ретрансмита по таймауту и congestion
control - оба сознательные упрощения); поддержка нескольких ОДНОВРЕМЕННЫХ
соединений добавлена позже как отдельный дополнительный API поверх тех
же помощников - см. "TCP-сервер с несколькими одновременными
соединениями" ниже. Ретрансмит по таймауту тоже добавлен позже (перенесён
с RISC-V) - см. "TCP-ретрансмит + DNS-кэш/ретрансмит" ниже; congestion
control по-прежнему не сделан. В отличие от UDP, TCP-чексумма здесь
обязательна (по псевдозаголовку) - реальный стек на другом конце молча
дропнет сегмент с неверной суммой.

Проверено вживую с обеих сторон, причём оба раза - против НАСТОЯЩЕГО
чужого TCP-стека, не подделки:
- **Сервер** (`fs/TCPSERVE.BIN`, слушает порт 8080): QEMU `hostfwd=tcp::
  8080-:8080` + обычный `socket.connect()` с хоста Python. Реальный
  клиент отправил строку, получил на неё эхо с префиксом `Echo: `,
  закрыл соединение - гостевой лог показал тот же приём/отправку/закрытие
  с ЕГО стороны.
- **Клиент** (`fs/TCPTEST.BIN`, подключается к захардкоженному
  `10.0.2.99:9000`): QEMU `guestfwd=tcp:10.0.2.99:9000-tcp:127.0.0.1:
  9001` прозрачно прокидывает это ИСХОДЯЩЕЕ соединение на настоящий
  Python TCP-сервер на хосте - тот получил ровно то сообщение, что
  отправил `tcptest.bin`, и его ответ дошёл обратно до гостя.

Оба раза - чисто с первой попытки, без единого бага (тот же паттерн, что
и у ARP/ICMP/UDP/DHCP - протокол уже полностью проверен на RISC-V,
портирование чисто механическое).

### DNS (полноценный) + HTTP

Седьмой (и последний на сегодня) слой - `src/user/dns.h` (полноценный
резолвер `dns_resolve_a()`, с разбором ANSWER-секции и сжатия имён
0xC0xx - в отличие от `dnstest.c`/`udp.h`, который только проверял
заголовок ответа) и два клиента поверх него: `src/user/httpget.c`
(резолвит `example.com` и делает настоящий HTTP/1.0 GET) и
`src/user/httpsrv.c` (HTTP/1.0-сервер, отдающий файлы прямо из FAT12 -
`"/"` → `fs/INDEX.HTM`, портирован вместе со страницей с RISC-V
стороны). Всё портировано построчно с `src/user/rv64/{dns,httpget,
httpsrv}.h/.c`.

Проверено вживую по максимально жёсткому из всех тестов этого стека -
настоящий интернет через SLIRP, без единой подмены:
```
HTTP/1.1 200 OK
Date: Wed, 08 Jul 2026 16:29:38 GMT
Content-Type: text/html
Connection: close
Server: cloudflare
...
<!doctype html><html lang="en"><head><title>Example Domain</title>...
http: connection closed by server
http: total 829 bytes received
```
(DNS честно резолвил `example.com` через `10.0.2.3`, TCP поднялся на
порт 80 настоящего внешнего сервера за Cloudflare, GET ушёл и пришёл
настоящий HTML.)

`httpsrv.c` проверен зеркально - `hostfwd=tcp::8080-:80` + настоящий
`urllib.request.urlopen()` с хоста получил `200 OK` и корректную
`INDEX.HTM` прямо из FAT12-образа; гостевой лог показал тот же путь
(`GET /`) и тот же размер ответа (486 байт) с его стороны.

Этим фактически закрыт x86-параллель полного RISC-V сетевого стека:
**virtio-net-pci → ARP → IPv4/ICMP → UDP → DHCP → TCP (клиент+сервер) →
DNS+HTTP**, каждый слой - механический построчный порт с RISC-V,
протестированный вживую против настоящих внешних систем (SLIRP-гейтвей/
DNS/DHCP, реальный хостовый TCP-стек через `hostfwd`/`guestfwd`,
настоящий интернет). Единственный НЕ чисто механический шаг за весь этот
путь - расширение FAT12 до 2 МБ, потребовавшее реальной правки
`paging.c` (см. врезку в разделе UDP выше).

### TCP-сервер с несколькими одновременными соединениями

Изначальный `tcp.h` (см. "TCP" выше) держит только ОДНО соединение за
раз - единственный глобальный `tcp_conn_t`, `tcp_accept()` блокируется,
пока не примет одного клиента, обслуживает его целиком и только потом
снова слушает. Добавлен отдельный, ДОПОЛНИТЕЛЬНЫЙ API `tcp_mux_*` (в
конце того же `tcp.h`) поверх тех же низкоуровневых помощников
(`tcp_send_segment`/`tcp_parse_segment`/`tcp_checksum`) - `tcp_connect`/
`tcp_accept`/`tcp_send`/`tcp_recv`/`tcp_close` не трогались и продолжают
работать как раньше (`tcptest.c`/`tcpserve.c`/`httpget.c` их и
используют).

Модель: `TCP_MAX_CONNS` (4) слотов, каждый - свой `tcp_conn_t` + стейт-
машина (`SYN_RCVD` → `ESTABLISHED` → `CLOSING` → `FREE`). Один вызов
`tcp_mux_poll()` = одна попытка `ax_net_recv()` (один входящий кадр) -
вызывающий код сам гоняет цикл. Как и весь остальной `tcp.h` - только
"счастливый путь": `tcp_mux_poll()` повторяет SYN-ACK при получении
ПОВТОРНОГО SYN для уже известного слота (см. ниже), а `tcp_mux_send()`
позже получил свой собственный неблокирующий ретрансмит по таймауту -
см. "TCP-сервер: неблокирующий per-slot ретрансмит" ниже. Ни
переупорядочивания сегментов, ни SYN-flood защиты по-прежнему нет,
только таймаут на подвисшие полуоткрытые/закрывающиеся слоты (3с / 500мс),
чтобы они не отъедали слот навсегда.

`src/user/httpsrv.c` переведён на этот API: `tcp_accept()`+`tcp_recv()`+
`tcp_send()`+`tcp_close()` в одном блокирующем цикле заменены на
`tcp_mux_listen(80)` один раз при старте, затем `tcp_mux_poll()` в
кооперативном цикле, `tcp_mux_send()`/`tcp_mux_close()` при готовности
запроса. Логика разбора HTTP-запроса и отдачи файла из FAT12 не
изменилась ни на строчку - изменился только способ, которым сервер ждёт
клиентов и данные.

Проверено вживую: 3 Python-потока открывают TCP-соединение к
`httpsrv.bin` ОДНОВРЕМЕННО (все три - до того, как хоть один отправил
запрос), держат его открытым, затем каждый шлёт `GET /` - и получают
корректный `INDEX.HTM` (`200 OK`, `473` байт) все трое:
```
httpsrv: serving FAT12 files on port 80 ("/" -> INDEX.HTM), up to 4 concurrent connections
httpsrv: client connected from 10.0.2.2
httpsrv: GET /
httpsrv: 200 OK, sent 486 bytes
httpsrv: connection closing

httpsrv: client connected from 10.0.2.2
httpsrv: GET /
httpsrv: 200 OK, sent 486 bytes
httpsrv: connection closing

httpsrv: client connected from 10.0.2.2
httpsrv: GET /
httpsrv: 200 OK, sent 486 bytes
httpsrv: connection closing
```
Со старым `tcp_accept()`-сервером это было бы физически невозможно -
второй и третий клиент просто не могли бы даже НАЧАТЬ рукопожатие, пока
первый не закрыл бы своё соединение целиком.

### TCP-ретрансмит + DNS-кэш/ретрансмит (перенесено с RISC-V)

Оба добавлены на x86 позже, чем на RISC-V (см. соответствующие разделы в
RISC-V-части README и память проекта `project_riscv_tcp_retransmit`/
`project_riscv_dns_cache_retry`) - механический перенос уже проверенной
там логики, только вызовы (`ax_net_*`/`ax_sleep_ms`/`ax_get_ticks` вместо
сырых RISC-V-обёрток). Единственное содержательное отличие - разрешение
часов для DNS-кэша: x86 использует `ax_get_ticks()` (100Гц PIT, 10мс/тик)
вместо RISC-V-шного `gettime()` (10МГц CLINT), с потолком TTL и той же
логикой протухания, только сравнение сделано через явно wrap-safe
`(int)(now - expiry) < 0` (32-битный счётчик тиков технически может
переполниться при достаточном аптайме, в отличие от 64-битного RISC-V
`long`).

`tcp.h`: тот же `TCP_RTO_MS`(300мс)/`TCP_RTO_MAX_MS`(2с)/
`TCP_MAX_RETRIES`(5) паттерн применён к `tcp_send()` (теперь ждёт и
проверяет ACK вместо fire-and-forget), `tcp_connect()`/`tcp_accept()`
(повтор SYN/SYN-ACK в пределах общего `timeout_ms`), `tcp_close()`
(полный RTO-backoff, см. "FIN: полный RTO-backoff" ниже), `tcp_mux_poll()`
(повтор SYN-ACK при дублирующемся SYN).

`dns.h`: та же 8-записевая TTL-кэш-таблица + тот же RTO-ретрансмит
запроса. Новый `fs/DNSCACHE.BIN` (`src/user/dnscachet.c`) - тот же тест,
что и на RISC-V стороне.

**Проверено вживую** (x86 не имеет serial-консоли - AxSH управляется
через HMP `sendkey`, см. память `project_x86_network_stack`):
- `DNSCACHE.BIN`: 1-й резолв `example.com` - 14 тиков `ax_get_ticks()`,
  2-й (тот же хост, кэш) - **0 тиков**, 3-й (`cloudflare.com`) снова идёт
  по сети - тот же качественный результат, что и на RISC-V, просто с
  более грубым разрешением счётчика (100Гц против 10МГц).
- `HTTPGET.BIN` (регрессия, реальный интернет через DNS+TCP) -
  `HTTP/1.1 200 OK`, 829 байт, соединение закрыто сервером штатно.
- Тот же адверсариальный тест, что и на RISC-V (Python-скрипт на
  `-netdev socket`, изображающий поддельный TCP-сервер, намеренно
  игнорирует первые 2 SYN и первый пакет данных TCPTEST.BIN) - клиент
  трижды посылает SYN с одним и тем же ISN, дважды посылает идентичный
  сегмент данных, соединение всё равно доходит до конца успешно.

### TCP-сервер: неблокирующий per-slot ретрансмит (x86-версия)

Перенесено с RISC-V (см. "TCP-сервер: неблокирующий per-slot ретрансмит"
в RISC-V-разделе за полным описанием очереди `outbuf`/`out_*`,
`tcp_mux_pump()` и найденного бага с компактификацией буфера - тот же
баг был исправлен и здесь синхронно, до отдельного обнаружения на x86).

**Одно НАСТОЯЩЕЕ платформенное отличие, не механическое**:
`TCP_MUX_OUT_BUF_SIZE` на x86 - **1024Б**, не 8320Б, как на RISC-V.
Причина - `build.bat`'s `objcopy -O binary` прописывает ВЕСЬ `.bss`
(включая новый буфер) нулями прямо в плоский бинарник, а каждая x86
пользовательская программа обязана целиком уместиться в один слот
`USER_PROGRAM_SLOT_SIZE=0x10000` (64КБ, `kernel.c`) - `argv` живёт сразу
за концом легального размера программы (`USER_ARGS_OFFSET=0xF800`).
Взятый по аналогии с RISC-V `TCP_MUX_OUT_BUF_SIZE=8320` раздул
`httpsrv.bin` до 90748Б - `sh: not a valid executable` при попытке
запуска (файл не помещается в 63488Б бюджет). `httpsrv.c` (обе
платформы) поэтому получил `mux_send_all()` - ждёт свободного места в
очереди через `tcp_mux_poll()`, если ответ крупнее буфера слота, вместо
однократной попытки.

**Проверено вживую**: тот же адверсариальный тест (два поддельных
клиента, один намеренно "теряет" первый сегмент) через `-netdev socket`
+ HMP `sendkey` (x86 без serial-консоли) - идентичный результат
RISC-V-версии. Плюс отдельный `hostfwd`-тест реальным host TCP-клиентом:
запрос `/SH.BIN` (файл крупнее 1024Б `TCP_MUX_OUT_BUF_SIZE`) до
исправления компактификации буфера зависал НАВСЕГДА (`httpsrv: GET
/SH.BIN` печаталось, `200 OK, sent N bytes` - никогда); после
исправления - полная доставка (`Content-Length` совпадает с реально
полученными байтами).

### FIN: полный RTO-backoff

`tcp_close()` (однослотовый) и `tcp_mux_close()`/`tcp_mux_poll()`
(многосоединённый) изначально ретранслировали FIN максимум один раз (на
середине фиксированного окна дренажа) - переведены на тот же полный
RTO-backoff (`TCP_RTO_MS`→`TCP_RTO_MAX_MS`, до `TCP_MAX_RETRIES` попыток),
что и `tcp_send()`/`tcp_connect()`/`tcp_accept()`. `tcp_close()` теперь
ДЕЙСТВИТЕЛЬНО проверяет ACK за свой FIN (`seg.ack >= expect_ack`) и
останавливается сразу по получении, не дожидаясь всех попыток.
`tcp_mux_close()`/`tcp_mux_pump()` получили общий `tcp_mux_start_closing()`
- переиспользует те же `out_retries`/`out_rto`/`out_rto_deadline` поля
слота, что и ретрансмит данных (к моменту закрытия очередь данных уже
пуста, поля свободны) - без роста `tcp_slot_t`, важно на x86 с его тесным
64КБ-бюджетом на программу (см. врезку выше).

**Реальный баг, найденный вживую**: первая версия `tcp_mux_start_closing()`
увеличивала `conn.snd_nxt` СРАЗУ после отправки FIN (как и раньше делал
однократный `tcp_mux_close()`). Но ретрансмит из RTO-свипа
`tcp_mux_poll()` строит сегмент из ТЕКУЩЕГО `snd_nxt` - если тот уже
сдвинут, "повтор" на самом деле собирает СЛЕДУЮЩИЙ (seq+1) сегмент, а не
настоящий повтор потерянного FIN. Пойман тестом с поддельным
собеседником: два "FIN" пришли с РАЗНЫМИ seq (`0x77aa023f` затем
`0x77aa0240`). Исправлено - `snd_nxt` теперь НЕ трогается в
`tcp_mux_start_closing()` (как и в однослотовом `tcp_close()`, где
инкремент и так был отложен до конца всех попыток) - слот всё равно
освобождается сразу после подтверждения закрытия, корректировать
`snd_nxt` впрок незачем.

**Ещё два реальных, полностью НЕСВЯЗАННЫХ с TCP бага ядра**, найденные
по пути на x86 (оба существовали ДО этой сессии, просто ничем раньше не
триггерились):

1. **NX-краш на границе W^X** - рост `httpsrv.bin` (новые `out_*` поля
   слота) съел запас, который ASLR обычно использует, чтобы подогнать
   `wx_data_off` (границу код/данные) под границу страницы (см. `align_fix`
   в `elf.c`). Без этого запаса `aslr_delta` остаётся 0, и граница
   попадает НА СЕРЕДИНУ страницы - `_ax_init_stack_guard` (самый первый
   вызов из `_start`, ещё до `main()`) оказался в той же 4КБ-странице,
   что и начало `.data`, и вся страница целиком помечалась `NX`
   (`paging_create_user_directory()` не умеет разные права внутри одной
   PAE-страницы, поэтому "пограничная" страница вынужденно получала ОДНО
   значение целиком). `*** PAGE FAULT ... [NX execute violation] - task
   killed ***` на каждом запуске, 100% воспроизводимо.
2. **SMAP-краш (system halted)** после первой попытки исправить (1) через
   перекодирование границы "в другую сторону" (страница → код вместо
   данных) - та же страница содержала и легитимный ЗАПИСЫВАЕМЫЙ `.bss`
   (`tcp_rx`), который тогда сломался в обратную сторону (кодовая
   классификация = без `PAE_RW`). `virtio_net_recv()`'s копирование
   входящего кадра в пользовательский буфер упало на `[SMAP] kernel data
   access to user page ... (missing stac?)`.

Оба - проявления ОДНОЙ и той же причины: `user.ld` никогда не
гарантировал выравнивание `.data`/`.bss` на границу страницы, а PAE
физически не может дать разные права разным половинам одной страницы.
Любая попытка "угадать" классификацию для пограничной страницы (вверх
или вниз) чинит один случай и ломает другой. **Настоящий фикс** - явный
`. = ALIGN(0x1000);` в `user.ld` перед `.data`, гарантирующий, что
граница ВСЕГДА совпадает со страницей независимо от ASLR/бюджета слота
(старая логика в `paging.c` вернулась к исходному варианту - округление
вверх; `elf.c`'s `align_fix` теперь всегда вычисляет 0 и просто ничего
не делает). Цена - ~4КБ паддинга на каждую x86-программу, потребовавшая
дополнительно ужать `TCP_MUX_OUT_BUF_SIZE` до 256Б (с 1024Б) и учитывать
ДВА разных лимита размера: `USER_ARGS_OFFSET`=63488Б (сама программа) И
чуть более тесный `ELF_STAGING_SIZE`=64000Б (обёрнутый `.ELF`-файл
целиком - заголовки+таблица релокаций+флэт-бинарник).

Из-за уменьшения буфера всплыл ЕЩЁ один баг: `mux_send_all()` резала
исходящие данные на куски до 512Б (сетевой сегментный предел) - но раз
буфер очереди стал МЕНЬШЕ 512Б, кусок физически никогда не помещался бы
ни при каком количестве освобождённого места, и цикл ожидания зависал
бы навсегда. Исправлено ограничением куска `min(512, TCP_MUX_OUT_BUF_SIZE)`
(оба `httpsrv.c`, хотя на RISC-V это чисто защитное - буфер там всё ещё
больше 512Б).

**Проверено вживую** (обе платформы, `-netdev socket` с поддельным
собеседником, намеренно не подтверждающим FIN): и `tcp_close()`
(`tcptest.elf`/`tcpserve.bin`), и `tcp_mux_close()` (`httpsrv`) шлют
идентичный повторный FIN (тот же seq) после потери первого и доводят
закрытие до конца после подтверждения. Плюс полная регрессия на обеих
платформах: `httpget`/`HTTPGET.BIN` (реальный интернет), `httpsrv`'s
3-одновременных-соединения тест, `SH.BIN` через `hostfwd` (крупный файл,
несколько раундов ожидания очереди) - всё без изменений в поведении.

#### Сравнение с RISC-V-оригиналом

| | x86 (этот раздел, порт) | RISC-V (см. "RISC-V порт" ниже, оригинал) |
|---|---|---|
| Транспорт | virtio-net-pci, **legacy PCI (I/O-порты)** | virtio-net, **MMIO** |
| Очередь устройства | Queue Size — **read-only**, QEMU навязывает 256 | Queue Num — RW, драйвер сам выбирает размер |
| Физическая память под очередь | кучa identity-mapped — `malloc()`-указатель уже физический адрес, страница вручную выравнивается | отдельный постраничный аллокатор `pmem.c` |
| Ожидание завершения TX | тугой busy-spin **завис** - понадобился `sti()+hlt()` (см. "Драйвер virtio-net" выше) | тот же busy-spin — работает без проблем |
| Протоколы ARP/ICMP/UDP/DHCP/TCP/DNS | построчный порт, багов почти не было — вся сложность уже была найдена и исправлена на RISC-V-стороне | написаны там первыми, весь путь багов пройден на этой стороне |
| Единственный НЕ механический шаг этого порта | рост FAT12 до 2 МБ пересёк границу фиксированной `PD[1]` — потребовал правки `paging.c`, никак не связанной с сетью | — |

Итог тот же, что и на RISC-V-стороне: два независимых стека, написанных
с нуля под разные транспорты устройства, сошлись к одному и тому же
протокольному коду — лучшее подтверждение, что уровни ARP/IPv4/UDP/TCP/
DNS в `arp.h`/`icmp.h`/`udp.h`/`dhcp.h`/`tcp.h`/`dns.h` спроектированы
действительно независимо от конкретного драйвера NIC.

## RISC-V порт (rv64)

Полностью независимый от x86 порт: своё ядро (`src/arch/riscv64/`), свой
userland (`src/user/rv64/`), своя сборка (`build_riscv.bat`) и свой
тулчейн (`riscv64-unknown-elf`-подобный, xPack RISC-V GCC). S-mode ядро
под прошивкой **OpenSBI** (QEMU `virt`, `-bios default`, M-mode) + U-mode
пользовательские процессы, Sv39 страничная адресация, вытесняющий
планировщик с приоритетами (тот же механизм, что и на x86, см. ниже),
virtio-драйверы (блок/GPU/ввод) и FAT12.

### Загрузка и обработка прерываний

`src/arch/riscv64/boot/entry.S`: `_start` глушит прерывания (`csrw sie,
zero`), ставит `stvec = trap_entry`, зануляет `.bss` (включая `.sbss` —
иначе `.sbss` попадает за стеком и портит данные), выставляет `sp =
_stack_top`, вызывает `kernel_main`. OpenSBI выступает и firmware (M-mode,
физически по `0x80000000`), и провайдером пары SBI-вызовов: `SBI_SET_TIMER`
(EID `TIME`) для таймера и `SBI_SYSTEM_RESET` (EID `SRST`) для
shutdown/reboot. Ядро загружается по `0x80200000` и работает целиком в
S-mode.

**Трюк с `sscratch`** (`entry.S`): инвариант — `sscratch == 0` в S-mode,
`sscratch == _stack_top` в U-mode. `trap_entry` делает `csrrw sp, sscratch,
sp`; если получившийся `sp == 0` — трап пришёл из S-mode, иначе — из
U-mode (кладём `user_sp` через `x1` как scratch, обнуляем `sscratch`). Оба
пути сохраняют все 31 GPR в 256-байтный кадр и зовут `trap_handler(scause,
sepc, stval, sp)` (`kernel_main.c`); обратно — `sret`, режим возврата
выбирается по `sstatus.SPP`.

`trap_handler()` обрабатывает: `ecall` из U/S-mode → `syscall_dispatch()`;
таймерное прерывание → инкремент `tick_count`, перевзвод SBI-таймера,
`schedule()` — **только если трап пришёл из U-mode** (`SPP==0`), иначе
ядро могло само сейчас крутиться внутри `sys_read`, и трогать его кадр
опасно; page fault/illegal instruction/access fault → если виновник был в
U-mode, убивает только этот процесс (`PROC_ZOMBIE`, будит ожидающих через
`wait()`, `schedule()`) — если сам фолтнул ядро (`SPP==1`), печатает и
останавливается (`wfi`-цикл), это баг ядра.

**Найденный и исправленный баг таймера**: `timer_init()` (арм таймера +
`sie.STIE`) и глобальный `sstatus.SIE=1` изначально вызывались уже ПОСЛЕ
`jump_to_umode()` — а `jump_to_umode()` никогда не возвращается (сразу
`sret` в первый процесс). То есть этот код был мёртвым НА ЛЮБОЙ загрузке —
аппаратное таймерное прерывание не включалось вообще никогда, и любое
"переключение задач" на деле было чисто добровольным (`yield()`/retry
неблокирующего `read()` — оба синхронные `ecall`, срабатывают независимо от
`sie`/SIE). Процесс, не делающий вообще ни одного syscall'а (чистый
compute-loop), из-за этого мог повесить всю систему навсегда. Исправлено
переносом `timer_init()`+`sstatus.SIE` до `jump_to_umode()`
(`kernel_main.c`) — проверено вживую: `spin.elf` (пустой `while(1)
counter++`) больше не виснет и корректно вытесняется по тику.

### Страничная память (Sv39)

`src/arch/riscv64/paging.c`/`paging.h` — 3-уровневая Sv39-адресация, один
глобальный `root_pt[512]` (статический массив в `.bss`). `paging_init()`
сначала ставит две грубые 1 ГБ-гигастраницы (MMIO-регион `0x0`, RAM/OpenSBI
`0x80000000`), включает Sv39 через `satp`. `paging_harden_kernel()`
(вызывается после `pmem_init()`/`heap_init()`, до первого создания
пользовательской таблицы) пересобирает эту область на постраничный
**W^X**: OpenSBI (первые 2 МБ) — только чтение, `.text`/`.rodata` ядра —
R+X, `.data`/`.bss`/стек — R+W, остаток RAM (до 128 МБ) — R+W
мегастраницами.

**Изоляция процессов**: `paging_create_user_pt()` — свежая нулевая корневая
таблица, копирует ПО ЗНАЧЕНИЮ записи `[0]` (MMIO) и `[2]` (ядро/RAM) из
общей `root_pt` (общие поддеревья ядра/MMIO), оставляет `[1]`
(пользовательское VA-пространство `0x40000000`-`0x7FFFFFFF`) нулевым —
его заполняет ELF-загрузчик под конкретный процесс. Т.е. у каждого
процесса своя корневая таблица, но общие поддеревья ядра/MMIO.

SMAP-аналог: `sstatus.SUM` включается только на время самого
`syscall_dispatch()` (`user_access_enable`/`disable`, бит 18) — случайное
обращение ядра к пользовательскому указателю ВНЕ syscall'а (таймер, fault-
обработчик) по-прежнему фолтит. ELF-загрузчик дополнительно отклоняет любой
`PT_LOAD`-сегмент вне `[0x40000000, 0x80000000)` — не даёт заранее
подготовленному ELF воткнуть маппинг в общее поддерево ядра/MMIO.
Пользовательский стек — одна страница на `0x7F000000`.

### Процессы и планировщик — тот же механизм приоритетов, что и на x86

`src/arch/riscv64/proc.c`/`proc.h`: `MAX_PROCS=4`, состояния `UNUSED`/
`RUNNABLE`/`RUNNING`/`WAITING`(ждёт `wait()`)/`ZOMBIE`. `proc_t`:
`state`/`pid`/`wait_pid`/`exit_code`/`name`/`regs[32]`/`sepc`/`pagetable`/
`heap_brk`, плюс те же поля приоритета, что и у x86 `task_t`: `priority`
(1-10, по умолчанию 3), `slice_left` (тиков осталось в текущем заходе),
`ticks` (суммарно). Явный комментарий в коде: "Mirrors the same scheme
added to the x86 side".

`schedule(frame, sepc)` — weighted round-robin: если текущий процесс
всё ещё `RUNNING` (это возможно ТОЛЬКО при настоящем вытеснении по тику
таймера — все прочие вызывающие явно переводят процесс в другое состояние
ПЕРЕД вызовом `schedule()`), инкрементирует `ticks`, декрементирует
`slice_left`; если ещё >0 — просто возвращается (тот же процесс продолжает
исполняться, без переключения). Иначе — ищет следующий `RUNNABLE` по
кольцу, при переключении сбрасывает его `slice_left = priority` (свежий
заход). `proc_set_priority(pid, priority)` — клампится к `[1,10]`, эффект
только со следующего захода (не режет текущий на лету).

Гочка, которую пришлось отдельно чинить: `SYS_YIELD` **обязан** принудительно
обнулять `slice_left` перед вызовом `schedule()` — иначе добровольный
`yield()` (вызывается, когда состояние процесса ВСЁ ЕЩЁ `RUNNING`, в
отличие от `SYS_EXIT`/`SYS_WAIT`/неблокирующего `read()`, которые меняют
состояние заранее) рисковал быть "поглощён" остатком слайса и не отдать
CPU по-настоящему.

Команда shell `nice <PID> <1-10>` → `set_priority()` → `SYS_SET_PRIORITY`.
Проверено вживую: два процесса `spin.elf` (чистый CPU-bound цикл, см. выше)
с приоритетами 1 и 10 за одинаковое время показывают в `ps` прирост тиков
примерно 5:1 (не ровно 10:1 — конкурирует ещё и AxSH с приоритетом 3).

#### Настоящая sleep-очередь (не busy-wait) — оба платформы

`sleep_ms()` — самый часто вызываемый блокирующий примитив в системе
(`sh.c`/`axsh.c` поллят `ax_task_alive`/`ax_task_alive`-аналог каждые 10мс
в цикле ожидания foreground-задачи). До этого раунда на обеих платформах
это был busy-wait, не настоящий блок:

- **RISC-V** (было): `sleep_ms()` — чисто userspace-цикл
  `while (gettime() < end) yield();` (`src/user/rv64/syscall.h`). Ядро
  вообще не знало, что процесс "спит" — он просто постоянно просил свой
  ход и сразу его отдавал.
- **x86** (было): `sleep_ms()` (`kernel.c`) — `hlt`-цикл ВНУТРИ обработчика
  `SYS_SLEEP`, пока `timer_ticks` не дойдёт до цели. `hlt` сам по себе не
  жрёт CPU, но задача весь это время оставалась "текущей" в кольце
  планировщика — продолжала получать свои ходы (переключение на неё,
  проверка часов, снова `hlt`) вместо того, чтобы быть пропущенной,
  размывая долю CPU остальных задач.

**RISC-V**: новое состояние `PROC_SLEEPING` (`proc.h`) + поле
`wake_tick` (сырой CSR `time`). `proc_wake_sleepers()` (`proc.c`)
сканирует `procs[]` и переводит просроченных спящих обратно в
`RUNNABLE` — вызывается БЕЗУСЛОВНО на каждом таймерном тике
(`kernel_main.c`), ДО существующей проверки `SPP` (та решает, звать ли
`schedule()` прямо сейчас, а не нужно ли вообще искать проснувшихся —
иначе полностью простаивающая система, где все спят, никого бы не
разбудила). Условие вызова `schedule()` расширено с `SPP=0` (прервано
из U-mode) до `SPP=0 ИЛИ current_pid<0` — второе условие нужно, чтобы
процесс, только что разбуженный этим же тиком, реально подхватился,
пока CPU простаивал в `wfi` (никакого "текущего" контекста для защиты
там нет, переключаться безопасно). `SYS_SLEEP` (новый, `syscall.c`)
списан один-в-один с уже существующим `SYS_WAIT` — сохраняет кадр,
переводит в `PROC_SLEEPING`, зовёт `schedule()`. `sleep_ms()`
(`src/user/rv64/syscall.h`) упростился до одного `__syscall1(SYS_SLEEP, ms)`.

**x86**: `task_t` (`tasking.c`) получил `sleeping`/`wake_tick`.
`schedule()`: (1) скан пробуждения просроченных спящих в начале функции
(тот же принцип, что и `proc_wake_sleepers`, только инлайн — кольцо
маленькое); (2) fast path (пропуск переключения, если у задачи ещё
остался слайс) теперь исключает спящих — спящая задача НИКОГДА не
удерживает CPU, даже посреди слайса; (3) поиск "кому отдать CPU"
пропускает спящих. x86 не может напрямую переиспользовать RISC-V-приём
"ранний return с готовым кадром" из обработчика syscall'а — но
`idt.asm`'s `timer_interrupt_handler` и `syscalls.asm`'s
`syscall_handler` кладут ИДЕНТИЧНЫЙ по раскладке кадр GPR (тот же
порядок push), так что `syscalls.asm` делает тот же приём ("сохранить
RSP → `schedule()` → RAX = RSP следующей задачи → восстановить
регистры → `iretq`") сразу после возврата из `syscall_dispatch`, если
новая `task_current_wants_resched()` (tasking.c) говорит "да" — сейчас
единственная причина этого "да" - только что усыпившая себя задача
(`sys_sleep()` → `task_sleep_current()`). `sleep_ms()` сама по себе
(старый `hlt`-цикл) оставлена БЕЗ ИЗМЕНЕНИЙ — ей всё ещё пользуются
`sys_beep()` и приветственная задержка (короткие, ring0-внутренние,
синхронные вызовы, которым не нужна настоящая приостановка задачи;
`sys_beep()` конкретно должна выключить динамик СРАЗУ после задержки в
той же C-функции, что сломала бы настоящая точка переключения).

**Реальный баг, пойманный живым тестом (x86)**: первая версия
`schedule()`'s пропуска спящих при выборе "кому отдать CPU"
ОШИБОЧНО использовала ТУ ЖЕ переменную `next` и для топологии кольца
(нужна unlink'у выходящей задачи), и для пропуска спящих (нужен только
для выбора следующей) — из-за чего `pred->next = next` при выходе
задачи мог "проглотить" не только `dying`, но и любую спящую задачу,
случайно пропущенную тем же поиском: она молча вышибалась из кольца
(без освобождения памяти — утечка), переставая быть видна `ps`/
`schedule()` навсегда, БЕЗ крэша и БЕЗ сообщения об ошибке. Пойман
именно живым тестом: фоновые `sleep.bin`+`top.bin` оба бесследно
исчезали из `ps` после того, как `sleep.bin` просыпался и завершался.
Исправлено разделением: `immediate_next = dying->next` (для unlink'а,
без пропуска спящих) отдельно от `next` (для выбора, с пропуском).

### Системные вызовы (`src/arch/riscv64/syscall.h`, зеркалируется в `src/user/rv64/syscall.h`)

| 26 | `SYS_NET_MAC` | `net_mac(mac[6])` → 1/0; MAC упакован в младшие 48 бит возврата |
| 27 | `SYS_NET_SEND` | `net_send(frame,len)` → 0/-1; сырой Ethernet-кадр, без virtio-заголовка |
| 28 | `SYS_NET_RECV` | `net_recv(buf,max_len)` → байт скопировано, 0 если ничего не пришло (неблокирующий поллинг) |
| 29 | `SYS_SLEEP` | `sleep_ms(ms)` — настоящий блок (`PROC_SLEEPING`), не busy-wait, см. ниже |
| 30 | `SYS_EXEC_PIPE` | `exec_pipe(cmdline,stdout_pipe_id,stdin_pipe_id)` → новый pid или -1, см. ниже |

Все указатели/длины проверяются на попадание в пользовательское VA-окно
(`user_range_ok`/`user_string_ok`) до использования — `kptrtest.elf`
специально проверяет отказ на адресе ядра и на переполняющей длине.

### Минимальный argv + потоковые pipes (`cmd1 | cmd2`)

Раньше на RISC-V не было ВООБЩЕ никакого argv (`int main(void)` у каждой
программы, `exec(path)` брал только путь) и никакой инфраструктуры
редиректа/pipe — обнаружилось только при попытке перенести x86'шные
потоковые pipes на эту платформу: будущему `grep`-фильтру было бы
физически некуда передать паттерн поиска. Оба пробела закрыты в одном
раунде.

**argv**: `elf_load()` (`elf_loader.c`) теперь принимает `cmdline`
("FILENAME.ELF arg1 arg2...", как у x86 `do_exec`) вместо голого имени
файла — парсит имя до первого пробела для `vfs_load()`, остаток
превращается в `argv[1..]`. Строки + `argv[]` (NULL-terminated массив
указателей) пишутся в ОДНУ фиксированную (не ASLR) страницу
`USER_ARGS_VA = USER_VA_TOP - 0x1000` на самом верху пользовательского
VA — `pick_stack_va()`'s ASLR-диапазон для стека сужен на одну страницу,
чтобы никогда сюда не попасть. `a0`/`a1` (первые два регистра
целочисленных аргументов RISC-V) выставляются в `argc`/`USER_ARGS_VA`
прямо в `proc_t.regs[]` после `proc_create()` — **`crt0.S` не тронут
вообще**: `_start` и так делает голый `call main`, а a0/a1 к этому
моменту уже содержат то, что записал `schedule()`'s обычный "восстановить
regs[] в кадр" путь (единственное исключение — `jump_to_umode()`'s
одноразовый бутстрап самого первого процесса при загрузке, которого
`run`/pipe-задачи никогда не касаются). Существующие `int main(void)`
программы не затронуты — лишние входящие регистры C просто игнорирует.

**Pipes**: в отличие от x86 (пришлось имитировать stdin/stdout поверх
системы, где их вообще не было), RISC-V уже имел настоящие fd 0/1/2,
привязанные к UART (`sys_write`/`sys_read`, `syscall.c`) — pipes
используют именно их, а не x86'шный трюк с `"PIPE:N"` как именем файла.
`proc_t` получил `stdout_pipe_id`/`stdin_pipe_id` (-1 = обычный
UART/консоль). Новый `SYS_EXEC_PIPE(cmdline, stdout_pipe_id,
stdin_pipe_id)` — как `SYS_EXEC`, но опционально подключает stdout/stdin
новой задачи к `pipe_bufs[N]` (тот же `PIPE_MAX=2`×`PIPE_BUF_SIZE=2048`
формат, что и у x86 - единственный в ядре буфер, видимый ДВУМ разным
процессам одновременно) — только писатель сбрасывает буфер при запуске
(читатель не должен затирать уже произведённое). `sys_write()`'s
`fd==1/2` и `SYS_READ`'s `fd==0` ветки проверяют `stdout_pipe_id`/
`stdin_pipe_id` первым делом. Блокирующее чтение — прямое расширение
`PROC_SLEEPING` из sleep-очереди: новое состояние `PROC_WAITING_PIPE`,
`proc_wake_sleepers()` (`proc.c`) получил второе условие пробуждения
(`pipe_ready()`, `syscall.c`) рядом с уже существующим. Выход писателя
(`SYS_EXIT`, `SYS_KILL`, page-fault kill в `kernel_main.c` — на RISC-V
нет общего "on_exit" хука, все три места независимо выставляют
`PROC_ZOMBIE`, как и раньше) выставляет `writer_done=1` через
`pipe_mark_writer_done()` — читатель получает EOF, а не висит вечно.

Новая `grep.c` (`src/user/rv64/grep.c`) — единственная на RISC-V
отдельная ELF-программа-фильтр (`cat`/`echo` остаются встроенными
командами `axsh.c`, не файлами — стандартного "cat"-эквивалента для
цепочки pipe'ов до сих пор нет). `argc==2` (только паттерн) читает
`fd 0` до EOF; `argc>=3` (паттерн + файл) открывает файл, как у x86.
`axsh.c` получил `|`-парсинг (тот же принцип, что у x86 `sh.c`: оба
запускаются сразу, foreground-ожидание только на cmd2) и заодно
починку `cmd_run()` — раньше многословный `run cmd arg` целиком
uppercase'ился в 13-байтный буфер без разбора по пробелам и никогда не
работал по-настоящему; теперь имя файла и аргументы разбираются
отдельно (регистр аргументов не трогается — паттерн `grep` не должен
портиться).

Проверено вживую: `run grep.elf hello TESTFILE.TXT` (argv доходит до
`main()` совершенно независимо от pipes), `grep.elf hello TESTFILE.TXT
| grep.elf world` (настоящий поток между ДВУМЯ разными процессами,
второй grep находит паттерн в строке, прилетевшей от первого), pipe с
непроходящим паттерном корректно завершается (EOF, не виснет),
`kill`/фоновые задачи не задеты.

### Драйверы VirtIO

Все четыре сканируют до 8 MMIO-слотов (`0x10001000` + `i×0x1000`, layout
QEMU `virt`):

- **`virtio_blk.c`** — блочное устройство, поддержаны и legacy (v1), и
  modern (v2) MMIO. `virtio_blk_read/write(sector, buf)`,
  `virtio_blk_capacity()`.
- **`virtio_gpu.c`** — 2D-only GPU (без 3D/virgl), фиксированное разрешение
  800×600 (было 640×480 - см. "Графика на RISC-V: догоняем x86" ниже),
  формат B8G8R8A8. Пиксели пишутся напрямую в линейный framebuffer
  в RAM гостя, `virtio_gpu_flush()` проталкивает их хосту. Плюс
  `putpixel`/`fill_rect`/`getpixel`, битмап-шрифт 8×8, аппаратный курсор
  (`virtio_gpu_cursor_move()`).
- **`virtio_input.c`** — планшетный ввод (абсолютные координаты, не дельты
  мыши), требует `-device virtio-tablet-device`; упаковывает состояние в
  одно 64-битное значение (x/y/маска кнопок). Отсутствие устройства не
  фатально — `SYS_MOUSE_STATE` просто деградирует до "нет мыши".
- **`virtio_net.c`** — сетевая карта, единственная из четырёх с ДВУМЯ
  независимыми очередями сразу (receiveq=0 в стиле `virtio_input.c` —
  заранее выставленные device-writable буферы, устройство само их
  заполняет; transmitq=1 в стиле `virtio_blk.c` — драйвер кладёт кадр,
  ждёт used-ring поллингом). Даёт только сырые Ethernet-кадры
  (`virtio_net_send/recv`, `virtio_net_get_mac`) — ни ARP, ни IPv4, ни
  выше в кодовой базе пока нет, это только сам драйвер. Требует
  `-netdev user,id=net0 -device virtio-net-device,netdev=net0`; без него
  `virtio_net_ready()` возвращает 0, `SYS_NET_*` деградируют до -1/0.
  Перед каждым кадром (RX и TX) устройство ожидает 10-байтный
  `virtio_net_hdr` (без `num_buffers` — `VIRTIO_NET_F_MRG_RXBUF` не
  запрашивается) — драйвер добавляет/срезает его сам, наружу отдаёт
  только чистый Ethernet-кадр. Проверено вживую: `fs/rv64/NETTEST.ELF`
  берёт MAC, шлёт широковещательный ARP-запрос "кто держит 10.0.2.2?"
  (гейтвей QEMU SLIRP по умолчанию) и получает настоящий ARP-ответ от
  SLIRP — подтверждает и приём, и отправку через реальную сетевую
  эмуляцию QEMU, а не просто отсутствие падения при вызове.

### Сетевой стек

Полностью пройденный путь этого стека (написан здесь, на RISC-V, ПЕРВЫМ)
позже был построчно портирован на x86 поверх `virtio-net-pci` (legacy
PCI-транспорт вместо MMIO) — см. "Сетевой стек (x86)" выше за деталями
и сравнением реализаций. Короткая версия: протоколы и логика идентичны
слой в слой (`arp.h`/`icmp.h`/`udp.h`/`dhcp.h`/`tcp.h`/`dns.h` переехали
почти без изменений, поменялись только вызовы синтаксиса под другой
syscall ABI), при этом x86-порт свёлся к чисто механическому переносу
почти везде — единственное исключение было архитектурным, не сетевым
(рост FAT12 до 2 МБ потребовал правки `paging.c`, никак не связанной с
самим стеком). Единственный слой, написанный на x86 С НУЛЯ, а не
портированием, — сам `virtio_net.c` (транспорт другой, протокол очередей
тот же) - и именно там нашлись оба реальных бага этого x86-порта (позиция
в ring-буфере по модулю не того числа, и busy-spin, который надо было
заменить на `sti()+hlt()`, чтобы дать QEMU шанс обработать событие).

#### ARP

Первый слой поверх `virtio_net.c`, живёт в userspace как header-only
библиотека `src/user/rv64/arp.h` (в стиле `malloc.h`/`gfx_ui.h` того же
каталога — подключается в один .c-файл, каждая программа получает свою
копию кэша, это не разделяемая между процессами память). Резолв
"IPv4 → MAC" исходящими запросами и ответ на входящие запросы НАШЕГО IP:

- `arp_resolve(ip, mac_out, timeout_ms)` — сначала смотрит в маленьком
  (8 записей) кэше `arp_cache_tbl`, иначе шлёт широковещательный запрос и
  поллит `net_recv()` до таймаута (шаг 20мс). Любой попутно увиденный
  ARP-ответ (даже не от того IP, которого ждали) тоже кладётся в кэш —
  "подслушивание" почти бесплатное.
- `MY_IP` (`10.0.2.15`) — статический IP гостя (не DHCP — клиента DHCP в
  проекте нет, это отдельная работа: свой UDP-слой плюс сам протокол
  DISCOVER/OFFER/REQUEST/ACK). В отличие от более ранней версии этого
  файла, где тот же адрес был просто "заглушкой, которая случайно
  прокатывает" (использовался как sender IP, но никто её не подтверждал),
  теперь `arp_maybe_respond()` реально отвечает на "кто держит MY_IP?" -
  гость по-настоящему владеет этим адресом с точки зрения ARP.
- `arp_maybe_respond(rx, n)` — если входящий кадр является ARP-запросом
  именно `MY_IP`, шлёт корректный unicast-ответ запросившему.
  `arp_resolve()` тоже вызывает её на каждый принятый кадр в своём цикле
  ожидания — попутно.

Проверено вживую `fs/rv64/ARPTEST.ELF`: резолвит гейтвей SLIRP
(`10.0.2.2`) и DNS (`10.0.2.3`) свежими запросами, затем резолвит
гейтвей повторно — второй вызов берёт ответ из кэша мгновенно (0мс)
вместо нового запроса.

Ответчик (`arp_maybe_respond`) проверен ГОРАЗДО строже — не через SLIRP
(там гость сам не может убедиться, что его увидели, не будучи ещё и
клиентом), а через настоящий независимый узел: `-netdev socket`
(прямой TCP-канал между QEMU и Python-скриптом вместо SLIRP) плюс
скрипт, изображающий посторонний хост (`10.0.2.99`), который шлёт
самодельный ARP-запрос "кто держит 10.0.2.15?" и проверяет ответ побайтово.
Это ЖЕ и поймало реальный баг в первой версии `arp_maybe_respond()`:
перепутанные абсолютные/относительные смещения ARP-полей (`target_ip`
читался из середины чужого MAC-адреса вместо настоящего поля tpa) — тест
на СВОЁМ ЖЕ трафике (`ARPTEST`/`PINGTEST`) этого бы никогда не поймал,
потому что тот код никогда не парсит входящие ARP-ЗАПРОСЫ, только ответы.
`fs/rv64/ARPSERVE.ELF` — демо-программа для этого сценария, слушает и
логирует входящие запросы 15 секунд.

#### IPv4 + ICMP (ping)

Третий слой, `src/user/rv64/icmp.h` — тоже header-only, поверх `arp.h`.
Собирает/разбирает IPv4-заголовок (20 байт, без опций и фрагментации) и
ICMP echo request/reply вручную, включая интернет-контрольную сумму
(RFC 1071, дополнение единицы суммы 16-битных слов — одна и та же функция
`ip_checksum()` используется и для IP-заголовка, и для ICMP-сообщения).

- `icmp_ping(dst_ip, seq, timeout_ms, &rtt_ms)` — резолвит MAC через
  `arp_resolve()`, собирает кадр Ethernet+IP+ICMP echo request (32 байта
  payload), шлёт, поллит `net_recv()` каждые 10мс до ответа с совпадающим
  ID (`ICMP_ID`) и seq или таймаута. Возвращает round-trip время в мс.
- `icmp_maybe_respond(rx, n)` — если входящий кадр это ICMP echo request к
  НАШЕМУ `MY_IP`, шлёт echo reply с тем же identifier/sequence/payload
  (учитывает реальный IHL заголовка IP и не читает за пределами того, что
  реально принято). `icmp_ping()` тоже вызывает её на каждый принятый
  кадр в цикле ожидания — попутно, тем же приёмом, что и `arp_resolve()`
  с `arp_maybe_respond()`.

Проверено вживую `fs/rv64/PINGTEST.ELF` — классический `ping -c 4` на
гейтвей SLIRP: 4 из 4 ответов, round-trip 0мс (виртуальная локальная сеть
QEMU, задержка не измерима на этом разрешении таймера).

`icmp_maybe_respond()` проверен так же строго, как ARP-ответчик — через
`-netdev socket` и Python-скрипт, изображающий посторонний хост
(`10.0.2.99`), который сам собирает и шлёт настоящий ICMP echo request
(с контрольной суммой, id/seq и payload). Ответ AxOS проверен побайтово:
`src_ip=10.0.2.15`, `dst_ip=10.0.2.99`, `type=0` (reply), тот же id/seq,
тот же payload эхом. На этот раз обошлось без багов при первой попытке —
сказался урок с ARP-ответчиком (смещения ARP/ICMP-полей писались
аккуратно с самого начала). `fs/rv64/ICMPSRV.ELF` — демо-программа для
этого сценария (аналог `ARPSERVE.ELF`), слушает и логирует входящие
echo request 15 секунд.

#### UDP

Четвёртый слой, `src/user/rv64/udp.h` — header-only поверх `icmp.h`
(переиспользует оттуда `ip_checksum()`/`MY_IP`/`arp_resolve()`, сам ICMP
не нужен, но выносить общие куски в пятый header ради этого не стали).

- `udp_send(dst_ip, dst_port, src_port, payload, len)` / `udp_recv(&src_ip,
  &src_port, &dst_port, buf, max_len)` — собирают/разбирают
  Ethernet+IP+UDP. UDP-чексумма отправляется как `0` — по RFC 768 она
  опциональна для IPv4 (`0` = "не считалась", легальный режим, а не
  битый пакет); считать её пришлось бы по псевдозаголовку с IP-адресами
  отдельно от обычной чексуммы IP-заголовка, а для минимального стека
  это лишняя сложность без выигрыша при работе внутри доверенной
  виртуальной сети QEMU.
- `udp_recv()` неблокирующий (poll, как и всё остальное здесь), учитывает
  IHL заголовка IP (обычно 20 байт, но не хардкодится).

Проверено на РЕАЛЬНОМ внешнем сервисе, не только на своих же пакетах —
`fs/rv64/DNSTEST.ELF` шлёт настоящий DNS A-запрос ("example.com") на
DNS-прокси QEMU SLIRP (`10.0.2.3:53`), который сам форвардит его в
интернет через хост. Получен настоящий ответ (2 A-записи, наш
transaction ID `0x1234` совпал, бит QR=1) — значит и отправка, и приём
UDP работают сквозно, вплоть до настоящего DNS-сервера в интернете, а
не только внутри виртуальной сети QEMU.

#### DHCP-клиент

Пятый слой, `src/user/rv64/dhcp.h` — поверх `udp.h`. Классический DORA
(Discover → Offer → Request → Ack, RFC 2131), без renewal/rebinding,
без DECLINE/RELEASE - один обмен на запуск программы. `DISCOVER`/
`REQUEST` собираются НАПРЯМУЮ (не через `udp_send()`), потому что на
момент отправки своего IP ещё нет - адресат `255.255.255.255`
резолвить через ARP нечего, кадр сразу широковещательный на уровне
Ethernet.

- `dhcp_client(timeout_ms)` — при успехе перезаписывает `g_my_ip`
  (тот самый `MY_IP` из `arp.h`) реально выданным адресом и заполняет
  `dhcp_subnet_mask`/`dhcp_router_ip`/`dhcp_dns_ip`, а заодно копирует
  маску/гейтвей в `g_subnet_mask`/`g_router_ip` (`arp.h`) - см.
  "IP-маршрутизация" ниже, зачем это нужно отдельно от `g_my_ip`.

Проверено вживую `fs/rv64/DHCPTEST.ELF` против настоящего DHCP-сервера,
встроенного в QEMU SLIRP: получена аренда (IP `10.0.2.15` - тот же адрес,
что раньше был зашит статикой, забавное совпадение с нумерацией SLIRP;
маска `255.255.255.0`, router `10.0.2.2`, dns `10.0.2.3`), а затем -
доказательство, что выданный адрес реально рабочий, а не просто "сервер
прислал ответ": `icmp_ping()` на полученный router с этим новым `MY_IP`
прошёл успешно.

#### IP-маршрутизация (`arp_resolve_next_hop()`, arp.h)

**Реальный баг, найденный при добавлении TCP** (см. ниже): все три
предыдущих слоя (`icmp_ping`, `udp_send`, будущий `tcp_connect`)
резолвили MAC адресата НАПРЯМУЮ через `arp_resolve(dst_ip, ...)` - что
работает только если `dst_ip` лежит в локальном сегменте. И `10.0.2.2`
(гейтвей), и `10.0.2.3` (DNS) как раз там лежат, поэтому все тесты до
этого момента (`PINGTEST`/`DNSTEST`/`DHCPTEST`) везло - маршрутизация
никогда не была нужна для их конкретных адресов. Первая же попытка
подключиться к настоящему интернет-хосту (`104.20.23.154` — Cloudflare,
за example.com) обнажила пробел: AxOS слала ARP-запрос "кто держит
104.20.23.154?" прямо в локальный сегмент — на который никто и никогда
не ответит (ни QEMU SLIRP, ни тем более настоящий интернет-хост,
который физически не видит наш L2-broadcast).

Исправлено добавлением `g_subnet_mask`/`g_router_ip` (умолчания
совпадают с тем, что раздаёт SLIRP: `255.255.255.0`/`10.0.2.2`,
перезаписываются DHCP при его использовании) и
`arp_resolve_next_hop(dst_ip, mac_out, timeout_ms)`: если `dst_ip`
внутри `(dst_ip & g_subnet_mask) == (MY_IP & g_subnet_mask)` - резолвит
его напрямую, как раньше; иначе резолвит MAC ГЕЙТВЕЯ, а IP-заголовок
кадра всё равно адресован настоящему `dst_ip` - Ethernet идёт только до
следующего "хопа", дальше маршрутизацией занимается сам гейтвей.
`icmp_ping()`/`udp_send()`/`tcp_connect()` теперь используют её вместо
прямого `arp_resolve()`.

Найдено и исправлено через ту же методику, что и ARP/ICMP-ответчики
раньше - реальный внешний трафик (в этот раз не поддельный узел, а
настоящий `example.com` через SLIRP) вскрыл то, что тесты на
внутрисегментные адреса структурно не могли поймать.

#### TCP

Шестой слой, `src/user/rv64/tcp.h` — минимальный TCP (RFC 793) поверх
`udp.h`, теперь и клиент (`tcp_connect`, активное открытие), и сервер
(`tcp_accept`, пассивное открытие). Только "счастливый путь" одного
соединения за раз: three-way handshake, отправка/приём данных (с
ретрансмитом по таймауту - см. ниже), four-way close. Сознательно не
реализовано - управление окном/congestion control, переупорядочивание
сегментов, SACK - каждое из этого само по себе большой отдельный кусок
работы. Локальный порт клиента зафиксирован (`40000`, как xid в
`dhcp.h`) - раз соединение всегда одно, порт выделять динамически
незачем.

Разбор заголовков IP+TCP (с учётом переменных IHL/data offset) вынесен
в общую `tcp_parse_segment()`, которую используют `tcp_connect`,
`tcp_accept` и `tcp_recv` - раньше (в первой версии, клиент-only) это
было продублировано в двух местах, что уже само по себе рискованно
(offset-баги в ARP уже случались дважды в этом же стеке) - при
добавлении сервера дублировать в третий раз показалось неоправданным,
переписали на общую функцию.

В отличие от UDP, TCP-чексумма ОБЯЗАТЕЛЬНА (RFC 793, не опциональна, как
у UDP над IPv4) - настоящий стек на другом конце молча дропнет сегмент
с неверной суммой. Считается по псевдозаголовку (src/dst IP, protocol,
длина TCP-сегмента) + сам сегмент, той же `ip_checksum()`.

`src/user/rv64/dns.h` - resolve по имени (используется TCP-тестом, т.к.
адрес сервера обычно узнают по хосту, а не по IP): `dns_resolve_a()`
шлёт запрос через `udp_send()`/`udp_recv()` и разбирает ANSWER-секцию
настоящего DNS-ответа (включая сжатие имён - указатели `0xC0xx`,
которыми пользуются практически все настоящие серверы). Позже (см. ниже)
получил кэш ответов и ретрансмит запроса по таймауту.

#### DNS: кэш + ретрансмит по таймауту

Изначально каждый `dns_resolve_a()` слал запрос ровно один раз и просто
ждал `timeout_ms` без повтора - как и у изначального TCP (см. "Ретрансмит
по таймауту" выше), структурная дыра на случай потери UDP-пакета в любую
сторону. Плюс каждый повторный резолв одного и того же хоста снова бил по
сети, даже секунду спустя - расточительно и медленнее, чем нужно.

Добавлено (тот же RTO/exponential-backoff паттерн, что и у TCP -
`DNS_RTO_MS`=300мс, потолок `DNS_RTO_MAX_MS`=2с, до `DNS_MAX_RETRIES`=5
попыток в пределах общего `timeout_ms`):
- **Кэш** - маленькая фиксированная таблица на `DNS_CACHE_SIZE`=8 записей
  (`hostname` + `ip` + `expiry` в тиках `gettime()`), вытеснение: сперва
  свободный слот, иначе round-robin. TTL берётся из самого DNS-ответа
  (реальные секунды жизни записи от сервера), с потолком
  `DNS_CACHE_MAX_TTL_SEC`=3600 - не кэшируем "навечно" по прихоти чужого
  сервера. `TTL=0` в ответе (по RFC значит "не кэшировать") честно не
  кэшируется. **Живёт только в пределах одного процесса** - кэш это
  `static`-массив в data-сегменте, а RV64-процессы каждый раз грузятся с
  нуля, так что между отдельными `run`-запусками кэш не сохраняется, но
  внутри одной программы, резолвящей один хост несколько раз, работает
  в полную силу.
- **Ретрансмит** - при промахе кэша шлёт запрос и повторяет тот же уже
  собранный пакет (тот же `qid`) по RTO, пока не истечёт общий
  `timeout_ms`.

**Проверено вживую**: `fs/rv64/DNSCACHE.ELF` (новый тест) резолвит
`example.com` трижды подряд - 1-й раз бьёт по сети (`347431` тиков
`gettime()`), 2-й раз (тот же хост) - попадание в кэш, `1265` тиков,
**~275× быстрее**, ни одного пакета по проводу; 3-й раз (`cloudflare.com`,
другой хост) снова идёт по сети - кэш корректно не путает разные имена.
Ретрансмит проверен отдельно тем же способом, что и у TCP - Python-скрипт
на `-netdev socket`, изображающий поддельный DNS-сервер, намеренно
игнорирует первые 2 запроса (`example.com`) прежде чем ответить: клиент
трижды посылает запрос с ОДНИМ и тем же `qid` (подтверждает, что это
ретрансмит одного и того же запроса, а не новый), резолв всё равно
доходит до конца успешно с правильным адресом, а кэш после этого
продолжает работать как обычно.

**Найден и исправлен реальный баг в close-логике** при первой проверке:
`tcp_recv()` при получении FIN от собеседника сразу сбрасывал
`c->connected = 0`, из-за чего `tcp_close()` считал соединение уже
полностью закрытым и никогда не отправлял НАШ собственный FIN (застревал
в "получили чужой FIN, но своего не послали" - полу-закрытое состояние
никогда не завершалось). Исправлено разделением на два флага:
`peer_closed` (данных больше не будет) и `connected` (соединение ещё
"живо" с точки зрения `tcp_close()`, пока сам `tcp_close()` его не
сбросит).

Клиентская сторона проверена вживую двумя способами:
- `fs/rv64/TCPTEST.ELF` + Python-скрипт, изображающий полноценный TCP-
  сервер на `-netdev socket` (та же техника, что и для ARP/ICMP-
  ответчиков) - полный цикл from scratch: SYN/SYN-ACK/ACK, обмен
  данными в обе стороны, FIN в обе стороны, побайтовая проверка каждого
  сегмента (включая TCP-чексумму). Именно этот тест поймал баг с
  `tcp_close()` выше - без полноценного собеседника, который явно ждёт
  ответный FIN, баг был не виден.
- `fs/rv64/HTTPGET.ELF` - резолвит `example.com` по-настоящему через
  DNS, поднимает TCP-соединение на порт 80, шлёт настоящий HTTP/1.0 GET
  и получает настоящую страницу с настоящего сервера (Cloudflare) в
  интернете - `HTTP/1.1 200 OK` и полный HTML `example.com` дословно.
  Это же и обнаружило баг с маршрутизацией выше (`TCPTEST.ELF` его не
  ловил, потому что фиктивный сервер живёт по адресу в локальном
  сегменте `10.0.2.99`).

#### TCP-сервер (`tcp_accept()`)

`fs/rv64/TCPSERVE.ELF` - минимальный TCP-эхо-сервер: `tcp_accept()`
принимает одно соединение на порт 8080, эхом отвечает на всё, что
пришлёт клиент (с префиксом `"Echo: "`), закрывается по FIN клиента или
по таймауту бездействия.

**Найден и исправлен ещё один реальный баг** - на этот раз не через
`-netdev socket`, а через самый честный тест из всех: `-netdev
user,hostfwd=tcp::18080-:8080` плюс обычный `socket.connect()` с ХОСТА,
без единого самодельного пакета - настоящий TCP-стек хостовой ОС
разговаривает с TCP-сервером AxOS через настоящий SLIRP-NAT.
Изначально соединение зависало: `tcp_accept()` никогда не видела SYN.
Причина - SLIRP, прежде чем переслать входящее hostfwd-соединение
гостю, должен узнать его MAC через ARP; клиентские соединения хоть
раз да достучались бы наружу первыми, и SLIRP "подсмотрел" бы MAC
пассивно, а чистый сервер, который только слушает и никогда не говорит
первым, никогда не давал SLIRP такого шанса. `tcp_accept()` в цикле
ожидания SYN не звала `arp_maybe_respond()` (в отличие от
`arp_resolve()`/`icmp_ping()`, которые давно это делают) - добавили,
и настоящий хостовой клиент тут же подключился, обменялся данными и
корректно закрыл соединение.

Сетевой стек теперь: **virtio-net → ARP (двусторонний) → маршрутизация
→ IPv4/ICMP (двусторонний) → UDP → DHCP → DNS-резолв по имени → TCP
(клиент и сервер)**, всё проверено вживую против настоящих сервисов,
настоящих независимых узлов и настоящего TCP-стека хостовой ОС.
Изначально намеренно не сделанное - несколько ОДНОВРЕМЕННЫХ соединений/
полноценный accept-backlog (решили, что демонстрации одного соединения
за раз достаточно). Позже всё же добавили - см. "TCP-сервер с
несколькими одновременными соединениями" ниже.

#### Ретрансмит по таймауту (RTO с exponential backoff)

Изначальная реализация была полностью "fire and forget": `tcp_send()`
отправляла сегмент и сразу возвращалась, не дожидаясь ACK; `tcp_connect()`/
`tcp_accept()` отправляли SYN/SYN-ACK только один раз и просто ждали
полный `timeout_ms`, без повторной отправки, если пакет терялся по
дороге. На реальной, надёжной SLIRP-сети внутри QEMU это почти никогда
не проявлялось - но это структурная дыра: настоящая сеть теряет пакеты.

Добавлен общий паттерн: `TCP_RTO_MS` (300мс) стартовый таймаут,
удваивается после каждой неудачной попытки (`TCP_RTO_MAX_MS` = потолок
2с), до `TCP_MAX_RETRIES` (5) попыток для `tcp_send()`. Применено к:
- `tcp_send()` - теперь ДЕЙСТВИТЕЛЬНО ждёт ACK (`seg.ack >= expect_ack`,
  сравнение безопасно относительно переполнения seq через
  `(int)(seg.ack - expect_ack) >= 0`) и повторно шлёт тот же уже
  собранный сегмент (`tcp_tx` переиспользуется как есть - у этого стека
  всегда только ОДИН сегмент в полёте, конвейеризации нет, так что
  "повторить последний исходящий сегмент" - самодостаточный паттерн).
- `tcp_connect()` - повторяет SYN по RTO, оставаясь в рамках изначального
  общего `timeout_ms` (ретраи не расширяют общий бюджет ожидания).
- `tcp_accept()` - аналогично повторяет SYN-ACK, пока ждёт финальный ACK
  клиента.
- `tcp_close()` - полный RTO-backoff (позже, см. "FIN: полный RTO-backoff"
  ниже - изначально был один ретрансмит на середине фиксированного окна).
- `tcp_mux_poll()` (многосоединённый сервер) - при получении ПОВТОРНОГО
  SYN для слота, уже находящегося в `TCP_SLOT_SYN_RCVD`, шлёт SYN-ACK
  ещё раз. Неблокирующий ретрансмит ДАННЫХ (`tcp_mux_send()`) добавлен
  позже - см. "TCP-сервер: неблокирующий per-slot ретрансмит" ниже.

**Проверено вживую** через тот же `-netdev socket` + Python-скрипт
(изображающий поддельного собеседника), что и раньше, но с намеренными
потерями: скрипт игнорирует первые 2 SYN клиента (клиент трижды посылает
SYN с ОДНИМ и тем же фиксированным ISN - подтверждает, что это именно
ретрансмит, а не новое соединение) и первый пакет данных (клиент
повторяет ИДЕНТИЧНЫЙ сегмент с тем же seq/payload) - оба раза после
восстановления соединение доходит до конца штатно (обмен данными,
двусторонний FIN, `tcptest: total 55 bytes received`, exit code 0).

#### HTTP-сервер (`fs/rv64/HTTPSRV.ELF`)

Первое реальное приложение поверх всего стека, не просто тест слоя.
Минимальный HTTP/1.0-сервер: изначально слушал порт 80 через
`tcp_accept()` (одно соединение за раз), разбирает первую строку запроса
(`GET /путь HTTP/1.x`), отдаёт соответствующий файл из FAT12 через
`open()`/`read()`/`close()` (`/` → `INDEX.HTM`, любой другой путь - как
есть, без сопоставления MIME-типов кроме `text/html` по умолчанию) с
корректными `Content-Length`/`Connection: close`, либо `404 Not Found`.
Позже переведён на `tcp_mux_*` - см. "TCP-сервер с несколькими
одновременными соединениями" ниже, логика разбора запроса/отдачи файла
не поменялась ни на строчку.

`src/user/rv64/index.htm` - статическая HTML-страница, которую
`build_riscv.bat` копирует в образ диска как `INDEX.HTM` (та же
директория, куда попадают все скомпилированные `.ELF` - `fs/rv64/` в
git-дереве не заведена намеренно, чтобы не конфликтовать с
`tools/make_fat12_rv64.py`, который иначе взял бы файлы ТОЛЬКО оттуда и
потерял бы все программы).

Проверено настоящим HTTP-клиентом (обычный Python `socket`, ручной
`GET`-запрос, без библиотек уровня HTTP) через `-netdev
user,hostfwd=tcp::PORT-:80` - три запроса подряд, `Content-Length`
совпадает побайтово с реальным размером файла на диске:
```
GET /nonexistent.txt -> 404 Not Found
GET /INDEX.HTM        -> 200 OK (473 байта тела)
GET /                 -> 200 OK (тот же INDEX.HTM, 473 байта)
```

**Известное ограничение исходной, однослотовой версии, не баг**: два
запроса СРАЗУ друг за другом (без паузы) могли не пройти - `tcp_close()`
дренирует эфир 500мс перед тем, как сервер снова готов к `tcp_accept()`,
а конкурентных соединений тут по архитектуре не было (один глобальный
`tcp_conn_t` на всё). Снято переходом на `tcp_mux_*` ниже - несколько
слотов означают, что дренаж закрытия одного клиента больше не блокирует
приём следующего.

### TCP-сервер с несколькими одновременными соединениями

Написан здесь, на RISC-V, ПОСЛЕ x86-стороны - редкий случай в этой паре
стеков, где x86 сделал что-то первым (см. "TCP-сервер с несколькими
одновременными соединениями" в разделе x86 выше за архитектурным
описанием `tcp_mux_*`, тут оно один в один то же самое: пул из
`TCP_MAX_CONNS` (4) слотов, каждый - свой `tcp_conn_t` + стейт-машина
`SYN_RCVD → ESTABLISHED → CLOSING → FREE`, поверх тех же
`tcp_send_segment`/`tcp_parse_segment`, что и исходные `tcp_connect`/
`tcp_accept` - которые не трогались и остаются рабочими для
`tcptest.c`/`tcpserve.c`/`httpget.c`). Единственная содержательная
разница с x86-версией - тайм-ауты подвисших слотов считаются через
`gettime()` (10МГц CLINT), а не `ax_get_ticks()` (100Гц PIT).

`httpsrv.c` переведён на `tcp_mux_listen(80)`/`tcp_mux_poll()`/
`tcp_mux_send()`/`tcp_mux_close()` - разбор HTTP-запроса и отдача файла
из FAT12 не изменились ни на строчку.

Проверено вживую тем же способом, что и на x86: 3 Python-потока
открывают TCP-соединение к `HTTPSRV.ELF` ОДНОВРЕМЕННО (до того, как
хоть один отправил запрос), затем каждый шлёт `GET /` - все трое
получают корректный `INDEX.HTM` (`200 OK`, `473` байта):
```
httpsrv: serving FAT12 files on port 80 ("/" -> INDEX.HTM), up to 4 concurrent connections
httpsrv: client connected from 10.0.2.2
httpsrv: GET /
httpsrv: 200 OK, sent 473 bytes
httpsrv: connection closing
... (ещё дважды, то же самое)
```
Со старым однослотовым `tcp_accept()`-сервером второй и третий клиент
физически не могли бы даже начать рукопожатие, пока первый не закрыл бы
своё соединение целиком - именно это (не баг, а архитектурное
ограничение) описано во врезке выше.

#### TCP-сервер: неблокирующий per-slot ретрансмит

Изначально `tcp_mux_send()` был fire-and-forget (не ждал ACK, не
повторял) - осознанно отложенная работа, задокументированная как
известный пробел: настоящий ретрансмит потребовал бы либо блокирующего
ожидания ACK внутри `tcp_mux_send()` (держало бы ВСЕ остальные слоты,
раз `tcp_mux_poll()` обслуживает их одним вызовом `net_recv()` за раз),
либо честного неблокирующего таймера на слот. Реализован второй вариант.

Каждый слот получил собственную исходящую ОЧЕРЕДЬ (`outbuf`/`out_len`/
`out_acked`/`out_inflight`/`out_retries`/`out_rto`/`out_rto_deadline`/
`close_after`, `TCP_MUX_OUT_BUF_SIZE`=8320Б - с запасом под самый
крупный сегодняшний ответ `httpsrv.c`: заголовок + до 8192Б файла из
`filebuf`). Новая `tcp_mux_pump(idx)` - НЕ блокирует: если сегмент уже
в полёте, просто выходит; иначе шлёт следующий кусок (до 512Б) из
очереди или, если очередь пуста и был запрошен `tcp_mux_close()` -
отложенный FIN. `tcp_mux_send()` теперь копирует данные в очередь слота
и вызывает `pump()` (первый кусок уходит сразу же), `tcp_mux_close()`
- если очередь ещё не пуста - откладывает FIN до полной доставки
(`close_after=1`), иначе закрывает как раньше. `tcp_mux_poll()` в
начале КАЖДОГО вызова (даже если пакет не пришёл) проверяет RTO всех
ESTABLISHED-слотов и ретранслирует зависшие сегменты (или освобождает
слот после `TCP_MAX_RETRIES` неудач - собеседник считается мёртвым);
при получении ACK за наш сегмент - сразу пробует `pump()` следующий
кусок, не дожидаясь ещё одного `poll()`.

**Реальный баг, найденный вживую (не при код-ревью)**: `outbuf` -
обычный массив, а не кольцевой буфер. Первая версия компактификации
не делала вообще ничего - `out_len`/`out_acked` монотонно росли ВСЮ
жизнь соединения. Как только суммарно отправленные+подтверждённые байты
ОДНОГО ответа превышали `TCP_MUX_OUT_BUF_SIZE`, `tcp_mux_send()`
начинал отказывать (`out_len+len > TCP_MUX_OUT_BUF_SIZE`) НАВСЕГДА, даже
после того как более ранние байты давно подтверждены и место логически
свободно. На RISC-V (буфер 8320Б, файлы обычно << этого) баг был
незаметен; вскрылся при переносе на x86 (см. врезку про x86-специфичный
меньший буфер ниже) при запросе файла крупнее буфера -
`httpsrv: GET /SH.BIN` печаталось, а `200 OK, sent N bytes` - никогда
(зависание внутри нового `mux_send_all()` - см. ниже). Исправлено:
при каждом получении ACK за текущий сегмент буфер КОМПАКТИРУЕТСЯ - ещё
не отправленный хвост сдвигается к началу (`out_acked` обнуляется),
так что `out_len` отражает только реально ещё не подтверждённые байты,
а не исторический максимум.

`httpsrv.c` (оба платформы) получил новую `mux_send_all()` - шлёт
данные кусками по 512Б, и если `tcp_mux_send()` вернул -1 (очередь
слота переполнена) - крутит `tcp_mux_poll()` (обслуживая заодно и
ДРУГИЕ слоты), пока не освободится место, вместо того чтобы молча
терять хвост ответа (`tcp_mux_send()`'s -1 раньше никем не
проверялся). Если слот "умирает" (RTO исчерпан, `TCP_MAX_RETRIES`
превышен) во время ожидания - `mux_send_all()` сдаётся, а не крутится
вечно.

**Проверено вживую** (`-netdev socket` + Python-скрипт, изображающий
ДВУХ независимых поддельных клиентов A и B одновременно): A шлёт
`GET /`, получает первый сегмент ответа - скрипт НАМЕРЕННО его
игнорирует (не ACK-ает); пока A "висит" в ожидании ретрансмита, B
посылает СВОЙ SYN и получает ПОЛНОЕ обслуживание (SYN-ACK, данные,
FIN) - подтверждает, что медленный/потерянный A НЕ блокирует B. Затем
A получает тот же сегмент повторно (тот же seq/payload - настоящий
ретрансмит, не новая отправка), ACK-ает его - соединение доходит до
конца штатно. Отдельно (реальный host TCP-клиент через `hostfwd`,
не поддельный) - запрос файла крупнее `TCP_MUX_OUT_BUF_SIZE`
(`SH.BIN`, x86) воспроизвёл баг с зависанием ДО исправления
компактификации и подтвердил полную доставку (все байты, правильный
`Content-Length`) ПОСЛЕ.

#### FIN: полный RTO-backoff

`tcp_close()`/`tcp_mux_close()` тоже переведены на полный RTO-backoff
(были - один ретрансмит на середине фиксированного окна) - см. "FIN:
полный RTO-backoff" в x86-разделе за полным описанием, включая реальный
баг с преждевременным инкрементом `snd_nxt` (ловивший "повтор" как
СЛЕДУЮЩИЙ сегмент вместо настоящего повтора потерянного FIN) - тот же
баг был исправлен здесь синхронно. Два дополнительных бага ядра,
найденных попутно (NX-краш на границе W^X, затем SMAP-краш после первой
попытки исправления, оба из-за отсутствия выравнивания `.data` на
страницу в `user.ld`/линковке) - **x86-специфичны**, RISC-V использует
настоящий ELF-загрузчик без этой проблемы вообще.

#### Сравнение с x86-портом

| | RISC-V (здесь, оригинал) | x86 (порт, см. "Сетевой стек (x86)" выше) |
|---|---|---|
| Транспорт | virtio-net, **MMIO** | virtio-net-pci, **legacy PCI (I/O-порты)** |
| Очередь устройства | Queue Num — RW, драйвер сам выбирает размер | Queue Size — **read-only**, QEMU навязывает 256 |
| Физическая память под очередь | отдельный постраничный аллокатор `pmem.c` | кучa identity-mapped — `malloc()`-указатель уже физический адрес, страница вручную выравнивается |
| Ожидание завершения TX | тугой busy-spin (работает без проблем) | тот же busy-spin **завис** - понадобился `sti()+hlt()` (см. "Драйвер virtio-net" выше) |
| Протоколы ARP/ICMP/UDP/DHCP/TCP/DNS | написаны здесь первыми, весь путь багов пройден тут | построчный порт, багов почти не было — вся сложность уже была найдена и исправлена на этой, RISC-V, стороне |
| Единственный НЕ механический шаг x86-порта | — | рост FAT12 до 2 МБ пересёк границу фиксированной `PD[1]` — потребовал правки `paging.c`, никак не связанной с сетью |

Итог: два независимых стека, написанных с нуля под разные транспорты
устройства, сошлись к одному и тому же протокольному коду - лучшее
подтверждение, что уровни ARP/IPv4/UDP/TCP/DNS в `arp.h`/`icmp.h`/
`udp.h`/`dhcp.h`/`tcp.h`/`dns.h` спроектированы действительно независимо
от конкретного драйвера NIC.

### Куча ядра

`src/arch/riscv64/heap.c` — тот же tag+redzone+канарейка+карантин, что и на
x86 (см. "Усиление кучи" выше); арена стартует с 16 КБ, растёт по странице.
Тег — честные 64 бита (`unsigned long`, родное машинное слово на RV64/lp64
— в отличие от x86-ядра, которому пришлось явно использовать `unsigned long
long` из-за LLP64 у MinGW). До этой доработки RV64-ядро было единственным
из четырёх аллокаторов проекта (x86-ядро/x86-userspace/RV64-userspace/
RV64-ядро) вообще без какой-либо защиты. Userspace-куча
(`src/user/rv64/malloc.h`) устроена глубже — с явной shadow-memory таблицей
тегов (`mte_check`/`mte_tag`/`mte_check_tag`), а не только tag+redzone.

Отдельно от тегов (защита от UAF/overflow) — сам СТАРТОВЫЙ АДРЕС этой
кучи теперь тоже случаен каждую загрузку (KASLR), см. "KASLR/ASLR" выше.

### Графика на RISC-V: догоняем x86

x86-сторона (`src/kernel/gfx_shell.c`) рисует напрямую в собственный
backbuffer 800×600×32bpp с альфа-блендингом, градиентами и мягкими
скруглёнными тенями (радиус 14-16px). RISC-V-сторона (`virtio_gpu.c` +
`src/user/rv64/gfx_ui.h`/`window.h`) сидела на 640×480 и резала радиус
скругления до `UI_MAX_R=4` - на порядок меньше x86 - из-за отдельного
ограничения: RV64-процесс имеет ОДНУ 4КБ страницу стека на весь вызов
(`elf_loader.h`'s `USER_STACK_VA`), и буфер сохранения углов
`save[4][R*R]` при R=16 (4×16×16×4=4096Б) один пробивал всю страницу
насквозь (`axdesk.elf` падал с store-page-fault на первой же попытке).

Закрыты оба разрыва:

1. **Разрешение 640×480 → 800×600** (`virtio_gpu.h`'s `GPU_FB_WIDTH`/
   `GPU_FB_HEIGHT`) - чисто механическая правка: ВСЕ потребители
   (`console.c`'s сетка символов, `kernel_main.c`, `syscall.c`'s
   `SYS_GFX_INFO`, `virtio_input.c`'s масштабирование координат) уже
   были параметризованы через эти константы, а ВСЕ userspace GUI-
   программы (`axdesk.c`, `axpaint.c`, `gfxdemo.c`, `gfxtext.c`) узнают
   размер экрана динамически через `gfx_info()` - ни одной правки в
   самих приложениях не понадобилось. Framebuffer (постраничный
   bump-аллокатор, `alloc_page()`) вырос с 300 до 469 страниц - тривиально
   в 128МБ RAM QEMU.
2. **`UI_MAX_R` 4 → 16** (`gfx_ui.h`) - буфер сохранения углов переведён
   с локального (на стеке) на `static` (BSS) - тот же приём, что уже
   применялся к `tcp_rx`/`tcp_tx`/`dns_cache`/`tcp_slots` в сетевом
   стеке именно по этой причине (см. "RV64 user stack is ONE 4KB page" в
   памяти проекта). Статическая память не ограничена стековой страницей.
   Радиус скругления окон/иконок (`window.h`'s `WIN_RADIUS`,
   `axdesk.c`'s радиус иконок) поднят до 14-16, теперь визуально
   совпадает с x86's `CARD_R=16`/`ICON_R=14`. Свотчи палитры `axpaint.c`
   (маленькие, ~32px) получили более скромные 8px - радиус 16 на
   32-пиксельной кнопке выглядел бы каплей, а не скруглённым углом.

**Осознанно не перенесено**: x86's `shadow_round()` рисует тень
per-pixel по ВСЕЙ площади скруглённого прямоугольника - дёшево там,
потому что это прямая запись в свой backbuffer. На RISC-V каждый пиксель
идёт отдельным `gfx_putpixel`/`gfx_getpixel` syscall - полный проход по
площади иконки/окна означал бы тысячи syscall'ов на одну тень. `gfx_ui.h`'s
`ui_shadow()` поэтому остаётся урезанным до L-образной полоски (только
видимая за пределами прямоугольника часть) - уже существовавший,
осознанный компромисс под цену ecall'ов, не тронут.

Проверено вживую: `axdesk.elf`/`axpaint.elf` через screendump на новом
800×600 (иконки/свотчи заметно круглее, ни обрезки, ни сдвига холста),
курсор через QMP `input-send-event` долетает до правого нижнего угла
нового экрана (не зажат старым 640×480 маппингом), никаких
`*** PAGE FAULT` сообщений при старте (то, что раньше ловилось на
UI_MAX_R=16-на-стеке).

### Загрузка BMP-иконок (`src/user/rv64/bmp.h`)

`axdesk.c` раньше рисовал все 4 иконки launcher'а как одноцветные
карточки без реальной графики. Новый `bmp.h` (header-only, в стиле
`gfx_ui.h`/`window.h`) - минимальный BMP-декодер, только "счастливый
путь": `BITMAPFILEHEADER`(14Б)+`BITMAPINFOHEADER`(40Б), 24 или 32 бита
на пиксель, без сжатия (`BI_RGB`), только стандартный bottom-up порядок
строк (`biHeight>0`) - то подмножество, которое реально экспортируют
графические редакторы для простых непрозрачных значков. Максимум
64×64 - иконки, не обои: `bmp_draw()` шлёт один `gfx_putpixel()` syscall
на пиксель (bulk-blit syscall'а нет), для полноэкранной картинки это
были бы сотни тысяч ecall'ов, для 32×32 иконки при одноразовой
отрисовке — незаметно (тот же принцип, что и у теней/скруглений
`gfx_ui.h`). Декодируется в `static`, не стековый, буфер - тот же урок
про единственную 4КБ страницу стека RV64-процесса.

Загрузка идёт через уже существующие `open()`/`read()`/`close()`
(`syscall.h`) - никакой новой инфраструктуры не понадобилось, RISC-V
userspace и так уже читает файлы из FAT12 (например `httpsrv.c`). Без
`lseek()` (такого syscall'а тут нет) - если `bfOffBits` больше 54,
разница вычитывается и отбрасывается последовательным `read()`.

Изначально сделано только для RISC-V - x86-сторона перенесена позже
(без чтения с диска, см. "BMP-иконки на x86" ниже).

4 новые иконки (`term.bmp`/`about.bmp`/`paint.bmp`/`power.bmp`,
32×32, сгенерированы через PIL - простая геометрия: монитор с
`>`-промптом, "i" в кружке, кисть, символ питания) лежат рядом с
`index.htm` в `src/user/rv64/` (тот же прецедент статического не-ELF
ассета), копируются в `rv64build\fs\rv64\` под 8.3-именами
`TERM.BMP`/`ABOUT.BMP`/`PAINT.BMP`/`POWER.BMP`.

Проверено вживую: screendump `axdesk.elf` - на всех 4 карточках видны
настоящие декодированные значки, подпись не наезжает на картинку.
Fallback (отсутствующий/битый файл) проверен намеренно - временная
подмена `TERM.BMP` на несуществующее имя дала карточку БЕЗ иконки
(только цвет+текст), без единого краша, остальные 3 иконки не
затронуты. Клик через QMP по иконке AxAbout после всех правок всё ещё
запускает `AXABOUT.ELF` (`exec()` не задет).

### BMP-иконки на x86 (`src/kernel/bmp.h`)

Перенесено на x86 позже - `gfx_shell.c`'s `draw_icon()` раньше рисовал
"символы" из обычных ASCII-глифов шрифта (`>`/`_`/`~` для терминала,
`?`/`i` для About) вместо настоящей графики. Формат/ограничения decoder'а
те же, что и на RISC-V (см. выше) - но БЕЗ файлового ввода-вывода:
`gfx_shell.c` вообще не имеет доступа к диску/FAT12 (отдельный мини-
кернел), так что вместо чтения из FAT12 картинки **встраиваются в
бинарник на этапе сборки**.

Новый `tools/bmp_to_c.py` конвертирует `.bmp`-файл в C-массив байт
(`static const unsigned char <name>_data[]` + `<name>_size`) - тот же
принцип, что и у `tools/make_elf.py`/`make_fat12.py` (небольшая, узкая
build-утилита). `build.bat` вызывает его ПЕРЕД компиляцией `gfx_shell.c`,
результат (`build\icons_data.h`, генерируется каждую сборку, не
коммитится - `build/` и так в `.gitignore`) попадает в `-I build`.
Исходные `.bmp` (те же самые `term.bmp`/`about.bmp`, что и на RISC-V -
скопированы в `src/kernel/`, не шарятся между платформами напрямую -
тот же принцип полного дублирования, что и у остального gfx-кода этого
проекта) декодируются один раз (кэш в `static bmp_image_t`, не при
каждом кадре) и рисуются прямо в `BACKBUF` через уже существующий
`px()` - никаких syscall'ов вообще, в отличие от RISC-V, где та же
операция стоит одного `gfx_putpixel()` ecall'а на пиксель.

Проверено вживую: headless QEMU (`os-image-shell.bin`, `-vga std`),
screendump - обе иконки (TERM/ABOUT) показывают настоящие декодированные
значки (тот же монитор с `>`-промптом и "i" в кружке, что и на RISC-V)
поверх скруглённых карточек, подпись не наезжает. Клик мышью
допроверен отдельно (см. врезку "Калибровка относительной PS/2-мыши
через QMP" ниже) - наведение подсвечивает карточку (голубой фон, белая
рамка, чёрный текст - как и задумано в `draw_icon()`), клик открывает
экран Terminal (`AxOS Terminal v1.0`, приглашение `>`) - вся цепочка
ввода (QMP → эмуляция PS/2 → прерывание → `mouse.c` → `gfx_shell.c`)
подтверждена работающей от начала до конца.

**Калибровка относительной PS/2-мыши через QMP** (пригодится для
будущих тестов этого шелла): `mouse_get_x()*10`/`mouse_get_y()*24`
(`gfx_shell.c`) переводят координаты из сетки 80×25 (`mouse.c`) в
экранные 800×600 - большие "прыжковые" relative-дельты (напр. ±2000
для сброса в угол) на практике режутся QEMU на много мелких PS/2-
пакетов и не успевают долиться до следующего screendump'а без
дополнительной задержки - лучше слать один аккуратный `rel`-делта
в пределах одного пакета (≲127) и сверяться скриншотом на каждом шаге.
По оси Y КОД `mouse.c` читается как `mouse_y -= dy` (что подсказывает
инверсию), но эмпирически положительное значение `dy`, отправленное
через QMP, ДВИГАЕТ КУРСОР ВНИЗ (т.е. по факту не инвертировано с точки
зрения вызывающего QMP) - доверять чтению исходника тут не стоит,
калибровать по факту screendump'ом.

### Сборка и запуск

`build_riscv.bat`: компилирует ядро (`-march=rv64imac_zicsr -mabi=lp64
-mcmodel=medany -ffreestanding -fno-stack-protector`) и ~20 отдельных
статически слинкованных ELF-программ, копирует их в `rv64build\fs\rv64\`
(имена 8.3, напр. `HELLO.ELF`, `AXSH.ELF`, `SPIN.ELF`), затем
`python tools\make_fat12_rv64.py` собирает `rv64build\disk.img`. Каталог
`rv64build\` — build-артефакт, в `.gitignore`, не хранится в репозитории.
Команда для запуска — см. "Быстрый старт" выше.

## Структура репозитория

### Используется текущей сборкой (`build.bat`)

- `src/boot/boot.asm` — загрузчик (реальный режим → защищённый режим, чтение
  ядра с диска).
- `src/boot/switch_to_pm.asm` — переключение в защищённый режим (подключается
  через `%include` из `boot.asm`).
- `src/lib/string.asm` — строковые функции для загрузчика (`%include` из
  `boot.asm`).
- `src/kernel/gdt.asm` — таблица GDT (ring0/ring3 сегменты + TSS),
  подключается через `%include` из `boot.asm`.
- `src/kernel/kernel_entry.asm` — точка входа `_start`, вызывает
  `kernel_main()`.
- `src/kernel/idt.asm` — таблица прерываний и низкоуровневые обработчики
  (таймер, клавиатура, page fault, `int 0x80`).
- `src/kernel/syscalls.asm` — мост `int 0x80` → `syscall_dispatch()`.
- `src/kernel/usermode.asm` — переход в ring3 (`enter_usermode`).
- `src/kernel/kernel.c` — основная логика ядра: инициализация, shell,
  обработчики прерываний на C, таблица syscall'ов.
- `src/kernel/screen.c` — вывод текста, скроллинг, `clear_screen`,
  `backspace`.
- `src/kernel/paging.c`/`paging.h` — страничная память, identity-map,
  read-only `.text`, `#PF`-обработчик, `paging_create_user_directory`
  (приватный PD/PT для изолированных `run`-задач).
- `src/kernel/tss.c`/`tss.h` — настройка TSS (переключение стека
  ring3 → ring0).
- `src/kernel/heap.c`/`heap.h` — `malloc`/`free`.
- `src/kernel/tasking.c`/`tasking.h` — preemptive round-robin планировщик
  (`task_create`, `task_create_user`, `task_create_user_isolated`,
  `schedule`).
- `src/kernel/selftest.c`/`selftest.h` — регрессионные тесты heap/paging/FAT12
  (команда `selftest`, `run_self_tests`).
- `src/kernel/vfs.c`/`vfs.h` — тонкий VFS-слой (vtable `vfs_driver_t`):
  `kernel.c`/`selftest.c` обращаются к `vfs_*`, единственный
  зарегистрированный драйвер - FAT12.
- `src/fs/fat12.c`/`fat12.h` — драйвер FAT12-тома на `build/disk.img`
  (`fat12_init`/`fat12_flush` через IDE, чтение и запись).
- `src/drivers/ide.c`/`ide.h` — PIO-драйвер ATA/IDE (primary master, LBA28),
  доступ к `build/disk.img` (команды `diskinfo`/`diskread`/`diskwrite`).
- `src/drivers/pci.c`/`pci.h` — драйвер шины PCI (config space mechanism #1,
  порты `0xCF8`/`0xCFC`): `pci_scan()` обходит bus 0 и рекурсивно мосты
  PCI-PCI, `pci_class_name()` — таблица базовых PCI class code. Доступ из
  ring3 — `lspci.bin` (`src/user/lspci.c`, `SYS_PCI_GET_DEVICE`), confined
  классом `pci_raw` (см. "MAC" выше) — как и `disktool.bin`, обычный запуск
  получает `avc: denied`.
- `src/drivers/keyboard.h` — порты ввода-вывода и таблица скан-кодов
  клавиатуры.
- `src/user/syscall.h` — общий ABI системных вызовов (`SYS_*`-константы и
  структуры аргументов) для ядра и ring3-программ.
- `src/user/start.asm`, `src/user/user.ld` — общая точка входа `_start`
  (вызывает `user_main()`, затем `SYS_EXIT`) и линковка на `0x100000` для
  всех ring3-демо.
- `src/user/hello.c`, `src/user/exitdemo.c`, `src/user/crashdemo.c` —
  исходники демо-программ, собираются в `build/*.bin` и копируются в
  `fs/HELLO.BIN`/`fs/EXIT.BIN`/`fs/CRASH.BIN`. `hello.c` — бесконечный цикл
  (демонстрирует syscalls, `run HELLO.BIN`), `exitdemo.c` — нормальный
  выход через `SYS_EXIT` (`run EXIT.BIN`), `crashdemo.c` — выход за пределы
  своего окна → page fault → kill (`run CRASH.BIN`). См. "Жизненный цикл
  задач".
- `kernel.ld` — линкер-скрипт (`ENTRY(_start)`, секции начинаются с `0x1000`).
- `fs/` — содержимое FAT12-раздела (`MOTD.TXT`, `STARTUP.CFG`), упаковывается
  `tools/make_fat12.py`. `fs/HELLO.BIN` генерируется при сборке (см. выше) и
  не хранится в git (`*.bin` в `.gitignore`).
- `tools/make_fat12.py`, `tools/nasm.exe` — генератор FAT12-образа и
  ассемблер.
- `tools/smoke_test.py`, `tools/regression_test.py`,
  `tools/exec_regression_test.py`, `tools/ai_ask_regression_test.py` —
  headless-тесты в QEMU через monitor (`smoke_test.py` — загрузка до
  шелла, `regression_test.py` — команда `selftest`, `exec_regression_test.py`
  — ELF-загрузчик: `echo` с аргументами и через AxSH/`ax_exec`, и через
  kernel-shell `run` — у `selftest` нет своего покрытия `do_exec`/`run`,
  без этого теста загрузчик проверялся бы только косвенно, через
  автозапуск AxSH; `ai_ask_regression_test.py` — режим `ai ask`: точное
  совпадение по ключевой фразе, совпадение по одному "голому" ключевому
  слову, дефолтный ответ при отсутствии совпадений, и чистый `exit`
  обратно в AxSH-промпт); общий код (`find_qemu`/`decode_vga`/`send_text`/
  `launch_qemu`/`dump_screen`) вынесен в `tools/qemu_test_helpers.py` —
  раньше каждый тест нёс свою копию, и именно расхождение копий
  (забытый `.lower()` для `sendkey`) стало причиной первого же бага в
  `exec_regression_test.py`. Используются в CI.
- `build.bat` — основной скрипт сборки, `run.bat` — запуск в QEMU.

## Формат итогового образа

Подробности и историю формата см. в [`docs/image-format.md`](docs/image-format.md).
Текущий `build.bat` собирает `build/os-image.bin` (1.44 МБ, как дискета)
так:

1. `build/boot.bin` + `build/kernel.bin` склеиваются друг за другом
   (`copy /b`);
2. файл дополняется нулями до `1 474 560` байт (1.44 МБ).

QEMU запускает образ как floppy (`-drive format=raw,file=build\os-image.bin,if=floppy -boot a`).

Отдельно `build/disk.img` (10 МБ, физический диск IDE) содержит в первых
256 КБ (LBA 0-511) FAT12-том, сгенерированный `tools/make_fat12.py` из
содержимого `fs/` (`build/fat12.bin`) — его грузит `fat12_init()` через IDE
при старте ядра.

## Текущий статус

**x86-64:**
- ✅ Загрузчик: реальный режим → защищённый режим → **long mode**
  (PAE/EFER.LME/CR0.PG), чтение ядра с дискеты.
- ✅ GDT (64-битный TSS) / IDT (64-битные врата), таймер PIT (100 Гц),
  клавиатура через IRQ.
- ✅ Страничная память: полная 4-уровневая адресация (PML4→PDPT→PD→PT),
  identity-map 4 МБ, `.text` read-only, `CR0.WP`, **NX/SMEP/SMAP** +
  постраничный **W^X** для пользовательских программ.
- ✅ GCC `-fstack-protector-strong` для ядра (64-битная канарейка).
- ✅ Ring3 (32-битный compatibility mode) + TSS64 + `int 0x80` (системные
  вызовы с `DPL=3`, ~36 syscall'ов).
- ✅ Куча: 32 МБ, `malloc`/`free` с разбиением и слиянием блоков; усиление в
  духе hardened_malloc/GrapheneOS — magic+канарейка-с-64-битным-тегом
  против double-free/overflow, левый redzone против underflow, карантин из
  8 последних `free()` (см. "Куча" выше).
- ✅ "ASLR-подобный" разброс начального стека изолированных `run`-задач
  (см. "Запуск пользовательских программ").
- ✅ MAC (Type Enforcement в духе SELinux), 9 классов, + MLS-уровни
  чувствительности для буфера обмена, + seccomp-подобная маска syscall'ов
  на процесс (см. разделы "MAC"/"MLS" выше).
- ✅ Preemptive планировщик с приоритетами (`nice <pid> <1-10>`, ring0 и
  ring3 задачи, per-task `TSS.RSP0`) + команда `ps`.
- ✅ FAT12-том на `build/disk.img` через IDE (чтение и запись, персистентно)
  + полноценный Unix-подобный shell AxSH (конвейеры/редирект/фон) поверх
  внешних ELF-программ.
- ✅ Загрузчик пользовательских программ с FAT12 (команда `run`,
  настоящий ELF32 — см. "ELF32-загрузчик"), каждая — в своём приватном
  наборе PML4/PDPT/PD/PT (изоляция памяти).
- ✅ Жизненный цикл задач: `SYS_EXIT` при нормальном выходе, kill при page
  fault изолированной задачи (без halt всей системы), реап и
  переиспользование слотов `run`.

**RISC-V (rv64):**
- ✅ Boot под OpenSBI, S-mode/U-mode, Sv39 с постраничным W^X-харднингом
  ядра и приватными таблицами на процесс.
- ✅ Тот же вытесняющий планировщик с приоритетами (`nice`), что и на

- ✅ virtio-драйверы: блочное устройство, GPU (framebuffer 800×600),

- ✅ FAT12 (тот же формат, что и x86), куча с тем же tag+redzone+

- ✅ Shell AxSH/RV64 + ~20 пользовательских программ (тесты кучи/W^X/

- ✅ Найден и исправлен фундаментальный баг: таймерное прерывание не
  включалось вообще никогда ни на одной загрузке (см. "RISC-V порт" выше).

    `vfs_driver_t` (`init`/`is_ready`/`is_locked`/`set_locked`/`list`/`cat`/

    Виртуальное окно `0x100000`-`0x108000` переотображается на физический

    ("no read up") для буфера обмена — см. "MLS" выше.
  - ✅ настоящий ELF32-загрузчик пользовательских программ
    (`src/kernel/elf.c`/`elf.h`, `tools/make_elf.py`) вместо плоских

  - ✅ AI-демо (`ai.bin`, `src/user/ai.c`): крошечный MLP (3-6-1) учится
    предсказывать любую из 256 булевых функций трёх аргументов (таблица
    истинности — аргументом командной строки или интерактивно) обратным

  - ✅ SMEP (CR4[20]) и SMAP (CR4[21]) — CPUID-детект, харднинг против

  - ✅ переход ядра на **x86-64 long mode** (4-уровневая адресация PML4→

  - ✅ `-fstack-protector-strong` для самого ядра (64-битная канарейка,
    раньше защита была только у userspace) — см. "Stack-protector" выше.
  - ✅ **приоритеты планировщика** (`nice <pid> <1-10>`, weighted

  - ✅ **RISC-V (rv64) порт** — независимое S-mode/U-mode ядро под

## CI

`.github/workflows/ci.yml` — два независимых job'а на `windows-latest`,
запускаются на каждый push/PR:

- **`build-and-smoke-test`** (x86-64): ставит `w64devkit` (multilib
  gcc — умеет и `-m64` для ядра, и `-m32` для юзерспейса/`libaxiom`,
  см. `KFLAGS`/`UFLAGS` в `build.bat`), собирает `build.bat`, проверяет
  размер `kernel.bin` (лимит 89 секторов), ставит QEMU и гоняет все 4
  headless-теста (`smoke_test.py`, `regression_test.py`,
  `exec_regression_test.py`, `ai_ask_regression_test.py`).
- **`build-riscv`**: ставит xPack `riscv-none-elf-gcc 15.2.0-1`,
  собирает `build_riscv.bat`, проверяет, что `kernel.elf`/`disk.img`
  реально появились по ожидаемым путям.

### Реальные баги, найденные только на чистом CI-раннере

Локальная машина разработки годами накапливала окружение (тулчейн,
конкретная версия QEMU, junction-папка `C:\axos_build` для обхода
кириллического пути репозитория), которое маскировало несколько
реальных проблем — вскрылись только на «чистом» GitHub-раннере, где
ничего из этого не установлено:

- **Тулчейн**: `mingw-w64-i686-gcc` (пакет MSYS2, стоял в CI раньше) —
  однонаправленный 32-битный, падал на первом же `-m64`-шаге сборки
  ядра (`cc1.exe: sorry, unimplemented: 64-bit mode not compiled in`).
  Заменено на `w64devkit` — тот же тулчейн, что и для локальной
  разработки, multilib, умеет оба режима одним `gcc.exe`.
- **`tools/bmp_to_c.py`**: `open(out_path, "w")` без
  `encoding="utf-8"` — писал кириллический авто-сгенерированный
  комментарий; локальная Python-локаль это проглатывала, а на
  CI-раннере (`cp1252`) падал с `UnicodeEncodeError`.
- **`tools/qemu_test_helpers.py`**: использовал `qemu-system-i386`
  (без long mode) вместо `qemu-system-x86_64 -cpu Broadwell` — ровно
  та ошибка, что уже описана в Troubleshooting ниже, просто этот общий
  модуль (используют все 4 регрессионных теста) никогда не приводили в
  соответствие с собственной документацией. На реальном железе
  x86-64-ядро триплфолтится на far jump в 64-битный сегмент сразу
  после входа в long mode; `-no-reboot` превращает это в мгновенный
  тихий `exit 0`, неотличимый со стороны теста от «QEMU не запустился».
  Нашли через `-d int` трассировку прерываний, не по логам.
- **Тайминги набора / таймаут `selftest`**: как только загрузка реально
  заработала (см. выше), вскрылись ещё два скрытых бага, которые
  раньше просто никогда не доходили до исполнения — `send_text()` слал
  символы каждые 0.05с и они терялись при печати («echo» превращалось
  в «ech»), а 90-секундного бюджета `regression_test.py` на `selftest`
  не хватало на реальный прогон FAT12-подтеста (~65–90с end-to-end).
  Оба увеличены (0.15с, 150с).
- **`tools/make_fat12_rv64.py`**: писал `disk.img` по абсолютному пути
  `C:\axos_build\rv64build\disk.img`, который на машине разработчика —
  directory junction на сам репозиторий; на CI такой папки нет,
  `os.makedirs(..., exist_ok=True)` создавал её с нуля в «никуда», и
  файл появлялся вне репозитория. `kernel.elf` при этом собирался по
  обычному относительному пути и находился — отсюда «сборка прошла, а
  один из двух артефактов не находится». Заменено на путь относительно
  самого скрипта (тот же приём, что уже был у поиска `fs/rv64/`).

Мораль: если тест никогда не проходил на чистой машине — то, что он
«всегда работал у меня», ничего не доказывает.

## Контрибьюции

Подробное руководство для контрибьюторов доступно в [`CONTRIBUTING.md`](CONTRIBUTING.md).

Кратко:
1. Сделайте форк репозитория.
2. Создайте ветку по шаблону `feature/имя` или `fix/имя`.
3. Добавьте описание изменений и, если меняли ядро, проверьте `build.bat` и
   проверку в QEMU (`run.bat`).

### Стиль и требования

- Assembler: NASM-style, `[bits 32]`/`[bits 16]` явно, комментарии на русском
  для нетривиальных мест (по аналогии с `paging.c`/`heap.c`).
- C: совместимость с `gcc -m32 -ffreestanding -mno-sse -mno-sse2 -mno-mmx`
  (см. флаги в `build.bat`). Без libc — только то, что реализовано в самом
  ядре.
- Перед PR: убедитесь, что `build.bat` проходит без ошибок и `kernel.bin`
  не превышает 45568 байт (лимит — 89 секторов, которые грузит `boot.asm`).

### PR: оформление и чек-лист ревью

- Описание: кратко что сделано и почему.
- Сборка: `build.bat` проходит локально без ошибок.
- Проверка: загрузка в QEMU (`run.bat`), нет `*** PAGE FAULT ***` и тройных
  сбоев; затронутые команды shell проверены вручную.
- Документация: обновлён `README.md` или добавлены docs в `docs/`, если
  менялась архитектура/карта памяти/список команд.
- Если изменение большое — откройте issue перед реализацией.

## Troubleshooting

### Ошибка "NASM не найден"
- Используйте локальную копию `tools\nasm.exe` (её уже использует
  `build.bat`) или установите NASM и добавьте в `PATH`.

### Ошибка "gcc"/"ld"/"objcopy не найден"
- Установите `w64devkit` в корень репозитория (папка `w64devkit/`) —
  `build.bat` сам добавляет `w64devkit\bin` в `PATH`.

### `kernel.bin` слишком большой / `boot.bin` не грузит ядро целиком
- `boot.asm` читает с диска ровно 89 секторов (45568 байт) под ядро. Если
  `build\kernel.bin` больше — урежьте код/данные или увеличьте число секторов
  в `boot.asm`.

### `build\fat12.bin` не создаётся / `tools\make_fat12.py` падает
- Убедитесь, что установлен Python и доступен в `PATH`.
- Проверьте содержимое каталога `fs/` (`MOTD.TXT`, `STARTUP.CFG`).

### QEMU не запускается (x86-64)
- Установите QEMU для Windows и поправьте путь в `run.bat`
  (`C:\Program Files\qemu\qemu-system-x86_64.exe`) или используйте
  `qemu-system-x86_64`, если он есть в `PATH`.
- **Обязательно `qemu-system-x86_64`, не `qemu-system-i386`** — с переходом
  ядра на long mode образу нужен `EFER.LME`, которого нет у `i386`-эмулятора
  (образ либо не загрузится, либо триплфолтнет сразу после
  `wrmsr`/`CR0.PG`). Реально ловили этот баг вживую в CI — `tools/qemu_test_helpers.py`
  (общий модуль всех 4 headless-тестов) когда-то использовал `qemu-system-i386`,
  несмотря на этот же самый совет здесь; см. "CI" выше за подробностями.
- Нужен флаг `-cpu Broadwell` (или новее) для нативной поддержки SMAP —
  без него ядро всё равно загрузится (детектирует отсутствие SMAP через
  CPUID и просто не включит CR4[21]), но часть харднинга не будет иметь
  эффекта. Haswell поддерживает SMEP, но не SMAP.

### QEMU не запускается (RISC-V)
- Нужен `qemu-system-riscv64` (отдельный от x86-64 бинарник QEMU) и
  прошивка OpenSBI — используйте `-bios default`, QEMU сама подставит
  встроенный OpenSBI для машины `virt`.
- Без `-device virtio-tablet-device` мышь не будет работать в
  `axpaint`/`axdesk` (клавиатура при этом останется рабочей) —
  `virtio_input.c` в этом случае просто печатает предупреждение и
  деградирует, не падает.

### `*** PAGE FAULT at 0x... ***` в QEMU (x86-64)
- Обращение к памяти за пределами замапленных областей (см. [карту
  памяти](#карта-памяти-x86-64)) либо запись в страницу `.text`/данных
  без `RW` (`CR0.WP`, W^X). Отдельно смотрите на подпись фолта: `[SMEP/NX]`
  — ядро попыталось исполнить пользовательскую страницу; `[SMAP]` — ядро
  обратилось к пользовательским данным без `stac`/`smap_allow()`.
